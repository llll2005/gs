## 結論

- **官方原版在當前資料上的 held-out：PSNR 25.79／SSIM 0.833／LPIPS 0.176**，N 24.48M、ckpt 41 GB、test 峰值實佔 11.9 GB、每幀 0.088 s。
- **官方 aerial release 的 trim 從未執行**：從 .ckpt 初始化時 renderer 被 coarse 的（`diable_trimming: true`）蓋掉，resolved config 卻仍記 false。
  一行修正後官方 b3：N 5.23M → 0.91M（-83%）、峰值 7.30 → 2.75 GB、val 31.69 → 30.87；我方程式碼跑同配方 0.93M／30.91 => 一致。
- **論文 §5.1 的設定（ω=0.9、prune_ratio 0.025）與 release 不同**：照論文設定，b3 3.05M／31.78、b6 5.31M／30.35 —— **顆數少 25~42%、val 反而高**。全場景（14 塊＋合併＋held-out）已排。
- 官方的 **6GB 障礙在 coarse**（峰值配置 7.0 GB），逐塊微調每塊 7.3~13.9 GB => 一張 24GB 卡同時只跑得動 2 塊（一律 [solo]）。
- 官方模型依 opacity 剪 10% 逐位元不變、剪 25% 只 -0.03 => 約 610 萬顆幾乎白付。
- **v/c trim 在官方 vanilla 配方大輸**（b3 -2.62、b6 -3.77）：v/c 只在 MCMC 下有效。
- 與論文 27.23 的差距：release 的 trim 沒跑、ω／prune_ratio 與論文不同、資料為重生版 —— 論文設定的全場景出來後再談。

## §6 官方 test 集（踩過兩次）

- 我方自製的 `block_all_test/input` 是錯的：741 張只有 657 張是官方 test 影格，且對 sparse 相機分段錯開 => 官方 held-out 一度量到 15.62（已作廢、檔案改名 `input_WRONG_不要用`）。
- 正解：sparse 相機 N 的姿態＝transforms_test.json 第 N 幀（殘差 1.6e-6）＝官方 `transform_json2txt_mc_aerial.py` 的做法 =>
  `prep_test_official` 照官方 `data_proc_mc.sh` 從 tar 重建 `block_all_test_official2`，逐張 md5 驗。
- 第二次失敗：官方 json2txt 的 `--intrinsic_path` 預設讀 train 的 transforms（影格清單也從它讀）=> 已改傳 test 自己的 transforms。
- 741 就是完整的官方評測集（多出的 130 張沒有姿態也沒有相機）。
