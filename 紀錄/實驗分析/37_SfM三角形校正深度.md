## 現況與結論
- **★ 每張影像用「它自己觀測到的 SfM 點」做三角形校正單目深度，誤差中位 2.15% → 0.15%**（350 張對真深度）；判前方（真表面會被閘門當浮塊）15.7% → 2.2%；
  超高塔頂（z ≥ 3）18.35% → 0.45%、判前方 77% → 16%。**可靠三角形內（無因次斜率 < 3，佔 70% 像素）中位 0.05%、|e| > 2% 只有 3.1%、判前方 0.3%**（§1）。
- 🟨 出處：平面的逆深度在影像座標上是仿射的 => 三角形內線性內插 SfM 逆深度對平面精確（ACMP 的平面先驗，Xu & Tao AAAI 2020）；我方改成「校正單目」
  （內插的是 SfM 與單目的殘差，三角形內保留單目的起伏），並用三角形的斜率分級可靠度。沒有場景單位常數（斜率無因次、大小用 px）。
- 純 CPU：全場景 5,621 張 11.6 分（lab 6 行程）；輸出 1/2 解析度，深度 9.1 GB＋可靠度 2.3 GB（§2）。
- **救不了的**：畫面裡完全沒有 SfM 點的東西（重複窗格的高樓立面、玻璃塔）——三角形直接跨過去；那些像素落在斜率大或凸包外的級別，會被標成不可靠（示意圖 1120）。
- **b1 四臂（§3）**：單側不能看穿（比校正深度深 2% 就罰）F1 +.022、地下覆蓋 −13%、畫質與時間持平 => 候選；只換深度、補洞 2% 持平；閘門收緊 −0.05 dB 不採用。
  地下那幾層躲在中位深度已經對的貼地層後面，中位深度的 loss 碰不到。
- **稠密初始化（§4）不採用**：同排程與複製起點完全一樣，短排程（20k／40%、15k／40%）一樣掉 => 起點被訓練洗掉，沒有省到時間、也沒壓住地下層。

## §2 產生器與可靠度分級（`tools/make_tri_depths.py`）
```
inv(p) = 單目(p)·s + o ＋ 內插_三角形( 1/z_SfM − (單目·s + o) )(p)         凸包外：最近 SfM 點的殘差
可靠度（uint8）＝ 斜率級 + 8 x 大小級     斜率級 0／1／2／3／4 ＝ < 1／< 3／< 8／>= 8／凸包外     大小級 0／1／2／3 ＝ 最長邊 < 16／< 64／< 256／>= 256 px
```
- 輸出 `<dataset>/estimated_depths_tri/<名>.npy`（float32 逆深度、場景單位、960x540）、`estimated_depths_tri_rel/`、`estimated_depth_scales_tri.json`（全部 scale 1）。
- 5,621 張：13 張沒有可用的單目（改用純 SfM 三角形）、2 張連 SfM 觀測都不夠（全 0）；像素比例 斜率 < 1 34.9%、< 3 70.2%、< 8 82.2%、凸包外 10.2%；
  自我檢查（SfM 點所在像素的逆深度對 1/z）中位 0.022%。
- dataparser（`EstimatedDepthBlockColmap`）：`depth_rel_dir`＋`depth_rel_slope_max`（預設 1＝斜率 < 3）＋`depth_rel_size_max`（預設 3＝不限）；
  不可靠的像素設 0，深度支撐閘門、補洞放點、單側不能看穿本來就把 <= 0 當無效。沒給 `depth_rel_dir` 時行為與之前相同。
