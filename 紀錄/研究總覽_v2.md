## §7 方法論

### §7.1 量測

**先量再解釋。** 提出機制解釋之前先問「它預測什麼可量的量」。
2026-09 有一輪四個假說全部從一兩張圖跳到機制、**全被推翻**；而讀碼猜的三個減計算候選
**全沒進前 40 名**，真兇是沒想到的 trim pass（80%）。
⇒ **診斷能拒絕整個家族，介入一次只能測一個點。**

**判準要對準假設中的作用機制，不是方便量的東西。**
`oregstop` 的前提「收割期 opacity L1 是純損失」是用**死亡率**判的，
漏掉它真正在做的事：同樣 2.34M 顆，關掉後總 opacity 質量 +47%、o>=0.9 多 1.82 倍。

**隨機事件一律用重複試驗報比例，不准用單次。**
2026-09-13 我為 `max_split` 三次改口，全因單點量測：同一設定（N=2.6M、ballast 0.8G、
不開旗標）在六次試驗裡活過一次，我剛好抽到那次就宣稱「牆是隨機的」。
5 次重複後定案：不設 **OOM 5/5**、設了 **0/5**。

**比較前 diff 兩份 resolved config。**
`speed3_sfminit_b12` 以為唯一變數是 init，實際差**四項**，其中 `dynamic_strips=true` 讓
77.7% 的訓練步跑在被改過的 loss 上 => 一整趟 9 小時 GPU 作廢，而檢查是**秒級**的。
⇒ 已自動化：`tools/diff_resolved_config.py`，`run_fit` 收尾自動跑。
⚠ 讀的要是 **resolved config**（Lightning 寫下的實際生效值）—— CLI 旗標打錯字會被
  jsonargparse 吃掉而不報錯，只有它看得出來。

**比分數之前先驗跑次有沒有跑完。**
`results.txt` **不寫步數** => 半途 OOM 的跑次會留下看起來正常的分數。

**驗「有沒有異常值」要取 max 與計數，不能取樣。**
P7 的 `1/(surf_depth+1e-8)` 在無粒子像素回傳 **1e8**，取樣看不到。

**「A 對應到 B」的驗證，判準不能來自 A 或 B。**
2026-09-13 我用三個不足的測試撤回了一個**正確**的發現：
(a) sparse 對 transforms.json 是循環（同一組姿態）
(b) 對極幾何對「一致的幀偏移」不敏感
(c) 「模型重建得好」與過擬合相容 —— **這一點是使用者指出的**
⇒ 最後是**位元組級 md5** 定案。三個不足的測試不會相加成一個足夠的測試。

**先量便宜的再投昂貴的。** 6GB 單卡序列，一個實驗鎖 4~11 小時。
2026-09-13 的例子：背包的「有沒有空間」用**一次前向**就答完（`tools/rho_value_cost.py`），
而原本的計畫是跑 60k；`cost_budget` 的標定同理，省下約 15 小時 lab 時間。

**上界要標成上界。** `rho_value_cost` 的 +57% 是離線、且知道每顆真實 v 的選擇；
訓練期只能用代理訊號 => 實際一定更少。不標清楚就會變成 overclaim。

## §2 6GB 信封

### §2.1 VRAM 是硬牆不是慢坡

N 固定、只改可用餘裕：每步時間 **0.999~1.001x 平到撞牆**，`num_alloc_retries` 一路 0。
⇒ **慢不是配置器在搬**。純計算 ≈ 155 ms/百萬顆 + 21 ms，而全訓練的固定項是 179 ms
⇒ 那 158 ms 的差額在 dataloader／全解析度 loss／Lightning，**不在 render**。

### §2.2 配置器：`max_split_size_mb:128` 要開（定案）

```
N=2.6M、ballast 0.8G、每臂 5 次
  不設                OOM **5/5**
  max_split_size_mb:128  OOM **0/5**   retries 13~15，314~320 ms
```
代價在新資料上是 **14~17%**（263.0 -> 300.0 ms 無壓力），不是舊資料時記的 6.4%。
對 8.8h 的跑次 = 75~90 分鐘，換掉「83% 機率整趟死」—— 划算。

**⚠ 但懸崖很陡，而 `cap_max 2.6M` 正好卡在邊上：**
```
N=2.0M / 2.2M / 2.4M   不開也 0 OOM（0/5、0/3、0/3）
N=2.6M                 不開 5/5 死
```
```
cap 2.6M + max_split    ~317 ms   非有旗標不可
cap 2.4M 不開            252 ms   快 20%
cap 2.0M 不開            212 ms   快 33%，而且剩餘餘裕更大（0.763G vs 0.429G）
```
⇒ 「2.6M 值不值得多花 20%」是**品質問題**，要用 2 萬步對比骨架答，不是再量 VRAM。

**「保留 − 配置」不等於碎片。** 壓力上升時那個落差會自己縮小（0.878 -> 0.272G），
因為配置器被逼著釋放快取 ⇒ 低壓時的落差**大多是可回收的快取**。
真正的失敗是「連回收完都湊不出一塊連續的大記憶體」，而 `num_alloc_retries` 正是在數這件事
（retries 13~15 卻只慢 4.5% ⇒ 那個「釋放再重試」的機制很便宜，它就是 +0.6GB 的來源）。

⚠ `expandable_segments` 在 torch 2.0.1 不支援。

### §2.3 上限旗標的邊界

`CITYGS_VRAM_CAP_GB` 用 `torch.cuda.set_per_process_memory_fraction`，只管 **PyTorch 配置器**。
實測 lab 上兩個行程各佔 **6,084 / 6,068 MiB**，而上限是 5,796 MiB（5.66 GiB）⇒ 超出約 **280 MiB**
（光柵器自己 `cudaMalloc` 的部分 + CUDA context 不受管）。
⇒ **那個上限是下界**，「塞不塞得進 6GB」的最終宣稱要在真的 6.1 GiB 卡上量。

### §2.4 時間花在哪

不是搬運（4.2%）：backward 37% ／ forward 24% ／ **週期性 trim 21%（densify 期）** ／ optimizer 10.5%。
⚠ cProfile 說 `Tensor.to` 佔 71% 是**同步點假象**，實際算術只有 0.14 秒。
  計時要每個標記點同步；週期性事件要按**真實週期**攤平，不是按取樣視窗。

### §2.x 新年代逐段成本與 max_split 的真實代價（2026-09-17，本機 b6，`scripts/task_stepcost2.sh`）
```
時間（hi，N 1.54M）  backward 172.1 ms 41%／forward 95.8 23%／optimizer 45.5 11%／loss 15.9 4%／迴圈外 9.0 **2.2%**
                     週期 trim 每次 75.5 s（548 台相機）=> 按 500 步週期攤平約 151 ms/步 => 增生期約 31%
VRAM（段內峰值配置） backward 2,818 MiB 最高；常駐約 1,634 MiB；trim 結束 empty_cache，保留掉到約 1.66 GB
max_split 關 -> 開   真實每步 340.8 -> 367.9 ms（+8.0%）；配置峰值不變；段末保留 3,860 -> 5,526 MiB（+1.67 GB）
```
⇒ **搬運不是瓶頸**（2%）；lab 台帳保留 5.6~5.7 GB 與乾淨起點 3.22 GB 之間的缺口 = max_split 帶來的配置器快取，不是隱藏配置。

### ⛔ 自鎖假設已否證：「不加點 => 足跡縮不下來」方向就是錯的（2026-09-14）
假設（我 09-14 口頭提出、當時註明未驗證）：超預算就不加點，而 MCMC 加點會縮小來源粒子的 scale
=> 不加點讓足跡降不下來 => 永遠超預算（用來解釋 b12 的退化）。
驗證：gsplat `cuda/csrc/compute_relocation.cu`（`add_new_gs` 第 154~162 行呼叫它，並把結果**寫回來源粒子**）——
`新 opacity = 1 - (1 - o)^(1/N)`；**scale x coeff**，`coeff = o / sum_{i=1..N} sum_{k=0..i-1} C(i-1,k) (-1)^k o'^(k+1) / sqrt(k+1)`
（三軸同一個係數；以純 Python 依同式代入）
```
opacity   N   新 opacity   scale 係數   N 顆 x 單顆面積
 0.05     2    0.0253       0.996        1.99
 0.20     2    0.1056       0.984        1.94
 0.50     2    0.2929       0.952        1.81
 0.90     2    0.6838       0.868        1.51
 0.99     2    0.9000       0.807        1.30
 0.99     3    0.7846       0.746        1.67
```
⇒ 加點時每顆只縮 0~25%，但數量變 N 倍 ⇒ **總足跡（Load）一律變大（>= 1.3 倍）**。
  不加點**不會**阻止 Load 下降；加點才會推高 Load ⇒ 自鎖不成立。
⇒ b12 的 Load 一直高於預算，**不是因為少了分裂**，而是早期粒子本來就大、加上梯度推動的 scale 成長 ——
  與「約束端只擋 add、擋不到 scale 成長」是同一件事。
⇒ **對預算設計的含意：要把 Load 壓下來，槓桿在 scale，不在加點數。** 只擋加點的預算，本質上只能防止 Load 再往上加。
⚠ 未計入：opacity 變低時光柵器的截斷半徑也會變小（`truncated_R` 隨 opacity、上限 3）。

### §4.1 為什麼隨機會失敗：**是範圍，不是點數**

`colmap_dataparser.py:532` 把隨機點撒在**半寬 3R 的立方體**（R = 相機到質心的最大距離），
而實際內容是貼地薄層：
```
random 立方體每軸跨度 64.90
SfM 主體（2.5~97.5 百分位）  x 14.58 (22%)   y 11.91 (18%)   z **2.00 (3.1%)**
=> 主體只佔立方體 **0.127%**
   撒 100,000 點只有約 **127** 個落在內容區；撒 1,000,000 也只有 1,272（SfM 有 3.83M）
   => 靠均勻亂撒追上要撒到**十億級**
```

### §4.2 起始 trim 對 init 類型的敏感度差 3,700 倍

```
SfM init    579,004 -> 579,003   被砍 **1 個（0.0002%）**
隨機 init   100,000 ->  25,599   被砍 **74%**
```
⇒ 舊記錄「存活數固定約 36.2 萬，與投入顆數無關」**只在同類型的 init 之間成立**
  （那是在兩種 depth-init PLY 之間量的，它們都大致貼著表面）。
  正確的說法是「存活數取決於**有多少點落在光柵器看得到支撐的地方**」。
