# DGD 反推 + DBP 探索 + 實驗審核（2026-06-27）

> 這次 session 的核心：搞懂 CityGSV2 為何同點數品質高、反推我們為何低分、嘗試合併新算法、審核實作有無 bug。
> 結論偏「診斷」而非「成功」，但釐清了很多搭配/機制問題。

## 一、baseline 重大修正（我犯的錯）

- 我先前報告「我們 24.30 贏 CityGSV2 21.78（+2.5）」**是錯的**——我選了會把 densify 壓死的 config（opacity_reset 6000/densify_until 30000）跑 CityGSV2，得 21.78/875k。
- **舊本機真實 CityGSV2 b7 = 28.9 / 4M**（`outputs/citygsv2_mc_aerial_sh0_trim`，24k regime：interval 300/reset 2100/until 12000，**full coarse init**）。其他塊 block_0=29.7、block_24=31.2。
- 視覺確認（`~/Pictures/citygs_compare/`）：21.78 那個 render 稀疏玻璃感（76% 覆蓋），跟低分一致。

## 二、DGD = CityGSV2 高分引擎（解碼 codebase）

- 論文 Tab 7：densify 梯度來源「最關鍵」。
- 實作：`gaussian_splatting.py:426-433` + `citygsv2_metrics.py:120-122`：`loss=λ(1−SSIM)+dist+normal+depth_reg`、`extra_loss=(1−λ)L1`；densify 梯度被重設回 `org_grad`（只來自 loss=SSIM 那次 backward）→ **densify 用 SSIM 梯度，在結構誤差處加點**。`densify_grad_scaler`(ω) 只調 magnitude。
- **我們 MCMC pipeline 用 opacity 放點 → 繞過 DGD**。scaling law 反推截距：我們 a≈12.1 vs CityGSV2 a≈16.7（差 ~4.5dB）。

## 三、實驗釐清「grad-densify 在 6GB 能不能長」（關鍵負結果）

| run | 設定 | 結果 | 結論 |
|---|---|---|---|
| E1 | grad-densify 24k + **裁切 coarse** 258k + scaler 0 | 崩到 **42k / 19.60** | 裁切 coarse 的點 opacity 崩潰 → 死 |
| E1b | 同上 + **scaler 0.9** | 也崩（258k→100k 還在縮）| **是 init 的鍋,不是 scaler** |
| E2-B | grad-densify 24k + **depth-init** 431k + scaler 0.9 | 卡在 **~280k 不增反減** | depth-init 點擬合好(alpha0.99)→梯度低→grad-densify 不觸發 |

**→ grad-densify 在 6GB 用我們可行的 init 都長不起來**：裁切 coarse 會死、depth-init 梯度太低不densify。**舊本機 4M 靠 full coarse(4.39M,高梯度)——但 full coarse 在 6GB step-1 OOM。**
**→ MCMC 不看梯度(add_new ×1.05 強制長)→ 從同 depth-init 長到 1.5M/24.30。這就是為何 MCMC 是 6GB 唯一能長的。**

## 四、合併新算法 DBP 的死結

- **想法**：DGD(去哪加)+ MCMC(預算/長)+ importance-prune(回收)+ cap。實作了 `dbp_density_controller.py`（grad-densify 為底 + cap）。
- **死結 1**：grad-densify 為底 → E2-B 證明它在 6GB 長不起來 → DBP-grad-densify 也會卡 ~280k。
- **死結 2**：改 MCMC 為底 + SSIM 梯度導引 → **查證發現 = gg-MCMC**（gg-MCMC config 用 MCMCCityGSV2Metrics→有 extra_loss→DGD 區塊動→gg-MCMC 累積的 viewspace.grad 就是 SSIM 梯度）→ **net-zero（已測過）**。
- **→ SSIM 訊號在 grad-densify 的 clone/split 有效,在 MCMC 的 sample/relocate 無效(gg-MCMC 證明)。差別在「機制」不在「訊號」。**

## 五、實作審核（核心程式無 bug，低分是搭配/訊號錯）

- MCMC noise/relocation：✅ 無 bug（Σ shape 對、與原版 3dgs-mcmc 一致、2D 切平面正確）。
- gg-MCMC buffer：✅ 維護正確（self-heal 只真 desync、densify 時 grads 有效、_prune_points 對齊）。用的是 SSIM viewspace 梯度（如上）。
- importance-prune：⚠️ top-K 是 running-maxima 非真 top-K（順序偏差），但與 renderer trim 同邏輯 → +0.46 成立、metric 不精確。
- EdgeAware：⚠️ override `_add_densification_stats` 把 SSIM 梯度乘 edge → 污染 DGD。

## 六、真正的方向（修正後）

1. **MCMC 缺的不是「SSIM 訊號」(gg-MCMC 試過)，是「SPLIT 機制」**：grad-densify 的 split 把大模糊高斯拆成小銳利的(細節精修)；MCMC 只 relocate/add，沒 split。**DBP v2 = MCMC + 對高-SSIM-梯度大高斯做 split**（唯一沒測過的機制）。但工程量大、design 不確定。
2. **★ 更強的槓桿 = CPU offloading**（文獻 CLM/GS-Scale）：MCMC 在 6GB 能長,只是被 VRAM 卡在 1.7M(sh3)/~4M(sh2)。offloading 讓 MCMC 衝到 4M+ → 品質隨點數上去。這是 field 對「消費級+大規模」的公認解,且在我們 stack 內。
3. **待跑**：E2-B 跑完(grad-densify+depth 6GB 數據點)、full-coarse b7（驗 28.9 需 >6GB，預期 OOM）。

## 七、數學工具

- scaling law：PSNR ≈ a + 0.8·ln(N)（我們 532k→969k 斜率 0.808 ≈ Grendel 0.78）。我們 a≈12.1 → 4M 預測 ~24.4；CityGSV2 a≈16.7。
- VRAM：2DGS sh2=444 B/顆、sh3=696 B（含 adam）；sh3 6GB 天花板 ~1.7M、sh2 ~4M(grad-densify)。
