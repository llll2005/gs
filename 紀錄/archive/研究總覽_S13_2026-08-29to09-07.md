### 11.82 ⚠ `ac_densify` 輸了，但它**根本沒搬動族群** —— 是「介入太弱」不是「機制否證」（2026-09-04）

`acd_b12` = 現行最佳 + `ac_densify 1.0`：PSNR **-7.0sd** / SSIM -24.5sd / LPIPS -8.5sd / 紋理比 +2.3sd。

**但關鍵在這個對照**（`tools/blur_gaussian_stats.py`，同一批 tile）：
```
              高斯/像素   投影半徑   opacity
agd2            0.62       1.18      1.27
acd             0.64       1.18      1.25   <- **幾乎完全一樣**
```
⇒ **AC 訊號根本沒有把粒子搬進失敗區**（密度比 0.62 -> 0.64，僅 +3%）。
⇒ **這個實驗沒有檢驗到假說**，它檢驗的是「一個太弱的介入」。
原因可算：AC 天花板只有 **2.83x**，`w=1` 時最大加權 3.83x，而每次事件搬動的粒子本就少。
⚠ **「介入太弱」與「機制否證」的結論完全不同** —— 不可把本次記成後者。

**⇒ 我的實作漏了 Gemini 原提案的另一半**：
```
① 偵測高 AC 殘差的 tile           ✓ 做了
② **強制把那裡的高斯 scale 縮小**  ✗ 沒做 —— 只做了「往那裡增生」
```
而數學上**抵消的程度取決於 footprint 相對於殘差空間頻率的大小**
⇒ 「往盲區放更多同樣大的粒子」不會脫離盲區，**要讓它們變小**。
⇒ 已實作 `ac_shrink`（每次 densify 事件把 AC 最高的 5% 粒子 scale x0.5），
   **繞過取樣瓶頸、直接作用在成因上**；與 `err_unlock` 同構（那個壓 opacity、這個壓 scale）。
⚠ 守衛已含 `ac_shrink` 自己（否則就是第七個靜默 no-op）。

**✅ 開跑後的兩項驗證（不等 10 小時）**
1. **旗標確實在作用**：`[ac-shrink] step 3000: 16591 顆 scale x0.50（AC 前 5%）`
   —— 與 `ac_densify` 形成對比，那個是量到「沒搬動族群」才知道太弱。
2. **⚠ 發現一個設計風險並已檢查**：print 每 3000 步一次，但 **shrink 在每個 densify

### 11.84 ⛔ `ac_shrink` 尺度塌陷：**在 3 次事件上驗證、外推到 193 次 —— 又錯了**（2026-09-04）

`acs_b12` 開跑後我加了安全檢查（判準事前寫死：`<1e-4 比例 > 1%` 或 `p0.1` 低兩個數量級）。
**step 14999（約 93 次 shrink 事件）實測**：
```
                    N          scale中位     p1          p0.1        <1e-4
agd2@14999      1,311,450    1.586e-02   4.764e-04   5.512e-08    0.78%
acs@14999       1,311,704    1.055e-02   **1.200e-20** 5.858e-26  **15.19%**
```
**`p1` 差 16 個數量級，15.19% 的粒子 scale < 1e-4，而 N 幾乎不變**
⇒ **那 15% 佔著 cap 卻渲染不出任何東西** ⇒ 這個跑次量到的是
「刪掉 15% 粒子的效果」，不是「縮小 footprint 的效果」。⇒ 已中止（step 17,039）。

**★★ 這是我今天第三次犯同一個錯：在少量樣本上驗證，然後線性外推。**
```
MCMC noise    用別的工作點的係數推 => 說省 10%，實際 **4.2%**
sh2 + cap     用兩個不同工作點的係數推 => 說小輸 0.09 dB，實際 **0.454 dB**
ac_shrink     用 **3 次事件**驗「成員每次都在換」=> 外推到 193 次，實際 **塌了 16 個數量級**
```
三次**都是往低估風險的方向錯**。
⇒ **規則：任何「在 k 次/一個工作點上驗過」的結論，外推到 N 次/另一個工作點時必須標註，
   並在中途重驗。** `ac_shrink` 這次靠中途重驗只賠 5 小時；前兩次沒有中途檢查，
   直接賠掉整個跑次加一個錯誤預測。

**⚠ 成員確實在換 —— 但換得不夠快。** step 1499（3 次）時尾端只掉到 0.51x
（同一批被打應為 0.125x），看起來安全；累積 93 次後仍有 15% 被打到零。
**「每次換一部分」不等於「不會累積」。**

**修正**：`ac_shrink` 加下限 = 族群 scale 中位數 / 50
（仍遠小於典型 footprint，足以脫離梯度盲區，但不會歸零）。已排 `acs2_b12`。

**✅ 值得肯定的部分**：這個安全檢查是**開跑後主動加的**，判準也是**事前寫死**的，
所以一驗就抓到。若沒有它，10 小時後會得到一個「N 正常、分數平、看不出成因」的結果
—— 而那正是最難查的失效模式（見稽核清單 §7 的共同形狀）。


### 11.85 ⛔⛔ `ac_shrink` 修正版**仍然塌陷** —— 因為我把安全限綁在**機制自己會破壞的量**上（2026-09-04）

§11.84 的修正是「下限 = 族群 scale 中位數 / 50」。`acs2_b12` 用**同一個事前判準**重驗：
```
                    N          scale中位     p1          p0.1        <1e-4
agd2@14999      1,311,450    1.586e-02   4.764e-04   5.512e-08    0.78%
acs2@14999      1,312,136    1.070e-02   5.112e-09   3.002e-09   **13.96%**
```
**13.96% vs 修正前的 15.19% —— 幾乎沒改善。** 而 `[ac-shrink]` 印出的下限說明了原因：
```
step  3000: 6,753 顆   下限 3.64e-04
step  6000: 3,966 顆   下限 3.75e-04
step  9000: 6,428 顆   下限 3.06e-04
step 12000: 27,385 顆  下限 2.61e-04
step 15000: 24,244 顆  下限 2.14e-04
step 18000: 41,660 顆  下限 1.78e-04     <- 下限一路滑，命中數一路漲
```
**下限 = median/50，而縮小本身會壓低 median ⇒ 下限跟著降 ⇒ 允許更多縮小 ⇒ median 再降。**

**★★★ 可複用的教訓（比這個機制本身值錢）：
**⇒ 絕不可把安全限／閾值綁在「這個機制自己會改變的統計量」上。** 那不是保護，是正回饋。
判斷法：問「若機制完全失控，這個限會跟著跑掉嗎？」會 ⇒ 它不是限。
本專案已有同形狀的前例：`opacity` 自我強化（§ 幾何 5x5 條目）、起始 trim 的
「錯的在前 ⇒ 對的在後被刪 ⇒ 錯的鎖死」（`start_trim_shell`）。**這是第三次。**

**修正（已實作，`ac_shrink_target_px`）**：改成**冪等的絕對目標**，不做乘法累積：
```
scale = target_px * z / (3 * fx)       # 3-sigma 投影半徑的反解，且只縮不放
```
套 1 次與套 193 次**結果相同**（已用 log 空間驗證），不需要下限，因為沒有累積。
```
舊：同一顆被命中 20 次 -> x 9.5e-07（實測 15.19% / 13.96% 掉到 <1e-4）
新：命中 1 次或 193 次 -> 同一個值
```

**⚠ 但沒有立刻重跑 —— 因為 target_px 該設多少、以及縮小打不打得到成因，都還沒量。**
§11.76 實測失敗/成功區投影半徑只差 **1.18x**（20.73 vs 17.51 px），
與**當初正確預測 `egd` 失敗**的 1.22x（DC 誤差天花板）**同一個形狀**
⇒ 縮到 2px 是「對一個實測只差 18% 的變數做 10 倍介入」＝**破壞集合**（實測 −2.34 dB）。
唯一的活口是 §11.82 第 5 條「雙峰而非連續退化」＝**可能有懸崖**。
⇒ 先跑 `tools/radius_cliff.py`（~6 分鐘）而不是第三次 9.6 小時：
```
最大跌幅/全距 >> 1/箱數        => 有閾值，用它當 target_px 重跑
corr(log 半徑, log |g|/AC) ~ 0 => 抵消不由 footprint 驅動 => **整個「縮 footprint」家族收線**
```
**這是「診斷能拒絕整個家族，介入一次只能測一個點」的直接應用**
（2026-08-27 使用者指示，見 `scripts/queue.txt` 的分隔線區塊與記憶 `先量再解釋`）。


### 11.86 ★★★★★ 那 2.4 GB 缺口 = **配置器碎片**，而台帳記的是 reserved —— `cap_max` 可能一直被碎片壓著（2026-09-04）

使用者要求「嚴察」的缺口，`tools/vram_gap.py`（N=2.34M，單 process 乾淨起點）開獎：
```
                        階段         峰值增量 GB
A 常駐（僅參數，Adam 尚未建立）        0.522
B forward                            1.222
C forward+backward                   1.901   <- **最大**
D optimizer.step()                   1.012
E trim pass（284 台）                 1.239

allocated 合計 ≈ 2.42 GB      reserved = 4.87 GB      => **缺口 2.45 GB**
```

**★ 兩個原假設都被推翻**
```
① 「trim pass 決定峰值」    ⛔ 1.239 < forward+backward 1.901，且與單張 forward 相當
                              —— 它 `no_grad` 且逐台釋放，本來就不會疊加
② 「缺口是某個沒算到的張量」⛔ 缺口 2.45 GB ≈ reserved - allocated，**是配置器碎片**
```

**★★ 真正值錢的發現：`internal/callbacks.py:_vram` 記進台帳的是 `torch.cuda.memory_reserved()`。**
```
台帳長年寫 VRAM=5.57/6.1G  ->  那是 reserved，含約 40% 的配置器快取/碎片
=> **`cap_max` 一直是照著一個不代表真實佔用的數字調的。**
```
⇒ 已修：`_vram()` 同時回傳 allocated，台帳與面板都加上 `(實佔 x.xx)` 欄位
  （`train_console.py` 有無此欄位皆可運作，舊路徑相容已煙霧測試）。

**⚠ 但「碎片」不等於「可用」**：PyTorch 配置失敗時會先釋放快取區塊再重試，
真正的上限是 `allocated + 無法釋放的碎片`，**只能實測**。
⚠ 且 **torch 2.0.1 沒有 `expandable_segments`**（2.1 才加）⇒ 不能靠旗標繞過。

#### ⛔ 40 分鐘後，上面那段被我自己的量測推翻 —— **「2.45 GB 碎片」是我的工具的假影**

`tools/vram_scale.py`（複製粒子到目標 N，跑 6 個**完整**訓練步 + 1 次 trim pass）：
```
   目標 N    peak alloc   peak resv     碎片     佔卡
  2.34M        3.736       4.670      0.933    82.5%   ✅ 通過
  2.80M          -         5.312        -      93.8%   ⛔ OOM
（顯卡實際可用總量 5.66 GB，不是 6.1）
```
**⇒ 真實碎片只有 0.933 GB，不是 2.45 GB；而 2.80M 直接 OOM ⇒ 容量是真的滿了。**

**假影成因（我的錯，記下來避免再犯）**：`vram_gap.py` 的 `A 常駐` 是在
**Adam 狀態建立之前**量的（0.522 GB＝只有參數），但拿它去和「常駐＋最大階段峰值」相加，
於是把 `梯度 0.506 + Adam 動量 1.011 ≈ 1.5 GB` **整個漏掉**，
差額就被錯誤地全部歸給「碎片」。
⇒ **量分項再相加時，必須驗「分項和 ≈ 獨立量到的總和」**，否則漏掉的項會偽裝成殘差項。
這與 §11.84/§11.85 的「在少量樣本上驗證再外推」是同一類錯：**沒有做閉合檢查。**

**✅ 仍然成立、且值得保留的三件事**
```
1 trim pass 不決定峰值（1.239 < forward+backward 1.901）—— 原假設推翻，這條診斷有效
2 台帳記的是 reserved（`callbacks.py:_vram`）—— 已修，現在同時記 allocated `(實佔 x.xx)`
3 `cap_max` 2.6M 是**對的**：2.34M 已佔卡 82.5%，2.8M OOM ⇒ 現行設定沒有被浪費掉的餘裕
```
**⇒ 「靠回收碎片換 cap」這條線收掉。** 顆數槓桿（+0.541 dB/加倍）在 6GB 上已經到頂，
   要再往上只能靠**每顆更省**（sh0/SB 已測皆負）或**每顆更值錢**（＝現在走的訊號線）。


### 11.111 ⛔⛔⛔⛔ **成本感知增生取樣：三個變體全輸，這條線定案**（2026-09-07）

`cadd_b12` = 現行最佳 + `cost_add_densify 2.278`：**加法式**（不是冪次）＋**精確 c_i**
（trim 的 `num_covered_pixels`，不是 `radii²` 代理）＋**夾住尾巴**
（權重範圍實測 1.001~20.2x，與 absgrad 的 25.8x 同級）。三個病灶全部對症下藥。
```
              PSNR      SSIM     LPIPS    紋理比    floater
agd2       26.5602   0.7755   0.3467   0.4902    1.660%   <- 基準（**無成本項**）
fpd        26.4260   0.7753   0.3502   0.5109    1.713%   <- 冪次 w=-0.5（Taming 向）
cadd       26.3719   0.7725   0.3542   0.5069    1.596%   <- **加法+精確+夾住**
cheap      26.2398   0.7696   0.3585   0.4968    1.270%   <- 冪次 w=+0.5（我方向）

cadd vs agd2:  PSNR **-6.8sd** ／ SSIM **-30.1sd** ／ LPIPS **-8.7sd** ／ 紋理比 +3.2sd
```
**⇒ 基準贏過全部三個變體。**


### 11.78 ★★ 外部第二輪：Gemini 的「空間梯度積分抵消」是目前最好的機制候選（2026-09-03）

```
∂L/∂μ_i = Σ_p (C(p) − I_GT(p)) · T_i(p) · ∂α_i(p)/∂μ_i · c_i
```
DC 擬合完之後殘差是**零均值的高頻振盪**，而 `∂α_i/∂μ_i` 在 footprint 上是**平滑奇函數**
⇒ 兩者在 footprint 上求和**正負抵消 ≈ 0** ⇒ **殘差很大而位置梯度為零**。
而 MCMC/ADC 的分裂條件是 `|g_μ| > τ` ⇒ **永遠不觸發** ⇒ 該區永久卡在低頻態。

**★ 它一次解釋了三個我方量到但沒解釋的現象**：
1. 失敗區投影半徑大 **18%** —— 「稍微偏大就掉進盲區」正好對應那個幅度
2. **密度控制十次介入全無效** —— **驅動它的訊號在那裡本來就是死的**
3. **`absgrad` 幫了一次就飽和** —— `|g|` 正是被抵消掉的那個量，
   所以它會把粒子**送離**失敗區（§11.55：糊掉% 在 w=1 後完全不動）

**⇒ 可立刻檢驗的預測**：**失敗區的 `|g|` 應偏低，儘管殘差很大。**
我方已有基礎設施（`|dL_ds|` 累加在未使用的 `dL_dmean2D.z`）⇒ 一次 backward 即可。
⚠ 若量到 `|g|` **並不低**，這個機制就否證，要回頭看 GPT 的
「梯度夠大但方向不對」（`A_g = |<J_g,e>|/(||J_g||·||e||)` 餘弦）那一支。

**GPT 第二輪的實質貢獻（採納）**：
- **O0/O1/O2 三階段**：先「凍結拓撲只重優化」→ 再「增加容量」→ 才「給理想基底」。
  **先測現有 basis 能不能被救活，再測增加 basis** —— 順序反了因果鏈就不乾淨。
- **influence set 必須按光線貢獻取，不能按 primitive 中心落在哪個 tile**（兩邊都指出）。
- **對照組必須同流程跑成功 tile**（否則 `ΔQ` 無意義）。
- **措辭限制**：只能說「在此局部預算下無法恢復」，不能說「無法表示」。
- 該量的是 **transmittance `T_i` 的深度序分布**，不是 opacity 平均（我方量的是後者）。

Moment-Based 3DGS(2512.11800) **本地都沒有 PDF**，且本專案有過幻覺文獻前例
（EDGS / Photometric-SLAM-2026 / MDPI-2026）⇒ **引用前必須實際取得原文**。

⚠ 只陳述量到的：兩個正則項都**提高損耗**，法線的幅度是深度的 3.3 倍。
   不進一步推斷「為什麼會衝突」——那需要另一個能預測可量量的假說。

**尾巴判準（事前指定的那把尺）也輸** —— `tools/veil_detect.py`：

```
agd2_b12     19.63   46.08     0.624

agd2dl05_b12 19.08   **48.52**  **0.547**   糊掉 +2.44pp
```

### 11.64 ⛔ 速度線的真正阻塞：**wall time 的跨跑次噪音約 5%**（2026-09-01）

使用者要求「做些優化讓訓練快一些」。盤點後發現阻塞的不是「沒有候選」，而是**量不出來**。

**證據（台帳，全部 b12 / 60k / N=2.34M）**：
```
sched30_b12   32,649s -> 544 ms/step
agd_b12       34,305s -> 572 ms/step   absgrad 1.0
agd2_b12      36,098s -> 602 ms/step   absgrad 2.0
tsub4_b12     32,970s -> 550 ms/step   trim stride 4
agd2du36      38,105s -> 635 ms/step
```
`absgrad` 的**強度 `w` 完全不改變計算量**（只是 `probs` 裡的一個乘數），
但 `agd` -> `agd2` 差 **+5.2%** ⇒ **那 5% 是噪音**（筆電熱節流／背景負載）。
⇒ **跨跑次比 wall time 無法量出 <10% 的改善。**
⚠ 連帶：先前「零權重閘門 -9%／`skip_surf_normal` -1%／`fused_ssim` -4.9%」
   都是這樣量的 ⇒ **那些數字的可信度低於當初宣稱**（-1% 尤其等於沒量到）。

**加上另外兩個已知的量測坑**（§11.56）：cProfile 的 CUDA 非同步歸因、
40 步視窗被一次性起始 trim 佔 80% ⇒ **三種量法全部失效過**。

**且任何改動都要 9.6h 驗分數**（`tsub4` 剛示範：省 8.7% 但 PSNR -6.7sd）
⇒ 「小幅省時 + 無法量測 + 驗證昂貴」三者相乘 = 速度線目前不划算。

**⇒ 先補工具，不再猜**：`tools/step_breakdown.py`（`scripts/task_stepbreak.sh`，~2 分鐘）
在**同一個 process** 內用 **CUDA event** 對載入的 ckpt 逐段微基準
（光柵化 / L1 / SSIM / forward+backward / MCMC noise 的 cov3d+bmm），
每段重複取中位數、不含任何一次性事件 ⇒ 三個坑都繞開。
**先知道 602 ms/step 花在哪，再決定動不動。**

⚠ 已知的最大候選是「前 30k 用 1/2 解析度」（表列 15~23%，夠大能穿過噪音），
  但它**改變訓練動力學** ⇒ 與 `tsub4` 同類風險，必須端到端驗分數，不可當免費午餐。


### 11.63 使用者提案：收割期只回收「透明度趨近 0」的粒子（2026-09-01）

> 「既然會導致兩極化，透明度趨近於 0 的部分似乎會看不到，而沒那麼小的則會變成亮度細節。
>   那如果後期依然保留 MCMC 的搬運機制，但只作用在透明度極度趨近 0 的部分？」

**分析（全部用現成資料，零 GPU）**

**① 「只作用在極度趨近 0」實際上沒有限縮到什麼。**
現行門檻 `min_opacity 0.005` 與「連 binning 都進不去」的 `1/255 = 0.00392`
在收斂時選到**同一批**：15.03% vs 14.96%（比 0.995，§11.61）⇒ 再收緊門檻無意義，
用 `min_opacity` 即可。**提案的前半（來源端零成本）成立**：那批確實零貢獻。

**② 成本在目的地端，不在來源端。**
`relocate_gs` 會 **reset 宿主的 Adam 動量**（`replace_tensors_to_optimizers(inds=reinit_idx)`，
照 MCMC 論文 §3.4：target 重置、source 保留）。而**收割期的宿主正是在收斂最終外觀的粒子**
⇒ 這就是「churn 淨負」的具體機制。

**③ ⚠ 這與已知淨負的 churn 是同一個操作。** `notrim2` 撞 cap 後做了 27,700 步純 churn
（只 relocate、無淨成長），實測淨負（§11.26）。**提案 = 把同一個操作搬到收割期。**

**④ 但有兩個量化差異，足以讓符號可能翻轉：**
```
目的地   notrim2 時 `probs = opacity`（盲目）
         現在 `probs = o*(1+2|g|/mean|g|)` => 送到「梯度說缺細節的地方」
         而那是唯一跨塊驗證過有效的機制（§11.53，w=2 為峰值）
強度     死亡累積 0.375pp/1000 步 x densification_interval 150
         => 每次事件僅搬約 1,350 顆 = 族群的 **0.056%**
         notrim2 的 churn 密集得多（撞 cap 後每 150 步都在搬全部死粒子）
```

**⇒ 實作 `harvest_relocate`（預設 False），並掛成 §11.62 那個 40 分鐘小實驗的第三臂**
（`scripts/task_oregprobe.sh`：A 對照／B 只移除 L1／C 收割期回收），
三臂同起點（`agd2_b12@29999`）、同 2,500 步、判準同樣看**速率**。
⚠ C 臂特別要看**確信 `o>0.5` 的成長率有沒有被拖慢** —— 若宿主的 Adam 重置真的傷到收斂，
   它會先反映在這裡，而不是在 2,500 步的 PSNR 上。


### 11.62 ⛔ 自我推翻：收割期不是「L1 壓死大家」，是**兩極化**（2026-09-01）

使用者問「這兩輪講的東西不能先用小實驗驗嗎」。**對，而且一個兩分鐘的 CPU 量測就削弱了
我自己前一節的假說**——我當時已經把一個 9.6h 的跑次排進佇列。

`tools/opacity_drift.py`（讀現成 ckpt，零 GPU）：
```
step        N        o中位   判死<0.005   中間帶   0.05~0.5   確信>0.5
29,999  2,600,000  0.1083     3.77%     22.26%    64.85%     9.12%
41,999  2,340,000  0.1371     9.81%     13.79%    56.92%    19.48%
60,000  2,340,000  0.1539    15.03%      8.99%    52.76%    23.22%
```
**收割期在做的是兩極化，不是普遍衰減**：
- `o` 中位數 **0.1083 -> 0.1539（升）** —— 若 L1 是主導力，中位數應該**降**
- **確信端 `o>0.5` 從 9.12% 翻到 23.22%**（+0.86%/1000 步）

那個往確信的遷移很可能正是收割期 +1 dB 的來源 ⇒ **該實驗大概率會輸，
而且輸的理由會被誤讀成「回收缺口不重要」。已從佇列撤除。**

**改成外科版**：新增 `opacity_reg_until_iter`（`mcmc_citygsv2_metrics.py`）——
只移除**固定的 L1 下壓力**，光度梯度對 opacity 的學習照常 ⇒ 兩極化應保留。

**且先做 40 分鐘的兩臂小實驗，不直接投 9.6h**（`scripts/task_oregprobe.sh`）：
兩臂都從 `agd2_b12` 的 step=29999 ckpt 續跑 2,500 步，**判準看速率不看終點分數**
（2,500 步不足以移動 PSNR）：

```
介入臂要同時滿足：判死/k **明顯變緩**（L1 是損耗主因）
                  確信/k **維持不變**（兩極化沒被破壞）<- 關鍵，缺這條整條線收掉
```

⚠ **方法論**：這是本 session 第二次「排了大跑次才發現前提沒驗」（第一次是 08-27 的
14h 佇列）。兩次都是使用者提醒的。**排任何 >1h 的任務前，先問「這條推理鏈上哪一環
可以用現成 ckpt 或 <1h 實驗檢查」** —— 本例的答案是「全部都可以」。


### 11.61 ★ 機制重疊盤點：四個機制一個對象，而真正的損失是**回收缺口**（2026-09-01）

使用者提問「同時採用的機制有些作用在相同對象上，能不能合併？會不會互相兼容而失去意義？」

**作用在「低不透明度粒子」這同一批對象上的五個機制：**
```
生產者    opacity_reg 0.002          每步把 opacity 往下壓        全程 60k 步
選擇器A   min_opacity 0.005          MCMC 判死 -> relocate        ⚠ **只到 densify_until**
選擇器B   EXACT_SUPPORT 1/255        不進 binning -> 零貢獻       全程（光柵器）
選擇器C   trim contribution<=q(0.1)  零貢獻必落在底部 10%         全程（每 500 步）
清潔工    harvest_dust_*             收割期剪塵埃                 ⚠ 預設 -1，配方沒開
```
**A ⊃ B 是定義上的**（`0.005 > 1/255 = 0.00392`），而實測顯示兩者**幾乎重合**：

```
step        N          o<0.005(A)   o<=1/255(B)   B/A
14,999  1,311,450        7.38%         6.08%      0.82
29,999  2,600,000        3.77%         3.34%      0.89
60,000  2,340,000     **15.03%**    **14.96%**   **0.995**
```
⇒ 收斂時 **兩個門檻選到同一個集合**。C 也吃同一批（零貢獻必在底部分位，§11.20/21 已記）。

**★ 但真正的損失不是重複，是缺口。**
`mcmc_2dgs_density_controller.py:487` 的 `if global_step >= densify_until_iter: ... return`
讓**整條回收路徑在 30k 之後停擺**，而 `opacity_reg` 繼續壓 30,000 步：
**判死比例 3.77% -> 15.03%**。
⇒ 最終 2.34M 顆裡有 **351,500 顆不可見**（不進 binning、零貢獻、純佔儲存）。

⚠ **自我修正**：初稿寫「這些是按 `cap_max` 計價買來的」，**這句話不準確**。
cap 綁定的時刻是 **30k**，而那時判死只有 **3.77%** —— 它們當時是活的，是**收割期才死的**。
正確的表述是：`cap 2.6M -> 30k 交付 2.6M(全滿) -> 收割期 trim 移除 260k -> 2.34M，
其中 15.03% 在收割期死去但**沒有被移除**` ⇒ 終點實際工作約 **1.99M**。
**兩項損失都發生在收割期，且都源自同一個缺口。**

**⇒ 對成本預算命題的額外證據**：那 15% **同時是零成本（不進 binning）與零價值（零貢獻）**
⇒ 顆數這個貨幣連「這顆有沒有在渲染」都分不出來，比 §11.60 的「貴/便宜分不出」更基本。
**⇒ 同時驗證了 §11.60 controller 的設計決定**：`cost_budget` 之外必須保留 `cap_max` 安全閥——
不可見粒子成本為零，純成本預算攔不住它們，N 會被塵埃灌爆。

**可做的（附警告）**
1. 開 `harvest_dust_trim_interval`（現成、預設關）。⚠ **預期不會加分**（densify 已停、無物回填），
   它的價值是**驗證那 15% 真的無用**：剪掉不掉分 ⇒ 確認；掉分 ⇒ EXACT_SUPPORT 的
   「零貢獻」假設要重審。部署端的 `cull_dust` 已驗過 7.4x 無損，屬同一假設。
2. 把回收延到 30k 之後。⚠ **必須與 `vpc_prune_frac`（-2.34 dB）區分**：
   vpc 搬的是「低 v/c 但**活著**」的粒子（破壞集合）；這裡搬的是**已死透、零貢獻**的（改變集合）。
   ⚠ 但 MCMC 的 relocate 依 Eq.9 **會改動宿主** ⇒ 在收斂期擾動活粒子，風險真實，
   且收割期正是 +1 dB 的來源（§harvest jump）⇒ 不可貿然開。


（5.63 vs 5.53，且 ledger 的 VRAM 是 reserved 峰值，對容量沒鑑別力），時間 −0.4%。

**⚠ 先排除死碼**：`cost_aware_densify` 讀 `_max_radii2D`，而該緩衝的填充守衛
（`mcmc_2dgs_density_controller.py:412`）**原本不含 `cost_aware_densify`** ⇒ 它本來會是

族群大小由 **`cap_max`（顆數）** 決定，不由成本決定。所以「成本感知取樣」只能改變
**哪些顆存在**，完全不能改變**花多少資源**——成本訊號**沒有預算可以交易**。

```
現在的實作   max Q  s.t.  N <= cap          ← 約束是**顆數**，成本只是取樣權重
命題要的     max Q  s.t.  (1/K)·Σ c_i <= B  ← 約束是**成本**
```
⇒ **`cost_aware_densify` 從來就不是「論文命題的另一半」，它是把命題的訊號塞進一個
仍然以顆數為約束的框架裡。** 命題真正沒被實作過的部分是**把 `cap_max` 換成成本預算**。
在顆數約束下，v/c 排序只是在同一條等顆數線上移動 —— 這與 §3.1.1「覆蓋為硬下限」的
修正一致，也解釋了為何 `vpc_prune_frac`（剪枝側）與 `cost_aware_densify`（增生側）
兩個方向都碰不到分數。

**對立論的影響**：不可再說「成本感知增生是命題的驗證」。存活的說法是
「**價值訊號**（|g|）在 MCMC 取樣上有效（agd，兩塊全勝）；**成本訊號**在顆數約束下無效，
要有效必須把成本升格為約束本身」——後者尚未實作，是下一個真正的實驗。
