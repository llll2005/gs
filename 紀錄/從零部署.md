## 一、最短路徑（機器有外網 + conda + NVIDIA 驅動）

```bash
git clone git@github.com:llll2005/gs.git && cd gs
bash scripts/setup/bootstrap.sh --env gspl      # 建環境 + 編三個 CUDA 擴充 + 驗證
# 資料（不在 git 裡）：見第三節
conda activate gspl
python tools/verify_pairing_geometric.py --data data/matrix_city/aerial/train/block_all   # ★ 關卡
bash scripts/lab/task_speed3.sh 13              # 本機加 RUN_PREFIX= CITYGS_VRAM_CAP_GB=
```

`bootstrap.sh` 的步驟：
```
0 前置條件（conda / GPU / 磁碟）
1 conda 環境（python 3.9）+ CUDA 11.8 toolkit
2 torch 2.0.1+cu118
3 套件（requirements/lock_gspl_2026-09-11.txt，**自我修復**：跳過 PyPI 上沒有的並列出）
4 Trim 光柵器原始碼 + glm
5 編 Trim 光柵器
5b 編 diff_gaussian_rasterization 與 simple_knn   ← 少了它們**任何**跑次都起不來
5c 預先編 gsplat 的 CUDA 後端                      ← 不預編的話第一次 densify 才炸
6 驗證（**功能**驗證，不是「import 成功」）
7 單元測試（`-p "*_test.py"` 不可省）
8 資料清單
```

## 二、10 個阻斷點（按遇到的順序；括號是「會不會在安裝階段報錯」）

```
 1 鎖檔有 `dataclasses==0.8`（會報錯，但只在新環境）
   Python 3.7+ 的標準庫，PyPI 上那個是 3.6 backport => **全新環境一定裝不起來**。
   本機有它是舊 pip freeze 的殘留 ⇒ **在本機永遠看不出問題**。已從鎖檔移除。
 2 鎖檔有 4 個**不在 PyPI 上**的條目（會報錯）
   plas / pytorch3d / simple_knn / torch-scatter —— pip freeze 只留 name==version、URL 丟了。
   => 安裝改成**自我修復**：解析「No matching distribution found for X」、移出後重試，
      最後**明確列出跳過的**（不是靜默少裝）。
 3 `PIP_CONSTRAINT`（會報錯）
   NGC 容器把 torch 釘在 2.7.0a0 => `pip install torch==2.0.1` 直接 ResolutionImpossible。
 4 `LD_LIBRARY_PATH` 第一項是系統 torch 的 lib（**不報錯**）
   torch 2.0.1 **裝成功**，但 `torch._C` 載到系統 torch 的 libtorch_python.so：
   `undefined symbol: _PyThreadState_GetCurrent`。
   => bootstrap 清掉它，並寫進 `$CONDA_PREFIX/etc/conda/activate.d/00_sanitize_ld.sh`
      （否則使用者自己敲指令會再撞一次）。
 5 conda 插件炸掉（會報錯，但訊息莫名）
   conda 26.5.3 / CPython 3.14 / libmamba 在**任何**子指令都可能丟
   「An unexpected error has occurred」=> `CONDA_NO_PLUGINS=true`
   ⚠ 連帶：關插件會把 **libmamba solver 也關掉** => 必須同時 `CONDA_SOLVER=classic`
   ⚠⚠ `--no-plugins` 旗標必須放在**子指令之前**（`conda --no-plugins install`）；
      放成 `conda install --no-plugins` 是「unrecognized arguments」。我踩過，追了兩輪。
 6 容器的 `python` 是 3.14（**不報錯**，只是裝錯地方）
   `pip install --user huggingface_hub` 裝進 3.14 而它在那上面壞掉。
   ⛔⛔ **而且它把 conda 弄壞了**：舊版 typing_extensions 讓 conda 的 anaconda-auth
        entry point 載入失敗 => conda 每個子指令都掛。`rm -rf /root/.local` 復原。
   => 任何 python 步驟一律 `conda run -n gspl`；下載用 wget，不依賴 python。
 7 `third_party/glm` 是空的（**不報錯**）
   `.gitmodules` 沒有光柵器的條目 => `git submodule update` **回傳 0 卻什麼都沒做**
   => `A || B || C` 的鏈直接短路，clone 從來沒執行。改成每一步都驗 `glm/glm.hpp` 在不在。
 8 `TORCH_CUDA_ARCH_LIST` 含 Blackwell(10.0)（會報錯，但很晚）
   torch 2.0.1 不認識 => `ValueError: Unknown CUDA arch (10.0)`。
   建置期與**執行期都要**鎖（見 10）。不要寫死，問 GPU：
   `torch.cuda.get_device_capability(0)`。
 9 CUDA 11.8 的 nvcc 只吃 gcc <= 11（會報錯）
   容器是 Ubuntu 24.04 / gcc 13 => `crt/host_config.h:132: unsupported GNU version`。
   ⛔ **不要用 `-allow-unsupported-compiler`** —— nvcc 自己警告「may cause incorrect
      run time execution」，而這是算梯度的 kernel。正解：`conda install -c conda-forge
      gcc_linux-64=11 gxx_linux-64=11` 到環境裡，用 `NVCC_PREPEND_FLAGS="-ccbin $CXX"`。
10 gsplat 在**第一次被用到時**才 JIT 編譯（**不報錯，到 step ~1,049 才死**）
   wheel 裡沒有 .so。MCMC 的 `compute_relocation` 是第一個碰到它的地方
   => **第一次 densify 事件**才觸發，前 1,048 步完全正常。
   => ① 執行期也 export 正確 arch（`scripts/lab/_common.sh`）
      ② bootstrap 5c 先編好快取
   ⚠ 不要在別的行程正在 JIT 同一目錄時 `rm -rf ~/.cache/torch_extensions`
     —— 我這樣做過，把建置中的目錄刪掉：`can't create *.cuda.o: No such file or directory`。
```
**其他非阻斷但會咬人的**：headless 容器沒有 `libGL.so.1` ⇒ `import cv2` 失敗
（鎖檔同時裝了 `opencv-python` 與 `-headless`，前者遮住後者；移除前者後**要重裝** headless，
而且要 `--force-reinstall`，因為 dist-info 還在、pip 會判定 already satisfied）。

## 三、資料（**不在 git 裡**）

官方只出 `transforms_test.json`，**沒有 `transforms_train.json`** ——
`data_proc_mc.sh` 吃的那個檔案是使用者自己串 10 個 block 來的，而**串接順序決定
`0000.png..5620.png` 的命名**，預算 COLMAP 認的就是那組名字。所以：

```
① 下載（讓機器自己拉，不要從本機推：上行 14 Mbps vs 下載 71 MB/s）
   HuggingFace  BoDai/MatrixCity :: small_city/aerial/{pose,train,test}
     block_1..10.tar 共 27.9 GB ＋ 每個 block 的 transforms.json ＋ transforms_origin.json
   預算 COLMAP  gdown 1Uz1pSTIpkagTml2jzkkzJ_rglS_z34p7  -> data/colmap_results/
② 建 input/：**4 位數 = SfM 相機名**
   正確的 `NNNN.png` = `block_n/input/{frame_index:04d}.png`
   其中 (n, frame_index) = 依序串接 block_1..10 的 transforms.json 的第 k 幀
   映射檔 `data/matrix_city/aerial/global_frame_map_correct.json`
   工具 `scripts/setup/{lab,local}_rebuild_input.sh`（**hardlink**，不多佔 20GB）
   ★ 為什麼用 4 位數：`colmap_dataparser.py:350` 是**名稱優先**，檔名 == 相機名 ⇒
     「位置對應」那條 fallback 永遠不會觸發 —— 而那條路徑正是 §16.14 錯開 bug 的藏身處。
③ ★★ 關卡（沒過就不要訓練）
   python tools/verify_pairing_geometric.py --data <...>/block_all
   **C 段**（SfM 對應點的亮度一致度）要 >= 0.95：正確配對 0.988~0.995，錯開的 0.34~0.65。
   ⚠ A 段（sparse vs transforms.json）**抓不到錯開** —— 兩者共用同一組姿態。
④ partition：python utils/partition_from_colmap.py <...>/block_all --block_dim 5 5 --content_threshold 0.08 --force
⑤ 深度（**只有要開深度損失或 depth-init 才需要**）：scripts/lab/task_depthprep.sh
   ⚠ `estimate_dataset_depths.py` **不吃 `--encoder`**（CLAUDE.md 舊版寫錯，已修）
```

## 四、驗證「裝好 != 裝對」

`scripts/setup/verify_env.py`（bootstrap 第 6 步會跑）做的是**功能**驗證：
```
渲染一批合成高斯 + backward，檢查 means2D.grad[:,2] 非零
=> 證明 ABSGRAD **真的編進 kernel** 了（不是「import 成功」）
.so 的 mtime 要比 auxiliary.h 新 => 證明真的重編過
```
lab 實測通過：`16/16 顆的 .z 非零，最大 1.1570e+02`。

## 五、排程

```
單卡：setsid nohup bash scripts/runner.sh > /dev/null 2>&1 < /dev/null &
多卡容量（例如 24GB 放 3 個 6GB 信封）：
  RUNNER_SLOTS=3 setsid nohup bash scripts/runner.sh ... &
  [cpu]  前綴 = 不碰 GPU，不排隊
  [solo] 前綴 = 獨佔整張卡（給沒有 VRAM 上限的跑次，例如官方忠實 config）
```
