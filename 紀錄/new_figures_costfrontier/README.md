# 成本-品質前緣與相關比較（2026-10-01）

產生：`python tools/plot_cost_frontier.py`（數字寫在腳本裡，出處見各節）。
軸的讀法：**往左＝更便宜、往上＝品質更好；同成本比較看「同一個 x 位置誰比較高」。**
**每個點都是一個跑完的模型（或同一模型的一種剪法），連線只是把同一組設定的點連起來，不是訓練過程。**
成本一律是 **精確 Load 中位**＝光柵器實際 binning 的 (tile, 顆) 對數 Σtiles，每視角取中位（同工具 `tools/cost_budget_calibrate.py`、同相機）。
val PSNR 是 val⊂train（同模型、同塊之間的相對比較用）；只有圖 5 是官方 held-out。

判讀：

- **v/c trim 在 cap 線的左上方**：Load -46% 而 PSNR 只 -0.04；同 Load 下 cap 線推估 27.83 => **高約 +1.2 dB**。
  先前只看「PSNR 掉多少」把它判掉，是評估角度錯了。
- conic 是整條線往左平移（同品質、成本 -40%）。

⚠ 更正（2026-10-01）：原表頭「單視角最大貢獻（現行 trim 判準）」標錯了。它是各視角**總貢獻**（每像素平均 × 覆蓋像素）取最大，
偏好又大又亮的顆粒，所以同顆數下 Load 最高；**現行 trim 判準 v 是每像素平均貢獻取最大**（已除過面積），**v/c 也不在這張圖裡**。
兩者已補測（tools/tile_topk_prune.py 加了「現行 trim v」與「v/c」兩欄），結果出來後更新本圖。

判讀：同顆數下四種剪法的 PSNR 接近（隨機明顯最差），但**前 K 名的 Load 最低** => 同成本下它最好
（Load ≈1.37M：前 K 名 27.23 vs opacity 25.22）。opacity 分布：中位 0.39、o>0.9 佔 21.7%、o<0.05 佔 5.8% => 大量卡在中間值，兩極化有空間。

v/c 在「剪完不重訓」時最差：它只留小而暗的顆粒、畫面出現大洞；它在訓練期有效是因為 MCMC 會把名額重新分配（圖 1、2）。

## 圖 6　剪完再 fine-tune　`f6_prune_finetune.png`

cs60_conic b6 60k 剪枝後用 Lightning **接續** 60k -> 65k（學習率停在最終值，增生與 trim 在 30k 後本來就停）。

| 臂 | N | 剪完未重訓 Load / PSNR | fine-tune 後 Load / PSNR / SSIM / LPIPS |
|---|---:|---|---|
| 不剪 | 2.34M | 2.94M / 30.48 | 2.93M / **30.68** / .892 / .122 |
| 前 32 名 | 1.16M | 1.37M / 27.23 | **1.55M** / 29.84 / .868 / .153 |
| opacity（同 N） | 1.16M | 1.60M / 27.20 | 1.77M / 29.87 / .869 / .149 |
| 前 64 名 | 1.55M | 1.92M / 29.17 | 2.05M / 30.34 / .882 / .135 |
| opacity（同 N） | 1.55M | 1.93M / 28.83 | 2.07M / 30.32 / .883 / .133 |

判讀：fine-tune 補回大部分品質，兩種剪法補回後**幾乎一樣**（差 ≤0.04 dB）；前 32 名的 Load 低 13%（前 64 名只低 1%）。
fine-tune 時 Load 會回升（顆粒長大）。不剪多跑 5k 步本身也 +0.20 => 比較要對「不剪＋5k」。
相對於「不剪＋5k」：前 64 名 Load -30% / PSNR -0.35；前 32 名 Load -47% / PSNR -0.84
（訓練期 v/c trim 在 60k 是 Load -49% / PSNR -0.26 => 訓練期 v/c 仍較好）。
