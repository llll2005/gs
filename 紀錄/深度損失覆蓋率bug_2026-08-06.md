# 深度損失覆蓋率 bug（P7）：汙染範圍、修正、與重跑判斷

2026-08-06。**這份的用途是畫界線**：哪些數字被汙染、哪些沒有。不畫清楚的話，下次 session 會拿
被汙染的數字當基準繼續疊。

---

## 1. Bug 本身

`internal/metrics/citygsv2_metrics.py`：

```python
predicted_inverse_depth = 1. / (outputs["surf_depth"].clamp_min(0.).squeeze() + 1e-8)
```

`surf_depth` 在**沒有粒子渲染到的像素**是 0 ⇒ `1/(0+1e-8) = 1e8`。深度項在那些像素不是損失，
是噪音。上游第 83 行的 `# TODO: apply mask` 早就標了，**但那個除法是我方加的**——上游
`inverse_depth_metrics.py:74` 直接讀 `outputs[depth_output_key]`，不做除法。
我方必須除，因為 `sep_depth_trim_2dgs_renderer.py` 只輸出 `surf_depth` 沒有 `inverse_depth`；
**改寫是必要的，但沒有守住除數為零的情形**，而遮罩材料 `rend_alpha` 就在同一個 output dict
（`:175`）。

**汙染率與結果單調對應**（2.4% 掉一點分 → 15~19% 直接崩）＝劑量反應，不是巧合。

### 為什麼今天的線全中、以前的全乾淨

差在**顆數的走向**：

- 舊 60k 線 `interval 150` → 顆數**成長**到 1~2M → 覆蓋越來越滿 → 從不觸發
- 今天 24k 線 `interval 350` → 顆數從 1.2M **衰減**到 7.8 萬 → 過程反覆出現覆蓋破洞

⇒ **這不只是 metric 的 bug，24k 排程本身（interval 350 > 破平衡點 231.5）就是製造破洞的機制。**

### 爆點是暫態的

終點 checkpoint 全部乾淨（實測未覆蓋像素 0.0000%，`1/(d+1e-8)` 最大 1.71–4.71）。爆點發生在
densify / relocation / 剪枝事件之後、覆蓋短暫失效的那幾步，然後恢復。但**每次暫態都往 Adam 的
二階動量灌一個 1e5~1e6 的梯度**。

## 4. 修正

`CityGSV2Metrics.depth_coverage_eps: float = 1e-4`（0 = 回到舊行為）。

未覆蓋像素的預測**換成 detached 的 GT**，而不是刪除——`depth_loss_type` 是 `l1+ssim`，SSIM 是
窗口運算，挖洞會讓它沒定義；填 GT 讓誤差與梯度在該處恰為 0，兩種損失形式都成立。

**驗證（`tools/verify_coverage_gate.py`，兩面都要成立）**：

```

aggr24k_b12(v1,終點)    77,616     0.0000%         1.71      ✅ 靜默
graded_k4(終點)         78,899     0.0000%         1.62      ✅ 靜默
oreg_0p002(終點)       900,000     0.0000%         2.18      ✅ 靜默
reg000_exact(終點)   1,799,999     0.0000%         4.71      ✅ 靜默
```

gate 在健康模型上完全不動 ⇒ **既有的乾淨比較仍然有效**。

## 5. 界線：什麼被汙染、什麼沒有

### ❌ 被汙染，不可再當基準

| 結論 | 說明 |
|---|---|
| **v1 用 77,616 顆拿到 22.070** | 「少而準」整條線的起點。2.4% 的步數帶著壞梯度 |
| **77.6k 的建築紋理比 0.170** | 模型是在壞損失下訓出來的，不能當「77.6k 能買到什麼」 |
| **v2 / v3 的失敗歸因**（opacity 被壓垮 / interval 太短）| 主因可能是 P7，需重新檢視 |
| **cap80k 崩潰** | 已確認是 P7；「少而準」**仍是開放問題** |

### 🟡 部分有效

**Stage 0（graded init）的空結果**：兩臂汙染率幾乎相同（2.4% vs 2.3%），**差值比較大致仍成立**，
但兩臂都是退化的模型，絕對值不可引用。

### ✅ 完全不受影響

- **`oreg_0p002_b12` 23.848 / `b12_cap2m_reg000_exact` 23.39 與所有 60k 線**（0 個爆點）
- **步數 vs 顆數的邊際比較**（0.129 vs 0.039）——用的是 oreg/reg000 的 30k 與 60k checkpoint，兩者皆乾淨
- **起始 trim 的全部發現**（73% 被砍、存活數固定 36.2 萬、保留錯的前層）——量在 checkpoint 上，不涉及損失
- **幾何比較表**（覆蓋倍數 / PCA 厚度 / overdraw）——同上
- **RAIN-GS 核對**、**track 長度統計**、**重投影誤差反相關**——不涉及訓練
- **`official_ft_blk5` 23.342 與正在跑的 `official_depthinit_blk5`**（`d_reg` 最大 0.412，乾淨）

## 6. 重跑判斷

**不建議整條 24k 線重跑。** 理由：

1. 24k 線的存在理由是「快速迭代」，但它的 `interval 350` **本身就是缺陷**（破平衡點 231.5，
   顆數必然衰減）。修好 metric 再跑同一份 config，只是把一個有兩個缺陷的設定改成一個。
2. 真正的活問題只有一個：**「少而準」成不成立**。那需要 cap80k 用**修好的 metric + 不衰減的排程**
   重跑，而不是重跑 v1。
3. Stage 0 的空結果大致仍成立，重跑的邊際價值低。

**建議順序**：

| | 內容 | 成本 |
|---|---|---|
| 1 | 讓 `official_depthinit_blk5` 跑完（init 的單變數答案，乾淨） | 進行中 |
| 2 | cap80k 重跑：修好的 metric + `interval 150`（成長區）+ cap 80k | ~4h |
| 3 | CSV 逐筆標記被汙染的 7 個跑次 | 已做 |

⚠ 第 2 項有一個設計難點：`interval 150` 會讓顆數**成長**到 cap，但起始 trim 後是 36 萬 > cap 8 萬，
所以會先靠剪枝衰減到 8 萬——衰減過程仍可能出現覆蓋破洞。**修好的 gate 正是為了讓那段安全**，
所以這次重跑同時也是 gate 的實戰驗證。
