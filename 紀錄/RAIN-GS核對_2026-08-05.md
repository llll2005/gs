## 1. 結論先講：這篇是我方 init 線最強的外部支持，不是反證

先前（含使用者轉述的 Gemini 意見）把 RAIN-GS 定位成「主張 init 不重要」的反證。**讀完原文，
定位錯了。** 它的立論恰好是「init 極度重要，而且重要的原因是優化器搬不動高斯」。

### Table 1 — init 精度值多少分

```
Init.             PSNR↑    SSIM↑   LPIPS↓
SfM              27.205    0.815   0.214
SfM + ε          24.944    0.771   0.270     ← 加 N(0,1) 噪音：−2.26 dB
SfM + constant   26.204    0.761   0.277     ← 加一個常數偏移：−1.00 dB
```
（Mip-NeRF360 平均）

**我方 depth-init 離表面 20.2× 就是「SfM + ε」那一列。** 在他們的基準上，這個條件值 −2.26 dB。

### Table 2 — 為什麼 init 決定一切（Truck 場景，高斯在優化中移動的距離）

```
              3DGS(SfM)   3DGS(Random)   RAIN-GS(Random)
Means           0.349        0.184           12.100
Stds            0.726        0.297           18.600
Top 1%          3.418        1.524           82.721
```

原文：*"the original 3DGS optimization scheme **struggles to transport Gaussians further from
their initialized locations**"*。

**這就是 3DGS 論文那句「floaters that cannot be removed by optimization」的機制**——不是優化器
不想修，是它**搬不動**。也解釋了我方實測的 20.2× → 29.2×：粒子只漂了 1.45×，因為它們本來就搬不動。

### Table 3 — 他們的解法有效，但是走另一條路

```
                      Mip-NeRF360 平均    PSNR     SSIM    LPIPS
3DGS  + SfM                              27.205   0.815   0.214
3DGS  + Noisy SfM                        24.944   0.771   0.270
3DGS  + Random                           22.190   0.704   0.313
RAIN-GS + Random                         27.228   0.807   0.229   ← 追平 SfM
```

**兩條路通往同一個問題：**
- 我方：把 init 弄對（錨點）
- RAIN-GS：讓優化器搬得動（SLV + 漸進低通 + ABE-Split）

**互補，不互斥。** 而且它替我方的診斷前提提供了外部驗證。

## 2. ⛔ Prior art 撞擊：`s = HW/(9πN)` 就是我們的 `c_i`

§5.2「Progressive Gaussian low-pass filter control」：

> *"we control s to regularize the Gaussians to cover wider areas during the early stage of training
> and progressively learn from a more local region. Specifically, as the value s ensures the projected
> Gaussians area to be larger than 9πs², we define the value s such that **s = HW/9πN**"*

`H,W` 是影像尺寸、`N` 是高斯數 ⇒ **`s` 是「總螢幕面積 ÷ 顆數 ＝ 每顆的螢幕預算」**。

**這是螢幕足跡作為控制變數，從頻域論證獨立導出的版本。**

### 對論文的影響（必須改）

`紀錄/現行方案與公式.md` §4/§7 與 `論文核對表.md` 現在寫的是「**所有既有方法都是 `c_i ≡ 1` 的特例**」
——**這句話對 RAIN-GS 不成立，必須修掉。**

真正的區別（是真的，但要寫精確）：

| | RAIN-GS | 我方 |
|---|---|---|
| `c_i` 的角色 | 由粗到細的**優化排程下界** | 逐顆的**實際成本** |
| 逐顆差異 | **無**，每顆同一個下界 `s` | 有，`c_i` 是該顆自己的 tile 足跡 |
| 綁在什麼上 | 顆數 `N`（自我調節的排程） | **硬體 VRAM 預算 `B`**（資源約束） |
| 解的問題 | 學習頻率順序 | `max Q s.t. (1/K)Σc_i ≤ B` 的約束最佳化 |

⇒ 我方的貢獻要重新表述成「**把螢幕足跡從優化排程提升為資源約束，並逐顆計價**」，
不能再說「沒人用過螢幕足跡」。

## 3. 三個機制對 6GB / 城市尺度的可用性

### 3.1 漸進低通 → **在我方 N 下是 no-op**（算過）

取 `s² = HW/(9πN)`（原文寫成 `s = HW/9πN`，但要讓 `N·9πs² = HW` 成立必須是平方；
依其量綱與用途判斷為平方）：

```
H×W = 1600×900 = 1,440,000   （down_sample_factor 1.2）

N = 1,316,223 (我方 graded init) → s² = 0.0387, s = 0.197 → 半徑下界 ≈ 0.59 px
N =   458,700                    → 半徑下界 ≈ 1.0 px
N =    77,616 (v1 終點)          → s² = 0.656, s = 0.81 → 半徑下界 ≈ 2.4 px
N =     1,000 (RAIN-GS 的 regime)→ s² = 50.9,  s = 7.14 → 半徑下界 ≈ 21.4 px
```

**這個機制在 N 大時自動失效。** RAIN-GS 的 SLV 從幾十~幾千顆起步所以它很活躍；我方從 130 萬顆
起步，下界是**次像素**，完全不作用。**不能直接借。**

（🧪 但有一個副產物觀察：v1 的終點 77.6k 落在下界 2.4 px 的區域——若我方要走「極稀疏高效率」
那條線（v1 用 77.6k 拿到 22.070），這個機制會**開始有意義**。記在此處待評估。）

### 3.2 SLV（稀疏大變異初始化）→ **與 6GB 直接衝突**

SLV 是「少量、大變異」的高斯。在我方負載下，大變異高斯＝**怪物**（單顆蓋滿整幀），
而怪物正是我方 OOM 的主因——`screen_size_prune_px=250` 這個防禦機制存在就是為了殺它們
（見 `廢案彙整.md` §11）。**不可移植。**

### 3.3 ABE-Split → **可借，且對到既有待辦**

§5.3：分裂成三顆，前兩顆走原本的 split；**第三顆不從原高斯的 PDF 取樣**，而是位移一個正比於
場景尺度的常數，**並且保留原尺寸不除以 1.6**——目的是讓它在新位置能從更大範圍收到梯度。

理由（原文）：*"As the new Gaussian is sampled from the PDF of the original Gaussian, it is likely
to be located near the original Gaussians... 3DGS more easily models scenes inside the initial
bound compared to those outside of it"*。

**這正好對到待辦第 10 項**（Diet §3.2 的 relocation 共位問題：回收點沿累積位置梯度加小位移）。
兩者是同一族機制。**ABE-Split 給了「保留原尺寸」這個我方沒想到的細節**——位移後若把尺寸也縮小，
新位置收到的梯度範圍太窄，等於白搬。

## 4. 適用範圍的保留

RAIN-GS 在 Mip-NeRF360 / Tanks&Temples / Deep Blending 上驗證——**單物件為中心的小場景，
資源無上限**。沒有城市尺度、沒有 VRAM 約束。

使用者提出的辯護是「RAIN-GS 假設資源充足，6GB 沒本錢讓優化器盲目探索」。**現在有數字可以評估**：
它的傳輸把移動量從 0.349 拉到 **12.100（35×）**。在我方 regime，大幅移動 ＝ 重新分箱、重新排序、
churn——而 churn 我方已實測為淨負（`cost_aware_theory` 的消融）。所以這個辯護**方向合理**，
但仍未在我方負載上實測。
