## 1. 訓練時間

### 1.1 單跑牆鐘：lab 三槽平行 vs 本機獨佔（圖 7）

量測條件：lab = RTX 3090、`CITYGS_VRAM_CAP_GB=5.66`、`max_split_size_mb:128`、三槽平行（鄰居會搶 GPU／CPU／RAM）；
本機 = RTX 4050 Laptop 6 GB、獨佔、原生上限。牆鐘含快取影像、驗證、audit 等非訓練開銷。
⚠⚠ **台帳的 it/s 不可用來比速度**（2026-09-18 讀碼確認）：`internal/callbacks.py` 算的是
`(step - step_last) / (now - t_last)`，而 `t_last` 每 **≥1 秒**才重設一次 ⇒ DONE 行印的是
**最後約 1 秒視窗的瞬時速率**，不是整趟平均。三槽平行時它取決於那一秒鄰居在做什麼
⇒ 同樣工作量（同 N、同步數、同配方族）印出 **2.56~4.84 it/s（1.9 倍）**，而牆鐘只差 ±8%。

### 6.1 uint8＋不載深度的驗證

**(a) 窮舉 256 個 uint8 值，與現行路徑（CPU float64 / 255 -> float32）比較**

| 轉換方式 | 不同的值 |
|---|---|
| CPU float32 / 255.0 | 0 |
| CPU float32 / 255（整數） | 0 |
| CPU uint8.float().div(255.) | 0 |
| **GPU float32 / 255.0**（原本 `on_after_batch_transfer` 的寫法） | **126**（最大差 5.96e-08） |
| GPU float32 / 255（整數） | 126 |
| GPU float64 / 255 -> float32 | 0 |

**(b) 真實訓練影像（b6 資料夾抽樣，含 LANCZOS 縮放與 alpha 合成）**

| 比較 | 結果 |
|---|---|
| 抽 50 張：天真 uint8（GPU float32 / 255） | 50/50 張有差異 |
| 抽 50 張：修正 uint8（GPU float64 / 255 -> float32） | 0/50 |
| 抽 141 張：alpha 最小值 | 255（全不透明） |
| 抽 141 張：修正路徑 vs 現行（含 alpha 合成原式） | **0/141** |

## 9. 外接盒與 binning：上游線性化的代價（2026-09-20）

### 9.1 病灶：`truncated_R * extent(1)` 是線性化，不是精確解

`computeAABB` 用對偶圓錐的封閉解算出 **r=1 那條等高線**的精確外接盒，呼叫端接著做
`radius = ceil(truncated_R * max(max(ex, ey), FilterSize))` —— 乘一個純量、**中心不動**。
但 ray-splat 交點 `p = k x l` 對像素是**仿射**的（因為 `Tw x Tw = 0`），所以
`u^2 + v^2 <= R^2` 在螢幕上是**真正的圓錐曲線**，而透視下不同 R 的等高線**不是等比放大**。
⇒ 外推在透視強的地方偏小，會砍掉實際 alpha 仍 >= 1/255 的像素。

精確解同成本：把對偶簽名 `(1,1,-1)` 換成 `(R^2, R^2, -1)`，不要再乘 `truncated_R`。
正交極限下自動退化回 `R * extent(1)`，是現行式子的嚴格推廣。
⚠ `d = C*_33 ~= -(深度^2)`，**負號是常態**（`Tw = (u軸.z, v軸.z, 中心深度)`）；中心與半寬都是
C* 的比值，對整體符號不變 ⇒ 只有 `d == 0` 才是真退化。我一度用 `d > 0` 當門檻，結果
99.999% 被判成無界。

### 9.2 誤差的形狀（不是隨機噪音）

線性化在 **88.7%** 的（顆粒,相機）組合上**高估**（白付 tile），只在 **11.29%** 上**低估**；
平均多算 0.377 px，但**最大 73,491 px** ⇒ 是一小批**接近側視（edge-on）的片**被靜默截短。

### 9.3 離線天花板（`tools/bbox_rect_ceiling.py`，b6 `cs_refrep` @21,920，N=1,850,094，30 台相機，tile 16）

| 外接盒 | 半徑 | Σ tile | 相對現行 |
|---|---|---:|---:|
| 線性化 · 正方形 | 3 sigma **（現行 CUDA）** | 156,845,203 | 基準 |
| 線性化 · 矩形 | 3 sigma | 93,229,648 | −40.6% |
| 線性化 · 正方形 | 精確支撐半徑 | 136,555,115 | −12.9% |
| 線性化 · 矩形 | 精確支撐半徑 | 81,640,430 | −47.9% |
| 精確圓錐 · 正方形（塞回對稱 API） | 3 sigma | 168,026,161 | **+7.1%** |
| 精確圓錐 · 矩形（塞回對稱 API） | 3 sigma | 100,709,291 | −35.8% |
| **精確圓錐 · 不對稱盒** | 3 sigma | **92,189,961** | **−41.2%** |
| 精確圓錐 · 不對稱盒 | 精確支撐半徑 | **80,880,718** | **−48.4%** |

⚠ 「塞回對稱 API」那兩列是關鍵教訓：`getRect(中心, 半徑)` 逼你付 `|中心位移| + 半寬`
＝把位移**左右各算一次** ⇒ 精確圓錐盒單獨做反而 **+7.1%**。
⇒ **「精確圓錐盒」與「不對稱矩形盒」不能拆開做。**

### 9.4 為什麼中心不能動

`points_xy_image[idx] = center` 有**三個**消費者，不只是盒子的錨點：
① `getRect` ② **`renderCUDA` 的 `rho2d = FilterInvSquare * ||pix - xy||^2`＝低通濾波核的中心**
③ **`backward.cu` 的 `computeAABB`** 按 r=1 的公式把 `dL_dmean2D` 回傳到 transMat。
⇒ 動中心會**改變渲染本身**（小而薄的片受影響最大）且讓梯度**靜默不一致**。
而且它本來就不該隨 r 變：R->0 時它收斂到真投影中心 `Tu.z / Tw.z`，r=1 已偏離一個透視項；
若隨 R 走，低通核位置會**隨顆粒的不透明度飄移**。
⇒ 正解是**解耦**：`center` 原封不動，盒子改用 `(rect_min, rect_max)` 表達不對稱形狀。

`radii` 同理**刻意不動**：它餵 `_max_radii2D`，被 `screen_size_prune` / `vpc` 的 `c = radii^2` /
`cost_aware_densify` 當「顆粒的螢幕尺寸與成本」用；不對稱盒的覆蓋半徑含中心位移，拿去當尺寸會失真。

### 9.5 CUDA 實測（本機 RTX 4050 Laptop，同一 ckpt，20 台相機 x 3 次取最小）

| 建置 | forward | fwd+bwd | Σtile（radii 近似） | 渲染是否改變 |
|---|---:|---:|---:|---|
| 基準（線性化 · 3 sigma） | 101.81 ms | 266.55 ms | 基準 | — |
| `EXACT_SUPPORT_RADIUS 1` | 94.38 ms **−7.3%** | 253.96 ms −4.7% | −13.4% | **否**：1.93% 像素、最大 3.46/255 |
| `EXACT_CONIC_AABB 1` | **76.88 ms −24.5%** | 226.41 ms −15.1% | （見 §9.3） | 是（把被截掉的覆蓋補回來） |

離線 −13.4% vs 實測 −13.4%（精確半徑）⇒ **離線工具驗證通過**。
轉換率約一半：Σtile −13.4% -> forward −7.3%；Σtile −41.2% -> forward −24.5%。

**margin 掃描（證明殘差不是像素邊界效應）**：加 margin 後最大差
1px 0.5693/255（1.649% 像素）-> 2px 0.5658（1.460%）-> 4px 0.4327（1.277%）＝**打平**。
邊界效應加一圈 margin 就該消失；打平代表殘差來自**線性化**。
⚠ margin 必須同時夾住上限（`GROW=0` 的語意是「只縮不長」）：不夾時高不透明度顆粒的
`truncated_R` 已被 cap 在 3、半徑等於基準，再 +1 就**超過**基準 ⇒ 雙向差異，
不同像素從 1.93% 反升到 **6.50%**。已在 `forward.cu` 補上夾制。

### 9.8 精確的 binning 成本 `tiles`（2026-09-21 已實作）

`tiles_touched[idx]` ＝ 逐顆 tile 數 ＝ **binning 成本本身**。光柵器每步都算好，prefix sum 之後
仍完好（`rasterizer_impl.cu` 的 InclusiveSum 把結果寫進 `point_offsets`，沒覆蓋原陣列），
但**從未暴露給 Python**。現已接出來（`Rasterizer::forward` 的尾端選用參數 `out_tiles`，
nullptr 就完全不付；renderer 的 `outputs["tiles"]`）。
✅ 驗證：加了這個輸出之後渲染**逐位元相同**（SHA `a13583c9b550e9a2`）。

控制器旗標 `exact_tile_cost`（**預設 False**）把三個消費者從 `radii^2` 代理換成它：
`_update_load`（`cost_budget` 閘門）、`vpc` 的 `c`、`cost_aware_densify` 的 `cost`。

#### ★★ 代理的誤差會在訓練過程中**變號**

| 階段 | N | 代理 / 精確 | 方向 |
|---|---:|---:|---|
| 訓練初期（SfM init，首次觸發那個視角） | 579,003 | **0.280** | **低估 3.6 倍** |
| 訓練後期（`cs_refrep` @21,920，30 台平均） | 1,850,094 | **1.340** | 高估 34% |

逐視角的離散度（後期，30 台）：中位 1.319、**最小 0.852、最大 3.356**、標準差 0.4605。

**機制**：`Σ(2r/16)^2` 忽略 **tile 量化**。半徑 3px 的顆粒它算出 0.14 個 tile，但只要可見
就至少碰 1 個 ⇒ 小顆粒被系統性低估。實測 `Load/N = 1.15~1.28`（每顆約 1.2 個 tile，合理），
而代理會說每顆 0.14~0.3 個 ⇒ **物理上不可能的數字**。等顆粒長大，量化誤差被「正方形外接盒
高估」蓋過，於是翻成高估。

⇒ 對 `cost_budget`：**同一個預算數字在訓練前後代表的實際成本差約 5 倍，而且中途變號。**
這是閘門的**第二個**量測缺陷（第一個是取最壞視角的尖峰性，見 §1.2 與記憶
`cost_aware_sampling_refuted`）。⚠ 不宣稱它是 b12 退化的成因 —— 那件事已歸因於尖峰性 ——
但它是獨立存在、方向明確的第二個問題。

⚠⚠ **開旗標＝換單位**：先前標定的 `cost_budget` 數值是代理單位的，必須重新標定
（首次生效會印出當期的兩種單位值供換算）。
⚠ **窗口語意沒修**：`_max_tiles2D` 與 `_max_radii2D` 同語意（逐顆跨視角取 max）。
  DAR 當初刻意改用解析投影，理由就是「逐顆跨視角取 max 再加總，比任何真實單一視角都大」——
  換成 tiles 只是把**每一項**量準，那個設計債還在。

### 9.9 連帶結掉的舊帳：K 預測器的 load 估計（2026-09-21）

`internal/utils/strip_cameras.py:86` 的 `estimate_render_load` 是動態 K 在渲染**之前**估 binning 的
解析式：`r = 3·fx·s_max/z` 然後 `(2r/TILE)^2`。它同時踩了我們今天量到的**四個**高估來源：
用 `s_max` 撐**正方形**、假設**正面朝向**（無前縮）、`(2r/16)^2` **忽略 tile 量化**、**不做畫面裁切**。
檔頭自承是「保守上界」，但在今天之前**沒辦法量它高估多少** —— 光柵器的逐顆 tile 數從未暴露。

`tools/strip_k_audit.py --exact`（新增）同一支工具、同一組相機、同一個 ckpt（b6 cs_refrep @21,920，24 台）：

```
解析估計 load   中位 11.4M   p90 13.0M
精確 tile 數    中位  4.8M   p90  5.7M
估計 / 精確 = 中位 2.28x   範圍 2.12~2.61   （沒有任何視角低估 => 上界的宣稱成立）
```

**★ 但用精確值重算 K，K 完全沒變**（sfminit 參數 3 -> 3；speed3 參數 8 -> 8）：

峰值模型是 `[B·N + γ·load] / K`，而
`B·N = 1550 B/顆 x 1.85M = 2.87 GB` vs `γ·load = 24 B x 11.4M = 0.27 GB`
⇒ **load 項只佔可切分部分的 9%**，砍半只讓分子動 5%，跨不過任何 K 的門檻。

⇒ **有用的負結果**：記憶 `dynamic_strips_confound` 記的「K 是白付的、預測器 budget 訂低約 1.1 GB」
  —— 今天證實那個歸因是對的，而「load 估不準」**不是**成因。省下去修估計器的功夫。
  （這也與 2026-07-12 那條舊教訓一致：「OOM 主因是 activation 不是 binning」。）

**★ 順帶修正一條方法論。** 舊記錄寫「CPU 估計 8.71x 高估，實際 3.45x ⇒ 此類解析估計要標為
『上界』不是『預期值』」。今天有了反例：`tools/bbox_rect_ceiling.py` 估精確支撐半徑省 **12.9%**，
CUDA 實測 **13.4%** —— 準。差別不在「解析 vs 實測」，而在**複製程式路徑的程度**：
```
bbox_rect_ceiling.py   逐行重現 computeTransMat + computeAABB + getRect，含 tile 量化與畫面裁切
                       且有**對照關卡**（vs 光柵器 radii，差 >1px 佔 0.00%）        => 誤差 0.5%
estimate_render_load   簡化式（s_max 正方形 / 正面朝向 / 無量化 / 無裁切），無對照關卡 => 誤差 128%
```
⇒ 正確的說法是「**解析估計的準度取決於它複製實際程式路徑到什麼程度，而且必須有對照關卡**」，
  不是「解析估計一律只能當上界」。

### ⚠⚠ conic 開啟後，代理指標會給出**完全相反**的結論

```
              代理 Σ(2r/16)^2 ÷ 精確 Σtiles
b6   base 1.282   conic **2.272**
b13  base 1.070   conic **2.234**
```
具體到 b13 的 max：代理說 base 10,831,692 -> conic **23,146,522**（看起來**貴兩倍**），
而精確說 10,108,848 -> 5,669,418（**便宜 44%**）。

**機制**：`radii` 被**刻意凍結**成線性化的對稱半徑（保護 `screen_size_prune` / `vpc` /
`cost_aware_densify` 的下游語意，見 §9.4）⇒ conic 開啟後 `radii` 與真實盒子**完全脫鉤**，
而代理正是用 `radii` 算的。

⇒ **任何人看訓練中的 `[cost-budget]` 打印，在 conic 開啟時會得到「成本翻倍」的錯誤結論。**
⇒ **conic 若要設成預設，`exact_tile_cost` 必須同時處理**，否則所有既有的預算標定會錯約 2.3 倍。
  （這是 §9.11 「權威順序 ③ > ① > ⓪」的第一個實戰後果。）

**⬜ 還缺的三項**
1. **離線 Load（Σtile）** —— 預測 −41.2%，尚未在 lab 的終點模型上用 `task_load_compare.sh` 驗證。
2. **60k 判決** —— `trimvpc` 在 22k 也是平手、60k 才顯出 −0.27/−0.54 ⇒ 短配方會系統性低估品質代價。
   **只有 60k 能決定要不要把 `exact_conic_aabb` 設成預設。**
3. b13 的 `cs_tilecal`（b13 的噪音底）—— 上面 b13 的判定借用 b6 的噪音底，是個假設。

### 9.10 γ（每相交位元組）實測 36.27，程式裡寫死 24（2026-09-21）

峰值模型 `[B·N + γ·load]/K` 的 `γ = BYTES_PER_ISECT = 24.0`，註解寫「key(8)+value(4) doubled
for CUB radix ping-pong」。但 `BinningState` 有**五**個成員，第五個 `list_sorting_space`
（CUB radix sort 的暫存）**沒算進去**。直接量（`scratchpad/gamma_check.py`：呼叫
`_C.rasterize_gaussians` 取回 `binningBuffer` 張量的真實位元組 / 相交數）：

```
b6 cs_refrep @21,920，8 台相機
實際 γ = 36.27 B/相交（8 台完全一致，36.27~36.27）=> 寫死的 24.0 **低估 51%**
```

**★ 附帶的獨立驗證：`num_rendered == Σtiles`，8 台全部完全相同。**
⇒ 我接出來的 `tiles` 確實就是 binning 相交數，也就是峰值模型裡的 `load`。

**⇒ 但兩個誤差方向相反、會互相抵消：**
```
預測器算的  γ x load_est = 24    x 11.4M = 274 MB
真實值      γ x load_真  = 36.27 x  4.8M = 174 MB      => 淨高估 1.57 倍（不是 2.28 倍）
```
而 `B·N = 1550 x 1.85M = 2.87 GB` ⇒ binning 那一項只佔可切分部分的 **6%**，
淨誤差 100 MB 落在 3 GB 上 = 3% ⇒ **跨不過 K 的門檻**（與 §9.9 的結論一致）。
⇒ **整條 binning 側的建模對 K 的決策而言是捨入誤差**，真正的槓桿是 `B·N` 與 budget。

### 9.11 四條成本量測路徑的權威順序（2026-09-21 定案）

同一個 ckpt（b6 cs_refrep @21,920）、同 30 台相機、`tools/cost_budget_calibrate.py`：

| 路徑 | max | 中位 | vs 精確 |
|---|---:|---:|---:|
| ⓪ 解析投影（`cost_budget_probe.py`：`3·fx·s_max/z·stretch`，clamp[1, 整幀]）| 20,144,376 | 18,102,572 | **3.452x** |
| ① 光柵器代理 `Σ(2r/16)^2`（**`cost_budget` 的現行單位**）| 8,525,008 | 7,242,940 | 1.381x |
| ② 代理 + 量化下限 `Σ max(q,1)` | 8,604,868 | 7,297,827 | 1.392x |
| ③ **精確 `Σtiles`（光柵器）** | 6,684,034 | 5,244,293 | **1.000x** |

**逐項差距的成因（各自獨立）**
- ⓪ vs ①：**半徑來源不同**（解析投影 vs 光柵器 radii），不是下限造成的。
- ① vs ②：**量化下限**。在**訓練後**的模型上只差 0.8%（顆粒已經夠大，多半 ≥8px），
  但在**訓練初期**它主導 —— 實測 SfM init 時代理只有精確的 **0.280 倍**。
  ⚠ 我原本假設「代理的誤差幾乎全部來自漏掉下限」，**這個 ckpt 上被證偽**（只差 0.8%）。
    兩個觀測不矛盾：它們是同一條曲線的兩端。
- ② vs ③：**正方形外接盒**的高估 —— 訓練後期的主要誤差來源，也正是 §9.1 那個線性化。

**★ 權威順序：③ 精確 > ① 光柵器代理 > ⓪ 解析（只可當上界）。**
⚠ 舊記錄「不可沿用 `cost_budget_probe.py` 的 23.1M」**成立且現在有數字**：那條路徑高估 3.45 倍。
⚠ `cost_budget` 的現行單位是 ①。換到 ③ 要重新標定，而換算係數**隨訓練變號**（0.280 -> 1.381）
  ⇒ 不能除以常數，要整條曲線（`tilecal` 臂產出）。
