### A1 精確外接盒（Speedy-Splat SnugBox 📄 §4.1.1、StopThePop 📄 §3.4）
**論文**：3DGS 的螢幕橢圓 `(x-mu)^T Sigma'^-1 (x-mu) <= t`，`t = 2 ln(255 sigma)`（sigma＝opacity），外接盒半寬
`x_d = sqrt(t * Sigma'_xx)`、`y_d = sqrt(t * Sigma'_yy)`，盒心＝投影中心。Speedy-Splat Table 1：render 4.48 → 2.34 ms（1.91x），排序 1.55 → 0.73 ms。
**我方**（`forward.cu` `computeAABB_R`，09-21 起預設）：2DGS 面元的螢幕支撐 `u^2 + v^2 <= R^2` 在透視下是圓錐曲線。設 2DGS 的螢幕變換三列為 `a, b, w`，
`S = diag(R^2, R^2, -1)`：
```
c_x = (a^T S w) / (w^T S w)        e_x = sqrt(c_x^2 - (a^T S a) / (w^T S w))     （y 同理用 b）
盒 = [c - e, c + e] ∪ 低通圓盤（中心＝r=1 的投影中心，半徑 0.7071 * R）        R = 3
```
**比較**：同一個想法（外接盒貼齊真正的支撐），我方是 2DGS 的精確透視圓錐、盒心可偏離投影中心（不對稱盒）；上游 2DGS 的線性化盒在 88.7% 的（顆粒,相機）上高估、11.3% 上低估。實測 Σtile −40～46%、forward −26%（`實驗分析/04`）。
**嫁接**：不需要；Speedy-Splat 的盒是我方的特例（正交極限、橢圓）。

### A2 依 opacity 縮小支撐（Speedy-Splat、StopThePop；FastGS Compact Box 📄 補充 §8）
**論文**：支撐半徑隨 opacity 縮：`t = 2 ln(255 sigma)`。FastGS 再乘 `beta^2`（`(p-mu)^T Sigma^-1 (p-mu) = beta^2 * 2 ln(sigma / tau_alpha)`），**有損**（丟掉 alpha 還 >1/255 的取樣）；Table 7：CB −14% 時間，PSNR −0.02。
**我方**（`auxiliary.h`）：`EXACT_SUPPORT=1` 只做「o <= 1/255 整顆不進 binning」（逐位元相同）；`R(o) = min(3, sqrt(2 ln(255 o)))` 已實作但 `EXACT_SUPPORT_RADIUS=0` 關著（無 margin 時有 25% 像素差到 0.38 個 8-bit 階）。
`R(o) < 3` 只在 `o < e^4.5 / 255 = 0.353` 時成立。
**量測（10-24，lab，ed10b4 全場景 b0／b4／b5 終模）**：o>0.9 佔 88.7／91.2／88.5%，o<0.353 只有 5.0～6.6%；以 `s1*s2` 當投影面積代理，**可縮的面積只有 5.1～5.9%**。
**判斷**：二元熵把 opacity 推到 0／1 => 這招對我們幾乎沒有空間（3DGS 的 opacity 分布散得多）。前 10k 只往 0 推的階段低 opacity 較多，但那段同時也在換顆。不做。FastGS 的 beta 是有損的品質旋鈕，不算加速。

### A3 逐 tile／逐列精確列舉（Speedy-Splat AccuTile 📄 §4.1.2；FastGS 沿用）
**論文**：在 SnugBox 內沿短邊逐列（或逐行）求橢圓在該列上下邊界的 x 範圍：極值只可能在盒的 x 極點（若落在該列內）或列邊界與橢圓的交點，
每列只算 2 個交點、相鄰列共用邊界 => 列舉成本正比於短邊長、處理成本正比於 tile 數。Table 1：render 再 2.34 → 2.06 ms（−12%）、排序 0.73 → 0.61。
**我方**：`tile_cull`（10-03，StopThePop §3.4 的 2DGS 版）：盒內**每個 tile** 用四角的單應映射算 rho 下界，判斷 alpha 是否可能 >= 1/255；
配對 −36%，但 **forward +30%**——每個 tile 都要 4 次叉積＋凸四邊形距離，而且 count 與 duplicate 兩個 pass 各做一次 => 判定比省下的還貴（已關閉的線 A）。
**比較**：兩者剔的是同一種浪費（盒的角落）。我們的判定逐 tile、用的是 alpha 門檻（較緊）；AccuTile 逐列、用的是幾何支撐（R=3 的圓錐），每列 O(1)。
**嫁接**（要改 CUDA）：在 `computeAABB_R` 的圓錐上做 AccuTile。2DGS 的支撐是「圓錐 ∪ 低通圓盤」，兩者在固定 y 下都是區間，逐列取聯集仍是 O(1)：
```
列 [y0, y1]：x_min = min( 圓錐左緣在 y0、y1 的值，以及 y* 若在列內的 c_x - e_x ；圓盤同理 )   x_max 對稱
圓錐在 y 的 x 區間：解 [x y 1] C [x y 1]^T = 0 的二次式（C = S 對應的點圓錐）
```
**先量再做**：離線（Python，同一批相機）算「conic 盒的 tile 數 vs 逐列精確的 tile 數」。若只少 10% 以下就不值得改 kernel。
**10-24 量（使用者授意直接做；本機 4050、b6 1.29M 顆、現行配方，光柵器各階段 CUDA event 計時，`scratchpad/tim_src` 計時版）**：
```
forward：前處理 1.12  展開鍵 0.55  排序 0.33  tile 範圍 0.02  render 25.4 ms   ｜ backward：render 38.8  前處理 1.15 ms   ｜ 一步 ~93 ms
```
binning（展開＋排序）一共 0.9 ms＝一步的 1%。10-03 的 tile_cull 已量過：配對 −36% 時 backward 只 −3%——被剔的配對多半排在飽和點之後，
render 迴圈本來就不會處理它們。=> AccuTile 能省的只剩排序那 1% 的三分之一。**不做**（程式沒動）。

### A4 逐顆平行的 backward（Taming 📄 §4.1；Faster-GS 🔍 消融最大的一項 1.20～1.84x）
**論文**：原版 backward 是「執行緒＝像素」，沿深度逆序走過該 tile 的每個 splat，對每顆的梯度做 atomicAdd => 同一 tile 的 256 個執行緒搶同一顆的位址。
Taming 改成「執行緒＝splat」：forward 每 N 顆存一次逐像素狀態（T、累積顏色），backward 開始時每個執行緒重建自己那顆之前的像素狀態，再用 warp shuffle 在執行緒間傳遞像素狀態，
每個執行緒只累加自己那顆 => 沒有 atomic 衝突。另外記 tile 的最後貢獻者、整批跳過遮擋後的尾巴。Table 2：拿掉它 Truck 7 → 14 分。代價：VRAM +20～38%（Faster-GS）。
**我方**（10-10，`backward.cu` `renderCUDA_opt`）：
```
飽和跳過：tile 內 last_contributor 取 max => 從那裡往回走，之後的配對整批跳過（Taming 的「尾巴」同一招）
先加總：  每個配對的梯度先在 warp 內 cg::reduce，再由一個 lane 做一次全域 atomicAdd（DISTWAR 同類）
```
實測增生期 backward −26～29%、60k −9～12%，換塊平手。
**比較**：Taming 把「像素 -> 顆粒」的歸約整個改方向；我們保留逐像素方向，只把 32 個 atomic 併成 1 個。剩下的差距＝warp 內歸約本身＋不同 warp 間仍有衝突。
**嫁接**：可行但工程大：2DGS 的逐像素狀態比 3DGS 多（現行配方開 dist100 => 要多傳 distortion 的累積量；lean 已把 normal／depth 通道拿掉）。
backward 現在 22.4 ms／步（44%）。Faster-GS 在已有類似 warp 歸約的基線上仍量到 1.2x 以上 => 估我方 −10～20% 每步。**要改光柵器 => 先問使用者**。
**10-24 先量上限（使用者授意直接做）**：編一個只計時的版本（`BWD_TIMING_NOR=1`：拿掉 warp 歸約與所有 atomic，梯度是錯的，但逐配對計算照做），
本機、b6 1.29M 顆、現行配方、SH16，交替兩輪：
```
              backward           一步
正常（RED）   48.9／48.1 ms      85.4／85.3 ms
拿掉歸約      43.3／45.1 ms      79.6／80.9 ms        => 歸約＋atomic 只佔 3～6 ms（約一步的 5%）
```
逐顆平行能省的就是這一塊，而它自己還要付「warp 內逐步傳遞像素狀態」的 shuffle（每配對約 8～10 個值，比 RED 每配對約 2.5 個 shuffle 多）。
=> 我們的飽和跳過＋先加總已經拿走論文那 1.2～1.84x 的大部分（他們比的是原版逐像素 atomic）。**不做**；上限實驗的旗標留在 backward.cu（預設 0）。
**更大的一塊是 dist**（見 §C 末「dist 每 k 步」）：同一設定 dist 關 => render backward 37.4 → 26.5 ms、forward 25.1 → 20.5 ms、一步 93.5 → 77.1 ms。

### A5 SH 分開存放（Taming §4.2、Faster-GS 1.02～1.09x、VRAM −4～11%）
**論文**：不在 forward 前把 SH0 與高階 SH 串成一個張量，光柵器分別讀兩個張量。
**我方**：每步 `cat(features_dc, features_rest)`＝N x 16 x 3 的新張量（2.25M 顆約 430 MB 寫入），backward 再切回兩份。估 1～2 ms／步。
**嫁接**：改光柵器的輸入介面（兩個指標）；或改成單一參數張量＋逐係數學習率（FusedAdam 是我們自己的 kernel，可以加）。延後，跟其他 CUDA 項一起問。
**10-24 實作（使用者授意）**：光柵器多收 `shs_rest`（`forward.cu computeColorFromSHSplit`、`backward.cu computeColorFromSHSplitBwd`；模板參數分出新路徑，原 kernel 原始碼不動），
renderer 旗標 `sh_split`（預設關）。驗證（本機）：新 .so 預設路徑 vs 舊 .so 渲染／radii／覆蓋數逐位元相同、梯度在噪音底內；split vs cat 渲染逐位元相同、SH 梯度與噪音底同級。
計時（本機、1.29M 顆、交替執行）：k=1（每步更新高階 SH）一步 −2～3%（全在 backward：省掉梯度切片的複製）；**疊在 SH16 上 +0.8%（量不到）**。
實際訓練裡 cat 的 forward 幾乎不花時間（之前的微量測 9 ms 是高估）。=> 預設關、不進配方。

### A6 融合 activation（Faster-GS 1.03～1.05x）
**論文**：exp(scale)、sigmoid(opacity)、normalize(quat) 在 preprocess kernel 裡做，不先在 PyTorch 產生中間張量。
**我方**：Python 端逐項產生（另外 MCMC 加噪每步也算一次 sigmoid 與共變異數）。估 2～3%。延後。

### A7 顆粒依 Morton 序重排（Faster-GS、LiteGS ⚠、SVRaster）
**論文**：依中心的 Morton（Z 序）碼排序參數陣列，同一 tile 的顆粒在記憶體中相鄰 => L2 命中率上升。約 3～6%。
**我方**：無。MCMC 的 relocation 把顆粒複製到任意死亡槽、新增的接在尾巴 => 順序在增生期持續變亂；收割期（後 50%）順序不再變。
**嫁接**（純 Python，10-24 已實作，`density.morton_reorder_interval`，預設 0＝關）：densify 事件結束處（所有視窗都已清空的地方），step 是倍數或最後一個 densify 事件就重排：
```
q_axis = round((x - p0.5%) / (p99.5% - p0.5%) * (2^21 - 1))        每軸 21 位元，交錯成 63 位元 Morton 碼；perm = argsort(code)
搬：參數＋Adam m／v（`Utils.prune_properties` 收 index）、`gaussian_model._trim_state`（累加式 V/C）、`_absgrad_accum`
```
trim 的剪枝用布林遮罩、保序 => 最後一次重排後，收割期（後 50%）順序不再變。漏搬狀態就是「看起來正常但量錯」（方法論 §2），所以：
本機 CPU 檢查（Morton 碼對逐位元參考一致、參數與 Adam 狀態一起正確排列、相鄰顆平均距離 6.57 → 0.77）；GPU 端第一次觸發時自檢「同一相機重排前後的渲染差」。
lab 功能測試（10-24 01:21 UTC，900 步、densify 提前到 100 步）：step 150、300 觸發；自檢重排前後渲染最大差 3.98e-3、只有 0.004% 像素不同（dup 副本深度相同時排序先後不同）。

### A8 融合 SSIM（Taming §4.2：可分離卷積＋融合 kernel；套件 `fused-ssim`）
**論文**：11x11 高斯窗可分離（`g g^T`），用兩個 1D 卷積；SSIM 的逐像素式子融合在同一個 kernel。
**我方**（`internal/utils/ssim.py`）：每次呼叫在 CPU 建 11x11 窗再 `.cuda()`，5 次 depthwise `conv2d`（x、y、x^2、y^2、xy）＋十幾個逐元素運算。
```
SSIM = mean[ (2 mu_x mu_y + C1)(2 sigma_xy + C2) / ((mu_x^2 + mu_y^2 + C1)(sigma_x^2 + sigma_y^2 + C2)) ]，C1 = 0.01^2、C2 = 0.03^2
```
**10-24 量測**（`scratchpad/fssim_check.py`、lab `scripts/lab/setup_fused_ssim.sh`）：

| | 本機 4050 fwd+bwd | lab 3090 fwd+bwd（卡上有訓練） | SSIM 對 float64 真值 | 梯度對 float64 相對 L2 |
|---|---|---|---|---|
| 現行（2D conv） | 26.1 ms | 14.6 ms | 3.3e-6 | 1.4e-5 |
| 可分離 PyTorch（10-24 新寫） | 27.1 ms | — | 9e-8 | 3.2e-6 |
| fused_ssim | **2.1 ms** | **1.2 ms** | 2.7e-7 | 2.6e-6 |

- 純 PyTorch 的可分離版**不會變快**（depthwise 卷積在 cuDNN 是記憶體頻寬受限，乘加數不是瓶頸）=> Taming 的加速來自融合 kernel，不是可分離本身。可分離版留在檔案裡（數值較準），不接進訓練。
- fused_ssim 比現行**更接近** float64 真值：現行版的 11x11 窗是 float32 外積，誤差反而較大。
- **當年為什麼退回**（config 註解、稽核清單 §5）：08-28 開過，sched30fast 的 SSIM 距三個同組態跑次平均 −4.06 sd。那是 09-13 影像錯位修正之前的年代（分數全部作廢），而且只有一個跑次對三個重複。
  數值上它比現行更準，沒有機制會讓訓練系統性變差 => 重開，用換塊評測定案。
- 預期：3090 上每步省約 5 ms（若無競爭時現行約 6～7 ms），約 −8～10%；6GB 筆電上省更多（26 → 2 ms）。
- **結果（10-24）**：b6 純訓練 1586 → **1380 s（−13.0%）**、b0 1712 → **1501 s（−12.3%）**，每步省 6.9 ms（206 s／30k），比預期的 5 ms 多；
  b6 換塊整張 +0.007（對照 +0.004）、本塊區域 +0.071（+0.057）、幾何區域 +0.164（+0.145）=> 品質不變（甚至略好）。
  b0 換塊整張 −0.021（對照 −0.006）、本塊區域 −0.102（−0.040）、幾何區域 −0.188（−0.042）=> 小輸；val 17.77 vs 17.73 反而略高。
  兩塊方向相反；b0 的同配方重跑差（10-23 量過）整張 0.011／本塊區域 0.041／幾何 0.058 => 整張在噪音內，本塊區域 1.5 倍噪音。

### B1 融合 Adam（Faster-GS 1.12～1.33x）
**我方**（10-19）：光柵器 extension 裡一個 kernel 一遍讀 p／g／m／v、寫 p／m／v，算式與運算順序照 torch 2.0.1 => 與 torch 逐位元相同；optimizer.step 13.5 → 4.6 ms，60k 54 → 45 分。同一做法，無可嫁接。

### B2 Adam 融進 backward（Faster-GS：再 −8%、VRAM −0.4 GB）
**論文**：backward 算完某顆的梯度就直接更新該顆的參數與 m／v，不寫出梯度張量。
**我方**：無。我們的 backward 寫出梯度後還有 Python 端的正則（opacity 熵、scale 正則、dist）加上去，以及 absgrad 累積讀 `viewspace_points.grad` => 不能直接在 backward 裡更新。要嫁接得先把那些正則的梯度也搬進 kernel。延後。
**10-24 實作 SH 那部分（使用者授意）**：SH 沒有任何 Python 端的正則 => 它的梯度在光柵器前處理 backward 裡就是完整的，可以直接更新（佔每顆 59 個 float 的 48 個）。
`backward.cu preprocessShAdamCUDA`（renderer 旗標 `sh_adam_in_backward`，需 `sh_split`＋FusedAdam；FusedAdam 提供 `sh_adam_args()`）：
```
每 block 128 顆：每條執行緒算自己那顆的幾何梯度＋16 個 SH 係數的梯度 -> shared memory
同步後整個 block 依記憶體順序合併更新這 128 顆連續的 p／m／v（更新式＝fusedAdamCUDA<VAR=1> 同一組 intrinsics）
看不到的顆粒梯度 0 照樣更新（稠密 Adam）；sh_rest_interval=k：rest 梯度在 kernel 內累加（acc + g），第 k 步才走 Adam 並歸零
```
- 第一版每顆自己跨步更新 48 個 float（沒合併存取）=> backward +44 ms、一步 +27%；改成 shared memory 轉置後才變快。
- 驗證：驗證模式把 kernel 用的梯度寫出來，用現行 FusedAdam 在更新前的複本上重算 => k=1、4、16 各 9～17 步，p／m／v／累加緩衝／step 計數**全部逐位元相同**。
- 與原流程唯一的差別：densify 那一步（增生期每 150 步）SH 照樣更新（原流程那一步所有參數都不更新）。
- 計時（本機、交替執行）：k=1 一步 −7.2%（optimizer.step 12.8 → 2.2 ms、backward +6 ms）；**疊在 SH16 上 ±0**（SH16 已砍掉 15/16 的高階 SH Adam，剩下的累加成本在 kernel 內外差不多）。
- => 預設關、不進配方（SH16 本身又快又好）。3090 上的比例待 lab 重編後補量。

### B3 稀疏 Adam（Taming、gsplat `SelectiveAdam`）
**論文**：本步不可見的顆粒不更新（m／v 也不衰減）。
**我方**（10-19 `FusedAdam(sparse=true)`）：換塊 PSNR +0.17／+0.13，但幾何 F1 −0.053／−0.063、60k 反而慢 2 分 => 不採用。

### B4 高階 SH 每 16 步才更新（Taming §4.2）／整個優化器每 32～64 步（FastGS 補充 §9.1）
**論文**：Taming：高階 SH（45 個 float，佔 59 個中的 76%）的 Adam 每 16 步才走一次（梯度在中間累積）；Table 2：拿掉它慢最多 50%，但 Truck PSNR 25.39 → 25.20。

**我方**：每步全部參數都 step。融合 Adam 5.4 ms 中高階 SH 約 4.1 ms；梯度累積本身要多讀寫一次（45 x N 個 float，約 1.5 ms）=> **淨省約 2.5 ms／步（5%）**。
**判斷**：收益不大且有已知的品質代價。若要試，先試 FastGS 那個只在收割期（後 50%）降頻的版本。第二輪。
**10-24 實作（純 Python，`FusedAdam.sh_rest_interval`，預設 1＝原行為；`sh_rest_interval_from` 指定從第幾次 step 起）**：
```
n = 第幾次 optimizer.step；n > from 且 n % k != 0  =>  shs_rest 參數群跳過 Adam，而且下一步的 zero_grad 不清它的梯度（autograd 累加）
n % k == 0                                          =>  用累加的 sum_{k 步} g 走一次 Adam（Adam 對梯度尺度近似不變 => 等同 k 步一個大批次）
densify／relocation 換掉 nn.Parameter               =>  梯度歸 None，那段累加作廢
```
CPU 測試（假的 fused kernel，經 LightningOptimizer 包裝）：k=1 與 torch Adam 逐位元相同；k=4 時其他參數群不受影響、shs_rest 只在 n%4==0 動、梯度＝跳過那幾步的和。
第二輪排的是 Taming 原設定（k=16、全程），疊在融合 SSIM＋Morton 上（b6、b0）；掉品質再試只在收割期。
**結果（b6）**：純訓練 1377 → **1214 s（−11.8%）**，換塊本塊區域 +0.062 → **+0.214**、幾何 +0.151 → +0.437 => 不但沒掉、反而變好（與 Taming 在 Truck −0.19 相反）。b0 確認中。

  優化器靠縮小顆粒、壓 opacity 去降它）。當年的 bestres（−14%、換塊 −0.04／−0.09）沒有 dist loss，所以沒碰到。
  「增生期全在低解析度、結構定錯」可能也有份，但不是 b0 崩掉的主因。
- lr 保持比不保持好（−0.25 vs −0.33）而且更快 => 方向保留，與 MCMC 加噪的交互作用在這個範圍是正的。
- **第二輪**：a=2（1/2 到 12.6k，增生期最後 2.4k 已是全解析度；平均像素 0.684，接近當年 bestres 的 0.70）＋lr 保持到 12.6k，疊在融合 SSIM＋Morton 上。
  **再加兩個修正臂（照使用者 10-23 的判準：快很多的要修，不直接丟）**：a=2 與 a=4 各一，**dist 只在全解析度時開**（`metric.dist_regularization_from_iter` = 12600／21300；
  原本 3000）。a=4 若修得回來就是 −18%。代價風險：dist 晚開可能讓幾何（F1、馬路地底）變差 => 勝者要補區塊 F1。
  預期：融合 SSIM 拿掉了一部分隨像素縮放的成本（每步 6.9 ms）=> 那部分剩約 18%，a=2 只省它的 32% => **約 −6%**；
  若仍掉 >0.05 就把解析度線關到「只在 densify 之前」。b0 的 a=4 臂（已在跑）照跑完；b0 的 a=4 不保持臂已從佇列刪除。

### C2 顆數跟著解析度長（DashGaussian Eq. 4、5）
**論文**：
```
P_i = P_init + (P_fin - P_init) / r_i^(2 - i/S)
P_fin^(i) = max( P_fin^(i-1), gamma * P_fin^(i-1) + eta * P_add^(i) )      gamma = 0.98、eta = 1、P_fin^(0) = 5 P_init
```
Table 3：只開顆數排程 −17%；兩者一起 −41%（5.51 → 3.23 分），PSNR 27.92。
**我方**：MCMC `N_{k+1} = min(cap, 1.05 N_k)` 每 150 步一次，直到 densify_until（STEPS/2）；dup init 讓 N_0 一開始就接近 0.9 cap（例：ed10b4 全場景終模 2.25M＝0.9 x 2.5M）。
**判斷**：方向相反——我們刻意前期就給滿顆數（10-02：dup init 是品質來源，`實驗分析/08`）。在低解析度階段，一顆面元常常小於一個像素，顆數多主要是成本。
可嫁接的形式：低解析度期間 cap 跟著像素數縮（例如 `cap_t = cap * max(0.3, 像素比例)`，多出的用 relocation 的同一套抽樣補回）。等 C1 的結果再決定。

### C3 多視角一致的增生／剪枝（FastGS 📄 §4.2、§4.3，CVPR 2026）
**論文**：
```
e^j(u,v) = (1/C') sum_c |r^j_c(u,v) - g^j_c(u,v)|                    M^j = minmax_normalize(e^j)、M^j_mask = 1[M^j > tau]
增生分數  s_d,i = (1/K) sum_{j=1..K} sum_{p in Omega_i} 1[M^j_mask(p) = 1]        Omega_i＝顆粒 i 的螢幕足跡；K = 10 個隨機視角
          s_d,i > tau_d（= 5）且通過梯度條件才 densify（clone 用原版梯度、split 用 AbsGS 絕對梯度）
剪枝分數  s_p,i = normalize( sum_j sum_{p in Omega_i} 1[M^j_mask(p) = 1] * E^j_photo )   E^j_photo = (1-lambda) L1^j + lambda (1 - SSIM^j)
          15k 後每 3k 步：剪 o < 0.1 或 s_p > 0.9
```
Table 7（Mip-NeRF 360，3DGS-accel 基線 7.10 分、2.64M 顆）：＋VCD 3.53 分、0.53M 顆，PSNR 27.46 → 27.69；＋VCP 5.32 分；全部 1.93 分、0.40M 顆。
**我方**（`mcmc_density_controller.py` `add_new_gs`／`relocate_gs`；renderer V/C trim）：
```
母點抽樣  p_i ∝ o_i * (1 + w * G_i / mean(G))，w = 2.0                     G_i＝上次顆數 N 改變以來累積的 AbsGS 絕對梯度 sum |dL/ds|（增生／trim 都會改 N，增生期約每 150 步重來一次）
增生      每 150 步加 min(cap - N, 0.05 N) 顆，複製抽到的母點（Eq. 9 分攤 opacity 與 scale）
回收      o_i <= 0.005 的顆粒搬到依 p_i 抽到的活顆粒上（同 Eq. 9）
剪枝      每 500 步剪 V/C 最低的 10%：V_i = sum_views sum_p T_i(p) alpha_i(p)、C_i = 覆蓋像素數（累加式，從訓練 forward 順便累積）
二元熵    L_ent = lambda * mean_i H(o_i)，H(o) = -o ln o - (1-o) ln(1-o)（ed10b4：1k 起 lambda 0.002 且只推 o<0.5 往 0；10k 起雙向、lambda 0.008）
```
**比較**：
- 訊號：他們數「足跡內高誤差像素」（二值、不加權、K=10 個視角平均）；我們用 AbsGS 的 `sum |dL/ds|`（誤差 x 該顆對像素的權重，增生期約 150 個視角累積）。都是「多視角、足跡內的誤差」，我們的訊號已經包含混合權重（被遮住的像素不算），他們的不包含。
- 加速從哪來：FastGS 的時間減半幾乎全部來自**顆數 −80%**（ADC 原本增生過量）。MCMC 的顆數由 cap 決定，不會爆量 => 這個加速在我們這裡對應的是「把 cap 調低、品質不掉」：
  1M 每塊約 20 分、61 FPS，2.5M 約 29 分、43 FPS，差 0.13 dB（`實驗分析/19`）。
- 剪枝：他們剪「出現在高誤差區域的顆粒」（s_p 高），我們剪「每像素平均貢獻低的顆粒」（V/C 低）。方向不同：他們的假設是高誤差區的顆粒沒在幫忙；我們的是貢獻小的不值它的成本。
**嫁接**：
1. 把 FastGS 的「門檻」用在 MCMC：只有 `s_d > tau_d` 的顆粒才能當母點（現在是全部活顆粒依權重抽）=> 新增的顆粒集中在多個視角都錯的地方。需要逐顆「足跡內高誤差像素數」，最便宜的拿法是累加式 V/C 那條 record 路徑多帶一張逐像素遮罩（改 CUDA）。
2. 只在 cap 1M 測（目標是追 2.5M），對照現行 1M。研究線，延後。

### C5 逐視角可見性剔除（Mini-Splatting2 🔍）
**論文**：在某個步數為每個訓練視角記下可見的顆粒集合，之後該視角只處理這個集合（4:04 → 3:34）。
**我方**：視錐剔除＋`EXACT_SUPPORT`（o<=1/255 不進 binning）＋forward 在 T<1e-4 停＋backward 飽和跳過。沒做的是「被遮擋的顆粒不進 preprocess 與排序」。
**判斷**：preprocess＋排序在我們的 forward（13 ms）裡佔多少還沒拆；被遮擋的顆粒多在高樓後方。延後到 forward 拆解之後。
**論文細節（10-24 讀原文）**：V_i^k = 1[ sum_j w_ij^k > tau ]（tau 取 0.99 分位）；500～13K 步之間用、與 critical Gaussian 一起更新；非可見的在 preprocessCUDA 就排除；
不是無損（快取會過期）；戶外場景峰值記憶體變高（要存逐視角遮罩）。
**10-24 量（使用者授意直接做，先量上限）**：本機 b6、12 視角：進了 binning（radii>0）平均 10.2%、真的有貢獻 8.9% => 能剔的只有全部的 1.3%（可見的 1/8）；
前處理＋排序一共約 2 ms／93 ms（光柵器分段計時）=> **上限約一步 0.3%**，而逐視角快取要 2.25M x 775 bit ≈ 218 MB。**不做**。

### C6 前期大量增生（Mini-Splatting2）
我方 dup init 是同類（一開始就把 SfM 點複製 K 份到接近 0.9 cap）。無可嫁接。
**論文細節（10-24 讀原文 🔍 arXiv 2411.12788）**：沒有用單目深度。
```
深度重新初始化（Sec. 3, Eq. 2）：d(x) = d^mid_{i_max}(x)，i_max = argmax_i w_i（射線上權重最大那顆的中位深度）；把各訓練視角的深度圖反投影回世界座標，
                                 2K 步時做一次，取樣點數＝當下的顆數
激進複製（Sec. 4）：critical＝在像素上給出最大權重的顆粒（再以 0.99 分位過濾，每次約 30% 顆，傳統逐步增生 <= 5%）；500 步起每 250 步，每顆複製成 2 份
                    alpha_new = 1 - sqrt(1 - alpha_old)、Sigma_new = alpha_old^2 (2 alpha_new - alpha_new^2/sqrt 2)^(-2) Sigma_old
增生只到 3K、總共 18K 步；增生期關 SH、前期 0.5 倍解析度
```
- 與我方：alpha_new 的式子就是 MCMC relocation Eq. 9 在 n=2 的情形；critical（最大權重者）對應我們用 opacity x absgrad 抽母點（訊號不同）。
- 可嫁接：「從渲染深度重新撒點」（自洽的表面，不受單目深度誤差影響）取代 dup 的等向擾動複本——未測。

### C7 dist 每 k 步（10-24 量測後新增；我方自己的槓桿，不是論文手段）
本機（4050、b6 1.29M 顆、現行配方＋SH16）光柵器分段計時：
```
                 render forward   render backward   一步
dist 關           20.5 ms          26.5 ms           77.1 ms
```

- **第三輪（已排）**：`fssh16rd2h`＝融合 SSIM＋SH16＋a=2（b6、b0）—— 看 SH16 的 +0.15 能否抵掉 a=2 的 −0.19，若持平則合計約 −28%。

勝者組合定案後：全場景重訓一次（拿最終配方的 741 幀與總時間；ed10b4 全場景 7.32 h 是對照）。
