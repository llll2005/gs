## §1 命題與硬約束

**目標**：消費級 6GB 筆電（RTX 4050 Laptop / 46GB RAM）上的 city-scale 2DGS 重建，
品質對得上 CityGaussianV2。

**論文命題 —— 成本感知密度控制**：現有密度控制用**顆數**計價（`cap_max`、opacity L1、scale L1），
盲於「這顆粒子實際上要花多少錢渲染」。我方改用**渲染成本**計價並解資源約束問題：

```
max Q(θ_S)   s.t.   (1/K) · Σ_{i∈S} c_i  ≤  B(hardware)

c_i = 螢幕 tile 足跡（VRAM-grounded）    λ = 影子價格    K = 條帶數（供給側槓桿）
```

## §3 理論：成本感知密度控制

### 3.1 統一形式（背包問題）

密度控制 ＝ `max Q(θ_S) s.t. (1/K)Σ c_i ≤ B`。
既有方法差別只在**價值訊號 `v_i`**（梯度／貢獻／opacity），**`c_i` 幾乎都是 1**。

**⛔ 但「所有既有方法都是 `c_i ≡ 1`」這句話不成立，必須改寫**——RAIN-GS 的
`s = HW/(9πN)` 就是「每顆的螢幕預算」。精確的區別：

| | RAIN-GS | 我方 |
|---|---|---|
| `c_i` 角色 | 由粗到細的**優化排程下界** | 逐顆的**實際成本** |
| 逐顆差異 | **無**，每顆同一個 `s` | 有 |
| 綁在什麼上 | 顆數 `N`（自我調節） | **硬體 VRAM 預算 `B`** |
| 解的問題 | 學習頻率順序 | 資源約束最佳化 |

**⛔ 第二個反例（2026-08-29 讀 `參考論文/taming_3dgs.pdf` 原文查出，比 RAIN-GS 更貼身）：
Taming 3DGS 的 densify score 裡就有逐顆的 `c`。**

原文 Eq.4 的 `F(∇g, c^i_g, 1^i_g, D^i_g, S^i_v, B^i_g, z^i_g, o_g, s_g)`，其中
`c^i_g` 明文定義為「the number of pixels covered by g in view i」——就是我們的 `c_i`。

| | Taming 3DGS | 我方 |
|---|---|---|
| `c` 的符號 | **+0.1（正）** ⇒ 大足跡**更該**被 densify | **除**（負）⇒ 大足跡**少**被 densify |
| 給的理由 | "large projections ... lead to a **blurry** appearance" | 大足跡吃 VRAM |
| 在 score 裡的份量 | 0.1 vs `∇g` 的 50、`D^i_g` 的 50 ⇒ **約 0.2%，近乎 no-op** | 主項 |
| `c` 的角色 | **偵測器**（哪些顆會造成模糊） | **價格**（綁 `(1/K)Σc_i ≤ B`）|

⚠ **兩件事必須誠實**：
1. 「既有方法 `c_i ≡ 1`」**要再收窄**。存活的區別是「`c` 當**偵測器** vs 當**價格**」，
   而**不是**「有沒有用 `c`」。RAIN-GS（全域排程下界）＋ Taming（逐顆偵測器）已佔掉後者。
2. **符號是相反的，而 Taming 那一側有敘述性理由而我方沒有實測**。
   ⇒ `cost_aware_densify` 的**負值路徑已開放**（`mcmc_density_controller.py`，原本 `>0`
   會靜默忽略負值），兩個方向都要量。⚠ 但 Taming 的 0.2% 權重代表**他們也沒真的檢驗過**
   ——不可拿他們的敘述當成「已知答案」，這正是 `paper_audit` 一再抓到的形狀。
   ★ 直接相關：使用者目視的第一抱怨就是**糊**，而 Taming 說糊＝大足跡造成。

⇒ 貢獻表述為「**把螢幕足跡從偵測器與優化排程提升為硬體預算下的逐顆價格**」。

**三個誠實邊界**：背包涵蓋不了「長」（成長需要不存在之點的邊際價值）／價值不可加
（alpha-blending 次模）／預算非靜態。

### 3.1.1 ★修正（2026-08-06）：這不是背包，是**帶預算的覆蓋問題**

上面那個式子把品質當目標、成本當約束，然後自然導出「按 value-per-cost 排序再切」。
**五條剪枝曲線的實測說那個導出是錯的**（見 §5.2.5）：贏的 `count` 幾乎就是 `c_i` 本身，
按它遞減保留 ＝ **保留最貴的**，與 v/c 完全相反。

正確的結構是**覆蓋為硬下限**：

```
max Q(θ_S)   s.t.   (1/K)·Σ_{i∈S} c_i ≤ B        （預算）
                    coverage(S) 完整               （下限，不可交易）
```

「在所有能蓋滿場景的子集裡，挑成本最低／品質最高的」——
**便宜與覆蓋完整不衝突，覆蓋是底線，成本是在底線之上才開始比的東西。**

**為什麼這個表述更強**

| 觀察 | 舊表述（純背包） | 新表述（覆蓋為約束） |
|---|---|---|
| `count`（≈ `c_i`）贏 | 矛盾：怎麼會保留最貴的？ | 它意外地在最佳化覆蓋 ✓ |
| v/c 剪枝「訓練側淨負」 | 只能記成負結果 | 它踩破了覆蓋下限 ✓ |
| `max` 居中 | 無解釋 | 保護「唯一蓋到某處」的粒子，部分維持覆蓋 ✓ |
| `sum` PSNR 高但紋理崩 | 無解釋 | 用少數大顆蓋滿＝覆蓋達標但解析度不足 ✓ |

**且它接上早已量到卻沒用起來的次模性**：`dim_returns_b12_reg000_FULL` 實測
「二階差分 contribution 8/8、random 7/8 全為正 ⇒ 邊際遞減」。
**集合覆蓋是次模最佳化的典型問題**，所以那個量測現在有了歸宿——
次模函數在背包約束下的貪婪／CELF 有近似保證，而「價值可加」的 LP 論證沒有。

⚠ **待改寫**：`archive/現行方案與公式.md` §8「v/c 門檻是 LP 最優解，不是啟發式」
建立在**價值可加**上。覆蓋顯然不可加（第二顆蓋同一塊的邊際價值近零，第一顆蓋空白的極高）
⇒ **那一節的論證不成立，需重寫為次模＋覆蓋約束。**

⚠ 全部證據來自**事後剪枝**（單一模型、兩種判官、五個工作點）。
訓練中的密度控制是否適用同一結構，未驗。

### 3.3 密度排程的破平衡公式（✅ 4/5 命中）

```
break-even interval = contribution_prune_interval × ln(1.05) / (−ln(1 − prune_ratio))
                    = 500 × 0.04879 / 0.10536 = 231.5
```

| 跑次 | interval | 預測 | 實際 |
|---|---|---|---|
| v1 (24k) | 350 | 衰減 | ✓ 1.21M → 77.6k |
| reg000_exact | 150 | 成長 | ✓ 撞 cap 2M |
| oreg_0p002 | 150 | 成長 | ✓ 撞 cap 1M |
| v3 | 100 | 成長 | ✓ 338k → 611k |
| v2 | 350 (+prune 0.05/850) | 成長 | ✗ 實際衰減（opacity 被壓垮的 confound）|

**⛔ `cap_max` 不可設在低於現有顆數**：`add_new_gs` 是 `num_gs = max(0, min(cap,1.05N) − N)`，
N 一碰 cap ⇒ `num_gs = 0` ⇒ **densify 永久關閉**，但 relocation 與 trim 照跑
＝**只剩破壞沒有建設**。

### 5.2.5 ★貢獻度判準的定案（2026-08-06，兩種判官、五個工作點）

事後剪枝 `oreg_0p002_b12`（900k），建築區紋理比：

```
             ── 訓練視角 ──          ── 官方 held-out ──
保留顆數    max   topk  frustum      max   topk  frustum
640,000    .368  .367   .367        .255  .254   .254
480,000    .357  .351   .351        .248  .245   .245
320,000    .339  .328   .329        .234  .228   .228
160,000    .303  .279   .284        .211  .197   .200
 80,000    .266  .236   .243        .188  .169   .176
```

**`max` 在兩種判官、五個工作點上全勝。** ⇒ `contribution_accumulator` 預設 `reduce="max"`。

**解釋**：max 保護的是**覆蓋**。一顆粒子在單一視角關鍵，是因為那裡沒有別人蓋到那塊；
刪掉就是一個洞，而那個洞在鄰近的 held-out 視角**一樣是洞**。
⇒ 「不要製造洞」勝過「偏好多視角一致的粒子」。

**兩個被否證的假說（都是我方自己提的）**：
- ❌「固定 top-K 輸是因為分塊邊緣被 0 稀釋」→ frustum-aware K 只回收 **20%** 的落差
  （合成案例上分離 3.6× 完美，真實資料上不是主因）
- ❌「max 適合重建、top-K 適合泛化，我們只量重建」→ **held-out 上排序完全不變**

⚠ held-out 樣本小（30 幀落在 b12 內、取 8 張），但五個等級兩種判官一致。
⚠ 全部量在**已完成模型的事後剪枝**上；訓練中 trim 反覆觸發，動力學未分離。

### ★★ 第四、五種判準：MVGSR 的尺寸感知（2026-08-06 晚間實測）

MVGSR §4.2 Eq.5 `C_MV = Σ_視角 Σ_像素 [T·alpha > δ]` 需要逐像素值，我方 CUDA 只回傳
平均與像素數 ⇒ 用兩個可算的極限代替：
`count` = Σ 覆蓋像素數（δ→0）　`sum` = Σ(每像素平均 × 覆蓋像素數)（總 T·alpha）

```
保留 80,000 顆（8.9%）的建築紋理比
                訓練視角      held-out
count            0.316         0.222     ← ★兩種判官都壓倒性最好
max              0.266         0.188
frustum_topk     0.243         0.176
topk_mean        0.236         0.169
sum              0.218         0.154

交叉點約在 320k：640k 時 max 略勝（.368/.255 vs .362/.250）
```

**`count` ＝ 尺寸 × 被幾個視角看到 ＝「總螢幕存在感」**，不看貢獻強度。
**為什麼贏**：紋理比是渲染梯度 ÷ GT 梯度，**空白區梯度為零會把比值拉下來**。
`count` 保證畫面被蓋滿；`max` 保留「某處峰值高」的粒子，那些可能擠在同一區。

**⚠ 與本命題的張力（必須處理）**：`count` 幾乎就是我方的 `c_i`（螢幕足跡）。
按 `count` 遞減保留 ＝ **保留最貴的粒子** ⇒「按 value-per-cost 剪枝（保留便宜的）」方向相反。
這給了 `v/c 判準「訓練側淨負」`（早已記錄）一個機制解釋：**便宜的粒子小，剪掉會讓畫面出洞，
而洞比什麼都傷**。命題本身（用成本當**預算約束**）不受影響，但
**§3.1 的「v/c 門檻是 LP 最優解」需要重新檢視——LP 假設價值可加，而覆蓋顯然不可加。**

⚠ 全部量在事後剪枝上，單一模型。`sum` 的 PSNR 反而最高（80k：16.65 vs max 15.47）
＝面積加權保留少數大顆粒，平均顏色對但細節全無 ⇒ **反過來驗證紋理比是對的尺**。

🧪 **原始 Eq.5 仍未測**：MVGSR（arXiv 2503.08093）§4.2 Eq.5
`C_MV(p) = Σ_視角 Σ_像素 [T·alpha > δ]`——**計數**而非平均或最大，且**逐像素**（隱含尺寸，
與我方的「每像素平均」相反）。

### 6.2 depth-init 的真實 input（2026-08-06 追碼）

```
utils/depth_init_blocks.py
  :79   read_model(sparse_dir)            ← COLMAP 姿態
  :82   estimated_depth_scales.json       ← 每張影像的 (scale, offset)
  :312  estimated_depths/*.npy            ← Depth Anything V2 逆深度
  ⇒ 直接幾何構造，【完全沒有訓練】
```

而 `utils/get_depth_scales.py` 是**用該影像可見的 COLMAP 點**擬合 scale/offset：
```
scale = s_colmap / s_mono ,  offset = t_colmap − t_mono·scale     （每張影像 2 個自由度）
```

⇒ **depth-init 不是「不用 SfM」，是「用 SfM 校準單目深度」。**
⇒ **8.6% 的誤差是 DA2 的形狀誤差，2 個自由度改不掉** ⇒ 這條線上沒有便宜的改進空間。
⇒ 也解釋了為什麼體素質心融合完全沒改善：形狀誤差是同一個網路的**系統性偏差**，
不同影像犯**相關**的錯，平均不會消掉。

**對照 coarse**：`points_from: sfm` ⇒ SfM 點**直接當粒子位置** + 30k 步光度訓練。
差的那一步是「用影像訓練」，不是密度。

#### ★ 缺陷 1 的含意：它動搖了一個反覆引用的結論

`sep_depth_trim_2dgs_renderer` 的版本把 `top_list[0] = trans` 寫在**位移迴圈裡面**：

```
[a, b, c] + 破紀錄的 r
  i=0: top[2]=top[1]→b ; top[0]=r   → [r, b, b]
  i=1: top[1]=top[0]→r ; top[0]=r   → [r, r, b]
```

舊的最大值被丟掉、新紀錄佔 K−1 個槽 ⇒ 穩態 `(2·max + prev)/K` ≈ **執行中的最大值**，
而且**與相機順序有關**，第一台相機的值被複製 K 份。

本檔 §5.3 與 `measure_view_consistency.py` 反覆主張：
> floater 不是貢獻度低，是貢獻度**集中**——它被放去解釋少數視角，而它確實解釋了那些視角。

**那個推理的前提是「trim 用的是跨視角統計量」。實作實際上按「最佳單一視角」排序**
——最寬容的判準，**只在單一視角尖峰的 floater 剛好拿高分而存活**。
⇒ **「剪枝盲於幾何」有一部分可能不是判準的哲學問題，是這個實作缺陷；
真正的 top-K 平均從來沒被測試過。**

⚠ **這是機制變更不是純 bugfix**：剪枝行為改變 ⇒ **修正後的跑次與既有結果不可直接比**。
⚠ `tools/prune_curve.py` 先前那兩條曲線用的排序也是壞的（**第三種錯法**：單一值填滿所有 K 槽），
數字要重跑。

### 9.2 ⛔ `screen_size_prune_px`：我先說它是死參數，實測後發現是**兩個半徑來源不相容**

**⛔ 2026-08-21 的原始說法「它從未執行過、是死參數」是錯的，2026-08-22 實測推翻。**

真相有兩層：

**① 它一直有在跑，只是從來沒抓到東西。** `_update_max_radii`（`:648`）在
`screen_size_prune_px > 0` 時每步被呼叫（`:283-285`），從**光柵器的 `radii`** 累積跨視角
running max。log 裡 0 則訊息不是「沒跑」，是**光柵器半徑從來沒超過 300px**。
（我當時只看到 `:298` 那個賦值就下結論，漏了 `:656-657`。）

**② 打開 `screen_prune_emergency_px` 會把半徑來源整個換掉 —— 而且是災難性的。**
`:296-299` 每步用 `projected_radius()` **覆寫**同一個 buffer。那是**解析上界**，
其 docstring 明說「對每一個點都有定義，可見與否都算……相機後方的點是 clamp 不是歸零」。
實測同一批粒子的解析半徑：

```
b7   中位 77.7px   >300px 佔 25.16%   >600px 佔 18.17%
b12  中位 20.2px   >300px 佔  6.53%   >600px 佔  4.18%
```
⇒ 打開 emergency 後，`screen_size_prune_px 300` 變成**每次 densify 刪掉 25% 的族群**
（大多是相機後方、光柵器根本沒畫的點）。

**實測後果（`scrprune_b7` = `sched30_b7` + `emergency 600`）：**

| | PSNR | 顆數 | it/s | 剪枝訊息 |
|---|---|---|---|---|
| `sched30_b7` | **24.993** | 2.34M | 2.34 | 0 則 |
| `scrprune_b7` | **13.498** | 2.06M | 4.40 | **20,129 則** |

**PSNR 崩掉 11.5 dB。** 跑得快（4.40 it/s）只是因為它一直在刪點。

⇒ **`:229` 那句「Set this ABOVE the normal screen_size_prune_px (e.g. prune=300, emergency=600)」
是有害的建議**：兩個旗標讀同一個 buffer，但 emergency 會把 buffer 的**語意**從
「光柵器實際半徑」換成「解析上界」，300 這個門檻在後者底下完全不是同一件事。
⇒ **要用 emergency，必須給它自己的 buffer，或把門檻按解析半徑重新標定**（>600px 佔 18%，
所以 600 也不安全；要抓「真正的怪物」大概要 5,000px 以上，見上表的 p99）。
⇒ 疊影那條線因此**沒有被測試到** —— 這一臂測的是「錯誤配置會不會崩」，答案是會。

## §11.2 ★★★★★ 找到尾巴的機制：起始 trim 在 step 1 鎖死了錯的前層（2026-08-22）

`sfminit` 的副產物指出 depth-init 的 121 萬顆有 87 萬在 step 1 被砍。原本以為那是
「砍掉看不見的點」（block PLY 的範圍大於 block 相機看得到的）。**實測推翻：**

```
depth_init PLY（b12）           1,211,537 顆
完全在所有 284 台訓練相機視錐外        157 顆 = **0.01%**
起始 trim 實際砍掉                 873,504 顆 = **72.1%**
```

**只有 157 顆是真的看不到。被砍的 87 萬顆全部在視錐內、幾何上看得見。**

### 機制

`sep_depth_trim_2dgs_renderer.py:212-238`，step 1，遍歷全部訓練相機：
```
contribution = sum over cameras of (T * alpha)      # transmittance 加權
tile = quantile(contribution, start_prune_ratio=0.0)   # 只砍貢獻度等於最小值的
prune_mask = contribution <= tile
```
而 `utils/depth_init_blocks.py` 給**每一顆**都設 **opacity = 0.99**（實測 PLY 的 opacity
欄位只有一個唯一值），加上那層殼比表面厚 20 倍（§7.1）：

```
單層之後殘餘 transmittance = 1 − 0.99 = 0.01
五層之後                    = 1.0e-10      -> 貢獻度在 float32 下就是 0
```

⇒ **前層吸光所有 transmittance ⇒ 後面 72% 的點貢獻度歸零 ⇒ 被砍，其中包含正確的表面。**
⇒ **錯的前層在任何最佳化之前就被鎖死。**

### 這解釋了三件先前對不起來的事

1. **尾巴為什麼「從頭就爛」**（§12.36：45,000 步只改善 4.5%）—— 決定在 step 1 就做完了。
2. **為什麼五種旋鈕全距只有 0.08 dB**（§2.3）—— 它們全都在 step 1 之後才作用。
3. **為什麼換 SfM-init 只動了 +0.15**（§11）—— SfM 點沒有殼、沒有前層問題，
   所以它繞過了這個機制；但它太稀疏（32 萬），換來的只有 10%。

### 已排的兩臂

- **`task_op05.sh`（攻根因）**：init opacity 0.99 → **0.5**（`tools/reopacity_ply.py`，
  **只改 opacity**，位置/尺度/法向/顏色完全不動）。五層深處 transmittance
  1.0e-10 → 3.1e-2 ⇒ 後層拿得到梯度，最佳化才有機會自己選出正確那層。
- **`task_notrim.sh`（歸因對照）**：只關掉 step 1 那一刀（`diable_start_trimming true`），
  opacity 維持 0.99。**預期偏中性**——即使不砍，被遮住的點仍拿不到梯度，只是改由
  opacity_reg 慢慢殺。**那個中性本身就是資訊**（把矛頭指向遮擋而非刪除）。

判讀：**最差 10%** 明顯上升 ⇒ 機制證實；只有平均動 ⇒ 鎖死的不是尾巴成因；
全面變差 ⇒ 那層殼是必要的、trim 砍對了。**必須看圖。**

## §11.9 ★★★ 讀 RTG-SLAM 原文：它的解法和我猜的相反（2026-08-24）

⛔ **我先前說「RTG-SLAM 論文不在 `參考論文/`」是錯的。** 它在，檔名是 ACM DOI
`3641519.3657455.pdf`，我的檔名 grep（`rtg|slam`）抓不到，而記憶
`reference_papers.md` 的對照表其實有記。**下次找論文要查對照表，不要只 grep 檔名。**

### RTG 的實際設計（§3.1, §3.2，已逐句核對）

1. **opacity 是二元的，而且完全不最佳化**
   > "we force each Gaussian to be either opaque or nearly transparent"
   > "determined **once after being added** to be opaque (α = 0.99) for fitting the 3D surface,
   > or to be nearly transparent (α = 0.1) for fitting the residual color"
   > "**The opacity learning rate lr_α is set to 0 to fix opacity**"

2. **深度不用 alpha-blend，取「第一個 α > δ_α 的不透明橢圓盤」的射線交點**（Eq. 4-5）
   Fig. 3 明說 alpha-blend 的深度會從高斯中心往外衰減、無法代表局部平面。

3. **★ 錯誤的處理方式：不是解鎖，是「加一顆透明的在前面修顏色」**
   > 對 `M_c`（幾何正確但顏色明顯有誤的像素）：查它對應的高斯的 confidence，
   > "**If unstable... we do not add a new Gaussian. Otherwise, we add a transparent (α = 0.1)
   > Gaussian to correct color errors together with the stable Gaussian.**"
   > "such Gaussians with low opacity do not cause a significant attenuation of light energy,
   > and the color impact to other views is little... during depth rendering, they are
   > automatically filtered out by δ_α"

4. **幾何錯誤靠深度誤差偵測**：`M_s` 包含 `|D̂(u) − D(u)| > δ_d`（δ_d = 0.1 m）
   ⇒ 深度重建誤差大 ⇒ 在那裡加**不透明**高斯。

### ⇒ 對我方的三個含意

**① 我的 `err_unlock` 不是 RTG 的機制，是我自己發明的。**
RTG **永遠不會解鎖已承諾的 opacity**——它的 opacity 根本沒有梯度（lr=0）。
（`rtg_stable_density_controller.py` 的 B4 是「stable→unstable 的**狀態**回退」，
控制的是「這顆還要不要繼續被最佳化」，不是把 opacity 壓低。我把兩者混為一談了。）
⇒ 實驗照跑（它是獨立的假說），但**不可宣稱是「RTG 的解法」**。

**② RTG 對「承諾錯了」的答案是「加一顆透明的在前面修」**，理由是低 opacity 不會顯著衰減光能、
對其他視角影響小、且會被深度渲染自動濾掉。
⇒ 這對我方是**可移植的新機制**，而且與我方觀察相符：§11.7 量到**好視角是靠大量半透明粒子
（<0.1 佔 47~49%）平滑混合做出來的**，壞視角反而高不透明多（>0.9 佔 18~23%）。
**RTG 的設計正好解釋了為什麼「半透明多」是好事。**

**③ 但 RTG 偵測幾何錯誤靠的是深度誤差，而我方最佳配方把 depth loss 關掉了**
（`depth_loss_weight.init: 0.0`）。⚠ 我們是在 §12.6 關掉它的，**而那是用舊的、汙染的
scales 量的**（§11.6 才修好，scale 中位變 11%）⇒ **depth loss 值得用修正後的 scales 重測，
判準看尾巴**（先前只看了平均與建築區）。

⚠ **RTG 用 RGB-D 感測器的公制深度，我方用單目估計（8.6% 誤差）**——
機制可以搬，精度不會跟著搬（記憶 `init_is_root_cause` 早就標註過這點）。

### 時間預算的實測拆解（b12, 2.34M）

```
每步 0.478 s，其中與顆數無關的固定成本 0.184 s = 38%（資料載入 + 全解析度損失含 SSIM）
60,000 步 = 8.0 小時，其中固定成本 3.1 小時
```

| 做法 | 省時間 | 狀態 |
|---|---|---|
| 早停 45k / 34k | 24% / 43% | ⛔ 見上表 |
| cap 2.6M → 1.3M | 23%（實測 7.4h vs 9.6h） | ⚠ PSNR −0.541，換了 regime，不可比 |
| 訓練視角減半 | ~50% | ⛔ 改變問題本身 |
| **前 30k 用 1/2 解析度** | **15~23%** | ✅ **未測**；像素數 1/4，只吃得到固定成本那 38%；⚠ 要同步縮放像素單位的閾值（`screen_size_prune_px` 線性、`blur_split_threshold` 平方） |
| **★ 尾巴專用實驗只跑 20k** | **67%** | ✅ 尾巴在 15k 就定了（sched30 實測 15k→60k 只改善 4.5%，平均改善 39%）⚠ **n=1，驗證已排** |

### ⛔ 我提的「尾巴專用實驗只跑 20k」被使用者當場否決 —— 那是循環論證

我原本提議：尾巴在 15k 就定了（sched30 實測 15k→60k 只改善 4.5%），
所以尾巴專用實驗只跑 20k，4 臂省 27 小時。

**使用者：「針對低分少跑根本不能用，我們最終還是要解決這個，而且當前的實驗就是針對此，
你讓他少跑我們還實驗啥。」**

**他是對的，而且問題比「不划算」更根本：這是循環論證。**
「尾巴不會動」是在**沒有任何介入的基線**上量的。而 `errunlock`／`tcorr`／`depthre`
**正是為了改變尾巴的動態而設計的** —— 若某個機制的作用是讓模型有機會脫離局部極小，
那個脫離很可能就需要完整的 60k（甚至更久）。
⇒ **用基線的「尾巴不動」去論證「不必給介入時間動它」，會系統性地偏向否定正在測的假說。**
⇒ 提案撤回，驗證任務也從佇列移除。

### ⇒ 結論：這裡沒有免費的午餐

| 做法 | 為什麼不是免費的 |
|---|---|
| 截斷 | 偏移 std 是噪音底的 10~20 倍；且對「需要時間發酵」的機制系統性不利 |
| 降 cap | 換了 regime（PSNR −0.541），結論不可轉移 |
| 減少視角 | 改變問題本身 |
| 漸進解析度 | **它本身就是一個介入**（會改變最佳化路徑），不是中性的加速 |

**⇒ 每一種「加速」不是換了 regime、就是改變了動態、就是偏向否定要測的東西。**
真正能省時間的只有一件事：**問更少、更準的問題** —— 那是研究紀律的答案，不是工程的答案。

⚠ 唯一仍然成立的實用結論：**排名 ρ 高不等於能選出贏家**（34k 之後 ρ=0.92~0.94，
但前三名從來沒對過，因為贏家之間只差 0.19 dB）。這條要記住，別再用 ρ 當「可以早停」的依據。

## §11.16 論文：AbsGS 與 StopThePop 實讀（2026-08-25）

**AbsGS**（§3.1-3.2 有證明）：`∂L_j/∂μ_i,x` 的正負由三項相乘決定，第三項是 `(μ_i,x − p̂_j)`
=> 大高斯中心左右兩側的像素推向**相反方向** => `g_i = Σ_j ∂L_j/∂μ_i,x` 很小即使總誤差很大
=> 過度重建的大高斯**永遠達不到分裂門檻**。Fig 4：3DGS 選 69,269 顆、AbsGS 選 16,448 顆，
選的是完全不同的一批。⚠ **修法我方套不上**（MCMC 按 opacity 取樣，沒有梯度門檻），
能拿的是**診斷**：MCMC 的 opacity 取樣同樣看不見足跡，甚至更盲。

**StopThePop**：已確認我方光柵器排序鍵 = `tile ID | 中心深度`（`rasterizer_impl.cu:102-104`），
逐高斯常數，與 3DGS 相同。原文 Fig 4：用正確逐像素排序渲染訓練好的 3DGS 會冒出霧團
=> 優化器在**利用錯排序**。⚠ 但我方是 val ⊂ train，這個作弊對我方分數是**有利**的。
且 §11.15 量到壞視角視差沒偏高 => 此線暫無支持。
（2026-07-28 只讀了 §3.4 的 tile 剔除 = 現在的 `EXACT_SUPPORT`，排序這半今天才讀。）

（鐵律：大實驗前先用 <1h 小實驗驗前提。三個看起來嚴謹的檢查繞過了唯一重要的那個。）

**實測**：`px_noprior_b12`（s=0.2, densify 30 / trim 100）族群在 step 3,000 見頂 872k 後
**下跌 20.3%**、成長率翻負，永遠到不了 2.6M cap ⇒ 跑在錯的 regime，作廢。
成長率只有理論值的 58%（全長跑次是 98%，與破平衡公式吻合）。

```

trim 500（完全不縮）  step 1,380 就衝到 2.38M，然後 OOM
```

**機制（假說，診斷實驗進行中）**：`sep_depth_trim_2dgs_renderer.py`
`prune_mask = (contribution <= quantile(contribution, prune_ratio))` 用 **`<=`**，
所以只要零貢獻粒子超過 `prune_ratio`，這一刀就把它們**全部**剪掉，遠超名目 10%。
零貢獻來自 `EXACT_SUPPORT`（opacity ≤ 1/255 不進 binning）；MCMC relocation 的子代
opacity 很低，需要若干步爬過門檻，而壓縮把「出生到首次 trim」從 250 步壓到 **50 步**。
⚠ **影響超出 proxy**：破平衡公式假設每次 trim 剛好 −10%，若剪除率是**狀態相依**的，
那條公式（紀錄稱「4/5 命中」）漏掉的那次很可能就是這個，且「交付 = 0.9×cap」也要重驗。

**★ 一般性結論：排程有三個獨立的時間尺度，時間壓縮不可能同時保住**

```
                        成長率   出生到trim   densify事件  trim事件
全長基準                  ✓        250 步         273        82
ci=100（等比例）          ✓         50 步  ⛔     273        82   <- 超剪，已實測失敗
ci=500（ci 不縮, di=62）  ✓        250 步  ✓      132  ⛔     16  ⛔
```
⇒ **純時間壓縮做不出忠實的篩子。** 剩下的省時方向只有「去掉計算浪費」（無失真）
與「接受少做實驗」。降解析度會刪掉高頻＝我方病灶；降顆數只值 28%（見下）。

**附帶發現：慢 ramp 是 VRAM 的保命機制。** `probe_t500` 在 step 1,380 撞 2.38M 就 OOM，
而全長跑次在 2.34M 只用 5.57G。差別是**粒子還沒被優化縮小** —— VRAM 由足跡驅動，
足跡隨優化步數衰減。⇒ 「先瘋狂分裂到 cap 再只刪只搬」（§11.13 使用者提案）
**會直接 OOM**，除非同時壓低初始尺度。這正是成本感知命題本身。

## §11.22 ★★★ AbsGS 移植：2DGS 的 viewspace 梯度不是 3DGS 的對應物（2026-08-25）

使用者提問：「MCMC 沒有梯度機制，能不能造偽梯度來用 AbsGS，甚至優化它？」

**查碼查出來的實情（三層，每層都推翻上一層的直覺）：**

1. **我方其實有梯度**（`gaussian_splatting.py:484` 就在讀 `viewspace_points.grad`）。
   MCMC 缺的只是「拿梯度當 densify 門檻」。
2. ⛔ **但那個梯度對 2DGS 幾乎沒用**：`dL_dmean2D` 在 `backward.cu` **全檔只有兩處被寫
   （440/441），且都在 `rho3d > rho2d` 的 else 分支**。那是 2DGS 低通濾波的
   **次像素 fallback** 路徑；解析良好的粒子走 `if` 分支，`dL_dmean2D` 對它們**恆為 0**。
   ⇒ **任何把 3DGS 梯度式 densify 天真移植到 2DGS 的做法，只會看到次像素 splat。**
3. 2DGS 真正的對應物是 **`dL_ds`**（backward.cu:407）＝「loss 想把 ray-splat 交點移到
   splat 上的別處」，與 AbsGS 微分的是同一個物件、只是用 splat 局部座標表示，
   且**同樣會抵消**（中心兩側像素的 `s` 反號）。但它立刻被轉成 dL_dTu/Tv/Tw 埋進
   9 個 transMat 分量、與旋轉/尺度梯度混在一起 ⇒ 逐顆的位置訊號現在無處可取。

**已實作（純新增、零刪除，已用 `git diff | awk '/^-[^-]/'` 稽核）：**
```
auxiliary.h   #define ABSGRAD 1          （可設 0 量它的速度代價）
backward.cu   ray-splat 分支 atomicAdd(|dL_ds.x|+|dL_ds.y|) -> dL_dmean2D.z
              ⇒ `.z` 全檔從未被讀（梯度鏈只用 .x/.y，見 629-632）
              ⇒ **渲染與梯度逐位元不變**，不需新 buffer、不改 API
density ctrl  `absgrad_report`（預設 0，只讀）
```
⚠ 代價：逐像素內層迴圈多一次 atomicAdd，backward 可能慢數 % ⇒ 旗標可關。
⚠ 刻意**只**在 ray-splat 分支累加：else 分支的梯度是螢幕座標、單位不同，混在同一個
   累加器會讓排序失去意義。

**判準（`scripts/task_absgrad.sh`，diagnosis-first）**：本任務**不問**「碰撞存不存在」，
只問決策相關的那個問題 —— **這個訊號排的名次跟 MCMC 現行的 `probs = opacity`
有沒有實質差別？** top-10% 若幾乎重疊、rho 接近 1 ⇒ 換訊號不會換掉增生位置 ⇒ 收掉。

**若通過，三個可談的延伸（皆未驗證）：**
1. **移植到 MCMC 會消掉 AbsGS 的兩個手調常數**：原文是硬門檻（τ_p=0.0002、τ_S=0.01），
   MCMC 是取樣分布 ⇒ `probs ∝ o·(1 + k·ĝ)`，取樣不需要切點。這是簡化不只是移植。
2. **成本感知版 `probs ∝ ĝ_i / c_i`**（`c_i` = tile 足跡，`record_coverage` 已在算）。
   AbsGS 回答「哪些粒子解析度不足」，我方問「其中哪些值得那個 VRAM」。
   ⚠ 這是**改變集合**（決定往哪加），不是選子集 ⇒ 不撞 §12 的退化定理。
3. **二維分類**：`ĝ` 高＋contribution 高 = 承重但錯 ⇒ 分裂；`ĝ` 低＋contribution 高 = 別碰；
   contribution 低 ⇒ trim。現行是兩條各自獨立的 1D 規則（densify 看 opacity、trim 看貢獻）。

⚠ **保留**：尾巴跨六種配方 Spearman ρ=0.990、換 init 只差 0.15 dB ⇒ **沒有證據顯示 ĝ 會動到尾巴**。
   這條線打的是平均與低頻結構（§11.15 量到那是唯一有差異的維度），不是尾巴。

## §11.28 ★★★★★ 退化定理的前提被推翻，成本感知剪枝在 frontier 上壓倒性勝出（2026-08-26）

使用者問「trim 剪掉最便宜的點所以沒省資源，那把成本感知加回來呢？」帶出來的。
⚠ 我一度用「退化定理」擋掉這條線，**那是錯的引用**：原檔名就是
`archive/S11_成本模型_bug下量測_作廢.md`，自述「解析論證不依賴資料可能仍成立，
但支持它的三個實測已作廢（bug 期量的）」⇒ **前提從未在當前資料上驗證過**。

在 `notrim2_b12` 的 60k 成品模型上量（`vpc_report`，只讀不剪枝，24 視角取樣）：

```
零值 12.9%（零值的 v 與 v/c 排序相同，必須排除才有鑑別力 —— v1 沒排除，量出空結果）
非零 226.5 萬顆：rho(v,c)=+0.127   pearson(log v, log c)=+0.085     <- 要求 ≈ 1.0
```
⇒ **`v = kappa*c` 決定性推翻。v 與 c 幾乎不相關。**

```
        剪除比例   成本節省   價值損失   兩遮罩重疊
按 v      10%      6.75%     0.06%
按 v/c    10%     49.59%     0.64%       60%
按 v      30%     21.28%     1.19%
按 v/c    30%     82.83%     7.47%       64%
```

⚠ **我第一版的判讀線是錯的**（寫「成本倍率 >> 價值代價倍率 才算有自由度」）：
兩種方法落在成本軸的**完全不同位置**，比「倍率的倍率」沒有意義。
正確的問法是**等成本節省下誰損失的價值少**：
  要砍 50% 渲染成本 —— `v/c` 只需剪 10% 顆粒、損 **0.64%** 價值；
  按 `v` 剪 30% 才砍到 21.3%，得剪到約 70% 才追得上，價值損失高一個量級。
⇒ **成本感知剪枝在 cost-value frontier 上壓倒性勝出。**

⚠ **保留（未驗證的環節）**：
- `v` = 24 視角取樣的 `Σ(T·α)/覆蓋像素`，`c` = 區間內最大螢幕半徑^2，**兩者都是代理**
- **`Σv` 不是品質**。損失 0.64% 的 `Σv` 不等於損失 0.64% 的 PSNR —— 這是這個結果與
  「真的會不會贏」之間唯一的缺口，**只有訓練跑次能回答**
- `v/c 跨度 = inf` 是 float32 顯示溢位（min 是 denormal），不是資料問題

⚠ **還有一個環節要標清楚**：診斷量的是「**移除**」的成本-價值前緣，但程式碼裡
`vpc_mask` 是併進 `dead_mask`（`:455-458`）⇒ 走的是 **relocation（搬移）不是刪除**，N 不變。
搬移後的成本取決於落點；relocation 會繼承宿主的尺度，所以一顆霧狀巨獸會被換成正常大小的
粒子，成本應該會降 —— 但**這一步沒有被上面的診斷直接支持**。

⇒ 已排 `scripts/task_vpc_b12.sh`：`sched30` + `vpc_prune_frac 0.05`，是本 session 第一個
**有正面前提量測支持**的介入（前面 notrim2／egd 都是先做再發現前提不成立）。

## §11.36 接線改對：v/c 與 |g| 進「增生取樣」而不是「回收搬移」（2026-08-26，使用者指示）

也在那）新增兩個獨立旗標，**預設 0 = 現行行為**：
```
absgrad_densify     probs *= (1 + w * |g| / mean|g|)      AbsGS 訊號，天花板實測 16.68x（§11.30）
cost_aware_densify  probs /= (c / median(c))^w            成本感知，c = 螢幕半徑^2
```
保留 opacity 當基底：MCMC 的 `o_new = 1-(1-o)^(1/N)` 會把父代 opacity 分給子代，

同時開就是 `probs ~ o*(1+w*g)/c^w'` ＝「每單位渲染成本的預期誤差下降」的貪婪規則，
但**先各自單獨測**。

`vpc_prune_frac` 卻把 mask 併進 `dead_mask` ⇒ 走 relocation ⇒ 把粒子丟到依 opacity 取樣的
隨機宿主、毀掉它原本在做的事 ⇒ -2.34 dB。**增生取樣是「改變集合」，不碰既有幾何。**

## §11.39 ⛔ `agd_b12` 連死兩次：我加的診斷呼叫造成 ZeroDivisionError（2026-08-27）

`absgrad_densify > 0` 會呼叫 `_absgrad_report`，但該方法開頭是
`if global_step % self.config.absgrad_report != 0`，而 `absgrad_report` 預設 **0**
⇒ `% 0` ⇒ `ZeroDivisionError`，跑次在 step 0 就死。

修法：`if self.config.absgrad_report <= 0 or global_step % ... != 0`。
`|g|` 的累積發生在該檢查**之前**，所以 densify 用途不受影響。

**教訓**：我把「報告」與「累積」塞在同一個方法裡，然後讓第二個用途去呼叫它 ⇒
報告專屬的前置條件（`absgrad_report` 必須 >0）變成隱藏耦合。
**診斷方法被第二個呼叫者複用時，要先檢查它的前置條件是不是只對第一個呼叫者成立。**

**★ 為什麼平：三個臂的 `N` 完全相同（2.34M ＝ 0.9×cap）。**

族群大小由 **`cap_max`（顆數）** 決定，不由成本決定。所以「成本感知取樣」只能改變
**哪些顆存在**，完全不能改變**花多少資源**——成本訊號**沒有預算可以交易**。

```
現在的實作   max Q  s.t.  N <= cap          ← 約束是**顆數**，成本只是取樣權重
命題要的     max Q  s.t.  (1/K)·Σ c_i <= B  ← 約束是**成本**
```
⇒ **`cost_aware_densify` 從來就不是「論文命題的另一半」，它是把命題的訊號塞進一個
仍然以顆數為約束的框架裡。** 命題真正沒被實作過的部分是**把 `cap_max` 換成成本預算**。
在顆數約束下，v/c 排序只是在同一條等顆數線上移動 —— 這與 §3.1.1「覆蓋為硬下限」的
修正一致，也解釋了為何 `vpc_prune_frac`（剪枝側）與 `cost_aware_densify`（增生側）
兩個方向都碰不到分數。

**對立論的影響**：不可再說「成本感知增生是命題的驗證」。存活的說法是
「**價值訊號**（|g|）在 MCMC 取樣上有效（agd，兩塊全勝）；**成本訊號**在顆數約束下無效，
要有效必須把成本升格為約束本身」——後者尚未實作，是下一個真正的實驗。
