## §1 命題：成本感知的密度控制

```
max Q(theta_S)   s.t.   (1/K) * sum_{i in S} c_i <= B(hardware)
  c_i = 螢幕 tile 足跡（精確量＝光柵器的 tiles_touched）   lambda = 影子價格   K = 條帶切分（供給側槓桿）
```
既有的密度控制用**顆數**計價（`cap_max`、opacity L1、scale L1），對「這顆實際多貴」是盲的；我方改用渲染成本計價。

⚠ 「每個先前方法都是 `c_i ≡ 1` 的特例」有兩個反例：RAIN-GS（`s = HW/(9πN)` 是全域螢幕預算）、Taming 3DGS（densify 分數含覆蓋像素數，
但符號為**正**、權重 0.1 約佔分數 0.2%）。倖存的區別是 **c 當偵測器 vs c 當價格**（綁在 `sum c_i <= B` 上）。
⚠ `scale_reg` 是 r=0.977 的成本代理（空拍深度範圍窄）=> 對它「c≡1」不成立。

### §1.1 三個位置的結果

- **剪枝端（最強）**：週期 trim 的判準 v → v/c（背包的貪婪近似），零額外成本（c 在同一個 pass 裡算好）。
  22k 三塊同 N：Load -64~-67%、PSNR -0.00~-0.17（3/3 同號）、LPIPS 較好；放到前緣上**同 Load 比只調 cap 高約 +1.2 dB**。
  60k：conic 關 -0.27／-0.54（品質代價隨訓練長度放大）；conic 開 -0.17／-0.20 且 LPIPS 較好。
  ⚠⚠ **塊內 held-out（conic 關）：b6 -1.02、b13 -1.00 dB**，是 val 代價的 2~4 倍 => v/c 剪掉的東西對新視角更重要；
  「以小 PSNR 換一半 Load」在泛化上不成立。conic 開的 v/c 還沒量 held-out。=> `實驗分析/12` §6
  ⚠ 只在 MCMC 配方成立（官方 vanilla 配方 -2.62／-3.77：vanilla 沒有把名額補回的機制）。=> `實驗分析/05`
- **取樣端**：寬鬆預算（cap 2.6M）下是旋鈕（w=+4：Load -15%／-0.17 dB；Taming 方向：+10%／+0.14），同預算下被剪枝端支配。
  緊預算 B0/4：b6 +0.66 dB 且同成本，但 b12 預算 step 1,500 就爆 16 倍（退化測試）=> 不可引用。=> `實驗分析/07`
- **約束端**：`cost_budget` 同成本下不贏直接調低 cap（代理單位 -0.21~0.00、精確單位 -0.15~-0.29）。
  根因：閘門只擋加點、擋不住每顆變大（每顆足跡 2.5~3.4 倍）；用區間最大值判斷時被少數視角主宰。前鬆後緊的相對預算最划算。=> `實驗分析/07`

### §1.2 背包的空間與成本的物理意義

- v 與 c 解耦（rho(v,c) ≈ 0）=> 退化定理的前提是假的；空間隨預算收緊放大（10% 預算 +48~57%、75% 只 +0.8~2.3%，離線上界）。=> `實驗分析/07`
- **c_i 主要是時間成本**：同 N 下 Load -63% 只讓渲染 forward 峰值 -6%，常駐的參數＋梯度＋Adam（928 B/顆）只看 N；時間則 fwd+bwd -27%。
  => 命題式子裡的 B 主要代表**每步時間預算**；VRAM 的主槓桿是 N（與 SH 階數）。=> `實驗分析/02`
- SSIM 本身已按足跡的**反比**計價（小斑塊罰得比大斑塊重 14 倍）=>「c 沒被計價」不成立；我方 1/c 與它同向。=> `實驗分析/07`
- 精確 c（Σtiles）與代理 Σ(2r/16)² 沒有固定倍率（0.28~4.40、訓練中變號），conic 開啟後方向相反 => 新年代一律 `exact_tile_cost`。=> `實驗分析/04`

### §1.3 待決的設計問題（使用者 10-02）
剪（誰不值：v 或 v/c）、搬（MCMC 把空名額放哪：opacity×|g|）、總量（cap／預算：顆數）目前用三種不同單位計價。
統一成同一個「邊際價值÷成本」與一個影子價格 lambda：剪 v_i/c_i < lambda 的、往預期收益/成本 > lambda 的地方加、調 lambda 達到預算 B => N 成為均衡結果。
判讀計畫：先看 `oent`（opacity 二元熵正則，60k 已排）同 cap 下的品質與 Load；若同 N 更好，再做「oent＋低 cap」看 cap 曲線是否整條上移。
**10-09 結果（修正 10-08 只看 val 的判斷）**：oent val -0.62／-0.13，但塊內 held-out **+0.22／+0.42**、held-out LPIPS 兩塊最好、精確 Load 中位 **-48／-52%**（`實驗分析/05` §0）=> **不關閉**；val 與 held-out 反向，下一步候選是 oent 疊在 dup4 上，再看「oent＋低 cap」。

## §7 方法論

### §7.1 量測

**先量再解釋。** 提出機制解釋之前先問「它預測什麼可量的量」。
2026-09 有一輪四個假說全部從一兩張圖跳到機制、**全被推翻**；而讀碼猜的三個減計算候選
**全沒進前 40 名**，真兇是沒想到的 trim pass（80%）。
⇒ **診斷能拒絕整個家族，介入一次只能測一個點。**

**判準要對準假設中的作用機制，不是方便量的東西。**
`oregstop` 的前提「收割期 opacity L1 是純損失」是用**死亡率**判的，
漏掉它真正在做的事：同樣 2.34M 顆，關掉後總 opacity 質量 +47%、o>=0.9 多 1.82 倍。

**隨機事件一律用重複試驗報比例，不准用單次。**
2026-09-13 我為 `max_split` 三次改口，全因單點量測：同一設定（N=2.6M、ballast 0.8G、
不開旗標）在六次試驗裡活過一次，我剛好抽到那次就宣稱「牆是隨機的」。
5 次重複後定案：不設 **OOM 5/5**、設了 **0/5**。

**比較前 diff 兩份 resolved config。**
`speed3_sfminit_b12` 以為唯一變數是 init，實際差**四項**，其中 `dynamic_strips=true` 讓
77.7% 的訓練步跑在被改過的 loss 上 => 一整趟 9 小時 GPU 作廢，而檢查是**秒級**的。
⇒ 已自動化：`tools/diff_resolved_config.py`，`run_fit` 收尾自動跑。
⚠ 讀的要是 **resolved config**（Lightning 寫下的實際生效值）—— CLI 旗標打錯字會被
  jsonargparse 吃掉而不報錯，只有它看得出來。

**比分數之前先驗跑次有沒有跑完。**
`results.txt` **不寫步數** => 半途 OOM 的跑次會留下看起來正常的分數。

**驗「有沒有異常值」要取 max 與計數，不能取樣。**
P7 的 `1/(surf_depth+1e-8)` 在無粒子像素回傳 **1e8**，取樣看不到。

**「A 對應到 B」的驗證，判準不能來自 A 或 B。**
2026-09-13 我用三個不足的測試撤回了一個**正確**的發現：
(a) sparse 對 transforms.json 是循環（同一組姿態）
(b) 對極幾何對「一致的幀偏移」不敏感
(c) 「模型重建得好」與過擬合相容 —— **這一點是使用者指出的**
⇒ 最後是**位元組級 md5** 定案。三個不足的測試不會相加成一個足夠的測試。

**先量便宜的再投昂貴的。** 6GB 單卡序列，一個實驗鎖 4~11 小時。
2026-09-13 的例子：背包的「有沒有空間」用**一次前向**就答完（`tools/rho_value_cost.py`），
而原本的計畫是跑 60k；`cost_budget` 的標定同理，省下約 15 小時 lab 時間。

**上界要標成上界。** `rho_value_cost` 的 +57% 是離線、且知道每顆真實 v 的選擇；
訓練期只能用代理訊號 => 實際一定更少。不標清楚就會變成 overclaim。

**增生期落後的機制要等跑完才算。** v/c trim 在 @10,960 落後 0.57 dB（7sd，且是虛假細節簽名），收割期全部補回（`實驗分析/05`）。

**成本比較看 p95／中位，不看 max。** max 會被少數視角主宰（cs_costdir：max +30% 而 p95 -12%、中位 -11%；b12 單一視角尖峰 32 倍平均）。

**一份輸出裡有一個不可能的數字時，同一份的其他數字也要重驗。** 印出「浪費 -16317.1%」（單位錯）的那份報告，
同時印出退化的「遮罩重疊 100%」，差點讓 v/c trim 被關掉（並列 + 量在機制已停的時點）。

**「作廢」這個標籤本身也要重驗。** 2026-09-13 推翻了兩個過去貼的作廢標籤（退化定理、破平衡公式）。
看到「作廢」先問：是因為 GT 配對作廢，還是別的理由？後者（量錯工具、被取代）常常是「量本身還在，只是要重量」。

**比較前先確認對照組的真實參數**（不只 diff 處理組）：sfmfill 掃描第一版把基準誤當工具預設，每個變體與對照差 2~3 個參數。

「runner.log 沒成長」不等於死了 —— 它只在 START/DONE/FAIL 時寫，三個槽都在跑長跑次時
