## §1 命題：成本感知的密度控制（現況）

```
max Q(theta_S)   s.t.   (1/K) * sum_{i in S} c_i <= B(hardware)
  c_i = 螢幕足跡（精確量＝光柵器的 tiles_touched；訓練期用覆蓋像素，排序相關 0.84~0.99）   lambda = 影子價格
```
- **兌現的位置＝剪枝端**：週期 trim 的判準由「最好視角的每像素貢獻 v」改成 **V/C**（各視角總貢獻 ÷ 覆蓋像素），
  再加 opacity 二元熵正則（顆粒趨向 0／1，低價值的更早被 MCMC 判死）=> best1：同品質、精確 Load −1/3（`實驗分析/13`）。
  背包的對偶 `V − lambda·C > 0 ⟺ V/C > lambda`：在預算切斷下與比值排序是同一個集合。
- **c_i 主要是時間成本**：同 N 下 Load 大降時 VRAM 只降約 6%；常駐（參數＋梯度＋Adam，864~928 B/顆）只看 N（`實驗分析/02`）
  => 式子裡的 B 主要是每步時間預算；VRAM 的槓桿是 N 與 SH 階數。
- 取樣端（增生時乘成本項）與約束端（成本預算取代 cap）同成本都沒有贏過直接調 cap => 已關閉（`new_archived/第五批_廢案_2026-10-15/07_成本感知取樣與預算.md`）。
- 文獻歸屬：RAIN-GS（全域螢幕預算）與 Taming 3DGS（densify 分數含覆蓋像素、符號為正）是「先前方法都是 c≡1」的反例；
  倖存的區別是 **c 當價格**（綁在預算上、用在剪枝）vs c 當偵測器；`scale_reg` 是 r=0.977 的成本代理。
- 待決：剪（V/C）、搬（MCMC 的 opacity×|g|）、總量（cap）仍是三種單位；統一成一個影子價格屬於 ADMM 框架（`實驗分析/14` §3.3~3.4）。

### §3.4 GT 的逐幀曝光（2026-10-15；`tools/exposure_check_b6.py`、`outputs/analysis/exposure_b6/`）
- b6 test 視角（val⊂train）上 best1 與官方 release 的「渲染／GT」整體亮度比中位 0.999／1.016（整批不偏），但**同幾幀一起偏暗**（1284、2200 需要 ×1.10）；
  平移 (0,0)、整張普遍偏暗、三通道同倍 => 曝光，不是錯位。逐幀增益兩模型 r = 0.865。
- **場景越暗的幀 GT 越被提亮**：場景亮度取另一模型的渲染（避開機械相關）corr −0.69／−0.48、log-log 斜率約 −0.5 => 符合 UE 自動曝光約一半補償（MatrixCity 文件未查證）。
- 靜態 3D 模型（含 SH3）表達不了逐幀曝光 => 兩邊同樣吃這個誤差。補償上限（val⊂train b6）：逐幀最佳增益我方中位 +0.17／平均 +0.33 dB、官方 +0.40／+0.58；
  不看 GT 的全域曲線 `log k = a·log(渲染亮度) + b`（可用於新視角）我方 +0.05／+0.13、官方 +0.14／+0.36；1284 26.05 → 27.73。
- 使用者 10-15 同意：逐影像曝光補償臂（步驟 1，§11）。
- **10-15 b6 第一個結果（`g44_best1expo`，只學增益；換塊評測與 F1 還沒跑 => 未定案）**：
  原始 val PSNR 27.58（best1 29.58，**−2.00**）、`psnr_ex`（全域曲線預測曝光）**30.31（+0.73）**；
  塊內 held-out（原始渲染、新視角）19.26 vs 19.07（**+0.19**）、SSIM .5764 vs .5638、LPIPS .4301 vs .4351（三項都較好）。
  學到的增益 p5／p50／p95 0.862／0.974／1.248；**log 增益對 log 渲染亮度 corr −0.962、斜率 −0.991**（`exp(c)`＝0.309 ≈ GT 平均亮度 0.30）
  => GT 幾乎是「每幀自動曝光到固定平均亮度」；沒補償的模型只量到 −0.5，是因為它把一半的曝光差背進了 SH（隨視角的顏色）。
  解讀：沒補償時 val（訓練視角）高是背出來的；新視角上補償版較好。原始 val 的 −2 dB 是曝光尺度不同，不是模型變差。

## §7 方法論

### §7.1 量測

**先量再解釋。** 提出機制解釋之前先問「它預測什麼可量的量」。
2026-09 有一輪四個假說全部從一兩張圖跳到機制、**全被推翻**；而讀碼猜的三個減計算候選
**全沒進前 40 名**，真兇是沒想到的 trim pass（80%）。
⇒ **診斷能拒絕整個家族，介入一次只能測一個點。**

**判準要對準假設中的作用機制，不是方便量的東西。**
`oregstop` 的前提「收割期 opacity L1 是純損失」是用**死亡率**判的，
漏掉它真正在做的事：同樣 2.34M 顆，關掉後總 opacity 質量 +47%、o>=0.9 多 1.82 倍。

**隨機事件一律用重複試驗報比例，不准用單次。**
2026-09-13 我為 `max_split` 三次改口，全因單點量測：同一設定（N=2.6M、ballast 0.8G、
不開旗標）在六次試驗裡活過一次，我剛好抽到那次就宣稱「牆是隨機的」。
5 次重複後定案：不設 **OOM 5/5**、設了 **0/5**。

**比較前 diff 兩份 resolved config。**
`speed3_sfminit_b12` 以為唯一變數是 init，實際差**四項**，其中 `dynamic_strips=true` 讓
77.7% 的訓練步跑在被改過的 loss 上 => 一整趟 9 小時 GPU 作廢，而檢查是**秒級**的。
⇒ 已自動化：`tools/diff_resolved_config.py`，`run_fit` 收尾自動跑。
⚠ 讀的要是 **resolved config**（Lightning 寫下的實際生效值）—— CLI 旗標打錯字會被
  jsonargparse 吃掉而不報錯，只有它看得出來。

**比分數之前先驗跑次有沒有跑完。**
`results.txt` **不寫步數** => 半途 OOM 的跑次會留下看起來正常的分數。

**驗「有沒有異常值」要取 max 與計數，不能取樣。**
P7 的 `1/(surf_depth+1e-8)` 在無粒子像素回傳 **1e8**，取樣看不到。

**「A 對應到 B」的驗證，判準不能來自 A 或 B。**
2026-09-13 我用三個不足的測試撤回了一個**正確**的發現：
(a) sparse 對 transforms.json 是循環（同一組姿態）
(b) 對極幾何對「一致的幀偏移」不敏感
(c) 「模型重建得好」與過擬合相容 —— **這一點是使用者指出的**
⇒ 最後是**位元組級 md5** 定案。三個不足的測試不會相加成一個足夠的測試。

**先量便宜的再投昂貴的。** 6GB 單卡序列，一個實驗鎖 4~11 小時。
2026-09-13 的例子：背包的「有沒有空間」用**一次前向**就答完（`tools/rho_value_cost.py`），
而原本的計畫是跑 60k；`cost_budget` 的標定同理，省下約 15 小時 lab 時間。

**上界要標成上界。** `rho_value_cost` 的 +57% 是離線、且知道每顆真實 v 的選擇；
訓練期只能用代理訊號 => 實際一定更少。不標清楚就會變成 overclaim。

**增生期落後的機制要等跑完才算。** v/c trim 在 @10,960 落後 0.57 dB（7sd，且是虛假細節簽名），收割期全部補回（`實驗分析/05`）。

**成本比較看 p95／中位，不看 max。** max 會被少數視角主宰（cs_costdir：max +30% 而 p95 -12%、中位 -11%；b12 單一視角尖峰 32 倍平均）。

**一份輸出裡有一個不可能的數字時，同一份的其他數字也要重驗。** 印出「浪費 -16317.1%」（單位錯）的那份報告，
同時印出退化的「遮罩重疊 100%」，差點讓 v/c trim 被關掉（並列 + 量在機制已停的時點）。

**「作廢」這個標籤本身也要重驗。** 2026-09-13 推翻了兩個過去貼的作廢標籤（退化定理、破平衡公式）。
看到「作廢」先問：是因為 GT 配對作廢，還是別的理由？後者（量錯工具、被取代）常常是「量本身還在，只是要重量」。

**比較前先確認對照組的真實參數**（不只 diff 處理組）：sfmfill 掃描第一版把基準誤當工具預設，每個變體與對照差 2~3 個參數。

### §7.2 基建

**共同形狀：這些失敗都不會報錯。**
已抓到 7 個「看起來正常但沒作用」的機制（死碼／守衛不含自己／ckpt 覆蓋 renderer 旗標／
步數不接續／0 秒 exit 1／test 分數被丟棄／`ColmapBlock.instantiate` 回傳基底 parser）。
2026-09-13 再加三個：
```
腳本被原地覆寫   bash **逐段讀取**腳本檔 => 跑到一半被 git pull／編輯器覆寫，
                 會從錯的位元組偏移繼續讀。實測後果是**靜默吃掉剩下的腳本且 rc=0**。
                 => scripts/_noedit.sh（讀進記憶體再執行，$0 設回原路徑）
下載被中斷       半個檔案留在最終檔名下，事後沒有東西比對大小 => 載入時才炸。
                 => 先寫 .part、比對大小、通過才原子改名
工具雙開         兩個行程寫同一個輸出目錄 => 產出的是**舊參數**的結果，
                 而檔案大小一模一樣。沒有錯誤、沒有崩潰，只是內容不是你以為的那個。
                 => internal/utils/outlock.py，且鎖要在**載入任何東西之前**取（快速失敗）
```

**新機制必須印「✅ 首次觸發 + 實現的參數範圍」或「⚠⚠ 拿不到訊號」。**
2026-09-07 連救三次。配套：「沒效果」的結論要先出示它**觸發過**。

**排程一律用 `scripts/runner.sh` + `queue.txt`，不准自開 watcher。**
`pgrep` 判 GPU 三種踩法全中過（cmdline 被 `conda run` 改寫／匹配到檢查自己的 shell／
殭屍照樣匹配）。2026-09-13 我用 `pkill -f 'lab.py pull'` 又中第二種 —— **把執行該指令的
shell 自己殺掉**（exit 144）。⇒ 要停行程用 **PID**，不要用會匹配到自己的 pattern。

**改正在執行的 `.sh` 一律用「寫暫存檔再 mv」**（新 inode），不要用 Python 就地覆寫。
實測 `sed -i` 換 inode、`open(w)` 不換。

**監看的判準要對準「活著」的直接訊號。**
「runner.log 沒成長」不等於死了 —— 它只在 START/DONE/FAIL 時寫，三個槽都在跑長跑次時
本來就不會成長。改看**跑次步數是否前進**。
同理：單次 API 逾時不算掛掉（我自己的大量下載就會把它塞住）=> 重試一次再判定。

### §7.3 這一節為什麼不受年代分界影響

判準只有一條：**這個量測有沒有經過「GT 影像↔姿態」的配對？**
方法論講的是「怎麼量」「怎麼排程」「什麼形狀的失敗不會報錯」，都不碰那個配對
=> 三次年代分界都沒有動到它們。這也是搬遷時先搬這一節的原因：**沒有判斷風險**。
