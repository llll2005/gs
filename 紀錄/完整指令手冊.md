```bash
python -c "
import torch, os
state_dir = 'outputs/ADMM_v2_RTG_mc_aerial_sh2_trim/admm_state'
for bid in range(25):
    path = f'{state_dir}/block_{bid}_state.pt'
    if not os.path.exists(path): print(f'block_{bid}: no state'); continue
    s = torch.load(path, map_location='cpu')
    y = s.get('dual_y', None)
    bnd = s.get('is_boundary', None)
    if y is None: print(f'block_{bid}: no dual_y'); continue
    n_bnd = bnd.sum().item() if bnd is not None else 0
    n_tot = y.shape[0]
    print(f'block_{bid}: bnd={n_bnd}/{n_tot}({100*n_bnd/max(n_tot,1):.1f}%) ||y||={y.norm():.4f}')
"
```

## 9. SB Color（Spherical Beta，DBS 移植）與逐塊 cap 校準（2026-07-17 新增）

### 9-1. SB color 是什麼

從 Deformable Beta Splatting 移植的色彩表示（**只移植 SB color，不移植 beta falloff kernel**——
後者我方實測淨負且需重寫 CUDA）。公式（ASCII）：

```
C(d) = clamp(SH_eval(shs, d) + 0.5, 0) + sum_i c_i * max(0, <mu_i, d>)^(4*exp(b_i))
```

- 每 lobe 6 參數 `[r,g,b,theta,phi,beta]`，rgb 過 softplus；預設 `sb_number=2`
- 搭配 `sh_degree=0`：色彩參數 48 floats(SH3) → 15 floats(DC 3 + SB 12)
- **每點總 floats：59 → 25**（模型狀態 944B/pt → 400B/pt，公式 F 槓桿，同 VRAM 塞 ~2.4x 點）
- 顏色在 Python 算好走 `colors_precomp` 進 trim rasterizer，**不碰 CUDA**

### 9-2. 相關檔案

| 檔案 | 內容 |
|------|------|
| `internal/utils/sb_utils.py` | SB 數學（activation + eval，autograd backward） |
| `internal/models/gaussian_2d_sb.py` | `Gaussian2DSB`（config: `sb_number`, `sb_params_lr`） |
| `internal/renderers/sep_depth_trim_2dgs_sb_renderer.py` | `SepDepthTrim2DGSSBRenderer` |
| `configs/mcmc_2dgs_sb_60k_aggr17_aerial.yaml` | aggr17 的 SB 版 config |

kernel 切換 = config 換 `gaussian.class_path` + `renderer.class_path`（jsonargparse 原生機制）。
訓練開始時 stdout 印 `[kernel] renderer=... model=... color=... floats/point=...` 橫幅。

### 9-3. SB 訓練指令（單塊，b7 為例）

```bash
conda run -n gspl python -u main.py fit --config configs/mcmc_2dgs_sb_60k_aggr17_aerial.yaml --model.initialize_from data/matrix_city/aerial/train/block_all/depth_init/block_7.ply --data.parser.block_id 7 -n mcmc_sb_60k_aggr17_b7
```

### 9-4. 逐塊 cap 校準（封閉預算公式）

```
N_max = (V_target * 0.9 - V_os) / (4*F*4 + gamma * tau_max * tau_growth / K)
```

三步（工具 `tools/calibrate_block_caps.py`，詳 `--help`）：

```bash
# 1) 逐塊量 tau（gsplat forward，免訓練，~分鐘級）
python tools/calibrate_block_caps.py taus --blocks 0-24

# 2) trim kernel 校準 gamma/V_os（N vs N/2 線性擬合；--sb 量 SB 版）
python tools/calibrate_block_caps.py probe-trim --block 12
python tools/calibrate_block_caps.py probe-trim --block 12 --sb

# 3) 產出逐塊 cap 表（餵給訓練的 --model.density.init_args.cap_max）
python tools/calibrate_block_caps.py caps --gamma_trim <G> --vos_trim <V>
```

- `tau_growth` 預設 1.65：init-tau → trained-tau 漂移修正（b12 實測 73→~120）
- 部署前清塵：`python tools/cull_dust.py <ckpt_in> <ckpt_out>`（砍 o<0.05&subpx 殭屍,7.4×,無損）；訓練中清塵=`--model.density.init_args.harvest_dust_trim_interval N`
- gamma/V_os 是 **kernel-specific**（gsplat 量的 23B/isect 不能直接套 trim）；tau 是幾何屬性可跨 kernel
- 輸出 `紀錄/block_taus.csv`（病理排名）與 `紀錄/block_caps.csv`（cap 表）

### 9-5. 預測式動態 K（2026-07-20）

K-strip 是 loss 不變量（條帶拼合=全幀 MSE 1e-4），故 K 可動態調而不影響品質。動態 K 每步用
**當前幾何**投影預估 render 負載→反解 budget 公式定 K（預測式非反應式，保穩健）：

```bash
# 開啟：多數步/視角自動 K=1(快)，只有高負載時刻升 K(安全)
--model.dynamic_strips true --model.strip_max 8
# 相關參數：--model.strip_vram_target_gb 5.4 --model.strip_v_os_gb 0.8 --model.strip_safety 0.6
```

- 機制：`internal/utils/strip_cameras.py:estimate_render_load`（投影+幀裁剪,不渲染）
  + `predict_num_strips`（K=ceil(load_bytes/(render_budget×safety))）
- safety=0.6 吸收 proxy 誤差；strip_max 上限。CPU 驗證:安全期 K=1、死亡點 K=5-6。
- 固定 K 用 `--model.train_strips N`（dynamic_strips 關時生效）。

## §N 執行台帳 `logs/quad_progress.log`（2026-07-28 改為程序自寫）

**格式（固定，不再由腳本拼字串）**：
```
MM-DD HH:MM | <run 名稱, 24 欄>   | START/DONE/DIED  <結構化欄位>
```
實例：
```
07-28 21:27 | b12_cap2m_reg000_exact   | START  max_steps=60,000 cap=2.00M opacity_reg=0.0 out=outputs/...
07-28 21:27 | b12_cap2m_reg000_exact   | DONE   step=60,000/60,000 N=1.93M 4.12it/s VRAM=4.83/6.1G PSNR=23.457@60,000
07-28 21:27 | b12_cap2m_reg000_exact   | DIED   OutOfMemoryError: CUDA out of memory... | step=12,345/60,000 N=1.93M ...
```

**由誰寫**：`internal/callbacks.py` 的 `TrainConsole._progress()`，掛在 `setup`(START) /
`on_train_end`(DONE) / `on_exception`(DIED)。數值直接取自 live footer 與 `state.vals`。

**為何改**：舊做法是**每個腳本各自 grep 訓練 log 再拼字串**，結果
(1) 把 tqdm 進度條與 ANSI 逃脫碼一起撈進台帳（`DONE rc=0 Epoch 5: 29%|██▊ |...[A[A`），
(2) 各腳本欄寬漂移（`%-22s` vs `%-24s`），
(3) 跑掛的時候常常什麼都沒寫（grep 不到 results.txt 就靜默）。

**規則**：
- **腳本不得再寫 START/DONE/DIED**——那三個由程序負責。
- 腳本的 `log()` 只寫**程序不可能知道的佇列層事件**（等 GPU、批次邊界），一律加 `QUEUE ` 前綴。
- 台帳寫入失敗**絕不影響訓練**（`_progress` 整段包在 try/except）。

## 跑次命名：平名 vs `_bNN` 後綴（2026-08-25 釐清）

**兩套慣例並存，是刻意的，不是混亂：**

```
outputs/<name>/blocks/block_N/      上游多塊工具（train_citygs_partitions.py）用這套
outputs/<name>_bNN/blocks/block_N/  我們手寫的單塊實驗腳本用這套（120 個跑次）
```

`merge_citygs_ckpts.py` 合併的是 `outputs/<path>/blocks/` 底下的**每一個**子目錄
（`merge_citygs_ckpts.py:17,37`），而 `train_citygs_partitions.py` 讓所有 partition
共用一個 `-n`、只變動 `--data.parser.block_id`（:74,95）⇒ **上游設計就是平名 + block 子目錄。**

**後綴為什麼存在**：手寫腳本開頭是 `rm -rf outputs/$NAME`。共用 name 的話，
跑 b7 會刪掉已經跑完的 b12（2026-08-17 真的發生過）。後綴給每支腳本獨立的生命週期，
`tools/lint_task_scripts.py` 則檢查 `rm -rf outputs/X` 與 `-n Y` 是否一致。

**選哪個**：`-n` 與 `--data.parser.block_id` 互相獨立，所以
- **單塊消融實驗** → 用 `_bNN` 後綴（現況，不遷移：120 個目錄 + 紀錄/CSV/記憶/工具預設的每個引用）
- **之後要 merge 的跑次** → **用平名**，並且**腳本裡不可以 `rm -rf outputs/$NAME`**
  （改成只刪 `outputs/$NAME/blocks/block_$BLK`，或不刪、靠可重入判斷跳過已完成的塊）

⚠ 後綴確實冗餘（`notrim2_b12/blocks/block_12` 重複資訊），但唯一擋住的是
「把 b12+b7 merge 起來」，而 25 塊裡的 2 塊合起來沒有意義 ⇒ 不值得遷移。
北極星（25 塊全場景）走 `train_citygs_partitions.py`，本來就不經過手寫腳本。
