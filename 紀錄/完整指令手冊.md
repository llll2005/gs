## 0. 每日工作流

### 0-1. 排程器（**鐵律：只用這一套，不准自己寫 watcher**）

單卡序列，所以一定要有東西持有佇列。那個東西已經存在：

```bash
setsid nohup bash scripts/runner.sh > /dev/null 2>&1 < /dev/null &   # 起（通常已經在跑）
```
```bash
$EDITOR scripts/queue.txt          # 一行一個任務；跑動中也可以改／加／重排
```
```bash
python tools/queue_status.py       # 現在在跑什麼、佇列裡還有什麼、最近完成
```
```bash
tail -f logs/runner.log            # 即時輸出
```
```bash
touch scripts/queue.stop           # 做完目前這個就停
```

規則：
- runner **每個任務開始前重讀 `queue.txt`** ⇒ **只有正在執行的那一行是固定的**，底下都可以改。
- 長指令放 `scripts/task_*.sh`，佇列行只呼叫它。**佇列行不可含 `$(...)` 或反斜線。**
- 任務行**正上方緊鄰的 `#` 註解區塊**會成為台帳標籤（含 ★ 的那行優先）。區塊錯位 =
  標籤掛錯跑次（發生過兩次）⇒ 用 `tools/queue_status.py` 確認「標籤 ↔ 指令」對得上。
- 不碰 GPU 的工作加 `[cpu]` 前綴，才不會排在訓練後面。
- GPU 是否空閒**由 `nvidia-smi` 的 VRAM 判定（<1500 MiB = 空）**。
  ⛔ **不准用 `pgrep`**：`conda run` 會改寫 cmdline、殭屍照樣匹配、檢查用的 shell 會匹配到自己
  —— 三種都害過這個專案空等（最久 2.5 小時）。
- `flock` 擋第二個 runner。

### 0-2. 比任何分數之前必做

```bash
python tools/run_status.py --all
```
`results.txt` **不寫步數** ⇒ 半途 OOM 的跑次會留下看起來正常的分數（曾害我擬出一條假關係）。

```bash
python tools/cmp_runs.py <base> <arm> [<arm> ...]
```
**跑次比較的唯一標準入口**：用「最後 4 個 val 點的平均」，不是終點值
（60/106 個跑完的跑次峰值落在 step 56,800，終點反而低 0.02~0.20 dB）。

噪音底（n=3 重新標定）：`PSNR sd 0.081（3sd=0.24）／SSIM 0.0005（0.0015）／
LPIPS 0.0025（0.0075）／紋理比 0.015`。

### 0-3. ⛔⛔ 比兩個跑次之前，diff 兩份 **resolved config**

```bash
diff outputs/<A>/blocks/block_12/lightning_logs/version_0/config.yaml outputs/<B>/blocks/block_12/lightning_logs/version_0/config.yaml
```
**不是 diff 任務腳本。** 手動啟動的跑次吃的是**當時的 config 檔**，而 config 檔會被別的實驗改過。
2026-09-11：`speed3_sfminit_b12` 與 `speed3_b12` 差**四項**而非一項
（`dynamic_strips` false→true 等），60k 分數因此作廢。見 §7 與 `研究總覽 §13.7`。

### 0-4. 複製任務腳本之後

```bash
python tools/lint_task_scripts.py
```
`sed` 複製腳本會漏改 `rm -rf outputs/X`，曾經刪光一整組跑次。這支檢查
`rm -rf outputs/X` 與 `-n Y` 是不是同一個，並警告「正在執行中的腳本」。

⛔ **絕不可用 `python open(p,"w")` 改正在執行中的 `.sh`** —— 就地截斷、同 inode，
跑動中的 bash 會用舊的位元組偏移繼續讀 ⇒ 讀到一行的中間。用 `sed -i` 或「暫存檔 + `mv`」。

## 3. 訓練（現行主線：MCMC 2DGS · sh3 · 60k）

### 3-1. 單塊訓練（幾乎每個實驗都是這個）

現行最佳配方 `speed3` = `sched30` + `absgrad_densify 2.0` + `fast_noise` + `noise_gate_eps 1e-3`。
**別手打，直接抄腳本**：`scripts/task_speed3.sh`（b12）／`scripts/task_speed3_b7.sh`（b7）。

最小形式（depth-init）：
```bash
conda run -n gspl python -u main.py fit --config configs/mcmc_2dgs_60k_sh3_aggr17_aerial.yaml --model.initialize_from data/matrix_city/aerial/train/block_all/depth_init/block_12.ply --data.parser.block_id 12 --model.density.init_args.cap_max 2600000 -n <run_name>
```

配方旗標（照 `task_speed3.sh`，**兩塊都驗證過的那一組**）：

| 旗標 | 值 | 說明 |
|------|-----|------|
| `--model.density.init_args.cap_max` | 2600000 | ⚠ **只交付 cap 的 90%** ⇒ 要 N 顆得設 `cap=N/0.9` |
| `--model.density.init_args.densify_until_iter` | 30000 | `sched30`，回到 vanilla 的 50% 比例 |
| `--model.density.init_args.absgrad_densify` | 2.0 | AbsGS 的 \|g\| 接到 MCMC 取樣權重 |
| `--model.density.init_args.screen_size_prune_px` | 300 | 單開是安全的（見下方 ⛔） |
| `--model.density.init_args.fast_noise` | true | 2D 切平面加噪的代數簡化 |
| `--model.density.init_args.noise_gate_eps` | 1e-3 | 跳過 69% 粒子的噪音 |
| `--model.metric.init_args.opacity_reg` | 0.002 | ⚠ **不是 0**（0 是更舊資料上的結論） |
| `--model.metric.init_args.lambda_normal` | 0.0 | 觸發零權重門檻 ⇒ 省 9% 且位元相同 |
| `--model.metric.init_args.depth_loss_weight.init` | 0.0 | 同上 |

⛔ **不要同時開 `screen_size_prune_px` 與 `screen_prune_emergency_px`**：兩者讀同一個
`_max_radii2D`，但 emergency 會把它從「光柵器實際半徑」覆寫成解析上界（含相機後方的點）
⇒ 300px 門檻變成每次 densify 刪 25% 族群（實測 PSNR 13.498 vs 對照 24.993）。

⚠ `absgrad_densify` 需要光柵器以 `ABSGRAD 1` 編譯（`cuda_rasterizer/auxiliary.h`）。

## 6. 逐塊 cap 校準（封閉預算公式）

```
N_max = (V_target * 0.9 - V_os) / (4*F*4 + gamma * tau_max * tau_growth / K)
```

```bash
python tools/calibrate_block_caps.py taus --blocks 0-24        # 1) 逐塊量 tau（免訓練）
```
```bash
python tools/calibrate_block_caps.py probe-trim --block 12     # 2) 校準 gamma/V_os
```
```bash
python tools/calibrate_block_caps.py caps --gamma_trim <G> --vos_trim <V>   # 3) 產 cap 表
```
```bash
python tools/measure_tau.py --run <run> --block-list data/matrix_city/aerial/train/block_all/partition/partitions-dim_5_5_visibility_0.08/002_002.txt
```

- `tau_growth` 預設 1.65：init-tau → trained-tau 的漂移修正（b12 實測 73 → ~120）。
- gamma/V_os 是 **kernel-specific**（gsplat 量的 23 B/isect 不能套到 trim）；tau 是幾何屬性，可跨 kernel。
- ⚠ **cap 只交付 90%**：四個跑次全停在 cap 的 90.00%，10% 全掉在收割期
  ⇒ 峰值按 cap 付、交付只有 0.9·cap。
- ⚠ 位元組模型**低估 8~37.5%** 且隨 lobe 數放大（Python 端 autograd 的 N×L 沒計入）。
- ⚠ `紀錄/block_taus.csv` / `block_caps.csv` 舊版已移入 `archive/`（用初始化期的 tau 算的）⇒ 要用請重跑。

## 7. 動態 K-strip ⚠ **會改變 loss，預設不要開**

```bash
--model.dynamic_strips true --model.strip_max 8 --model.strip_vram_target_gb 5.4 --model.strip_v_os_gb 0.8 --model.strip_safety 0.6
```
固定 K 用 `--model.train_strips N`（`dynamic_strips` 關閉時才生效）。

機制：`internal/utils/strip_cameras.py:estimate_render_load`（只投影不渲染）+ `predict_num_strips`
⇒ 把畫面切成 K 條橫帶，**逐帶前向 + 反向**，峰值 VRAM 按帶算。

### ⛔⛔ 2026-09-11 更正（舊版手冊這段是錯的）

舊版寫「K 是 loss 不變量，故可動態調而不影響品質」。**不成立**：
`internal/gaussian_splatting.py:_strip_forward_backward` 的 docstring 自承
*"Image-space SSIM is computed per strip (**boundary-window approximation**)"*。
逐點正則項確實是精確的（帶權重 h/H 且權重和為 1），但**影像空間的 SSIM 不是**。

實際代價（`speed3_sfminit_b12`，N=2.34M）：
```
VRAM 峰值實佔  4.87 -> 4.08 GB（-0.79）
速度           2.44 -> 1.85 it/s（**慢 24%**）
dynk_K.log     K>1 佔 **77.7%**、K>=6 佔 69.3%（K=1 只到 step ~12,900）
=> 77.7% 的訓練步跑在被改過的 loss 上 ⇒ 該次 60k 分數作廢
```

### 而且預測器太保守（`tools/strip_k_audit.py`，純 CPU）

```
兩個 60k 模型（load 中位 5.4M vs 6.9M）在**同一組參數**下都被判 K=6
predict budget = 0.85*(5.2-0.8) = 3.740 GiB
而 depth-init 同 N=2.34M 用 K=1 **實測**峰值 4.87 GB，沒 OOM（卡 6.1 GB）
=> budget 訂低約 1.1 GB，那 24% 的時間是白付的
```
⚠ 舊版手冊寫的公式 `K = ceil(load_bytes / (render_budget × safety))` **是過時版本**，
現行 `predict_num_strips` 還含一個不可切分的 `model_state + A_RENDER*N` 項
（程式碼註解自承舊公式「undercounted the N-scaling term and picked K=1 into an OOM at N=1.45M」）。
⚠ `strip_safety` 是**預算乘數**（`budget = safety*(target - v_os)`，越大越寬鬆），不是折減係數。

**結論**：要省 VRAM 優先用 `cap_max`；`dynamic_strips` 只在確定會 OOM 時開，
而且開了之後**不可與沒開的跑次直接比分數**。

## 8. 執行台帳 `logs/quad_progress.log`（2026-07-28 改為程序自寫）

**格式（固定，不再由腳本拼字串）**：
```
MM-DD HH:MM | <run 名稱, 24 欄>   | START/DONE/DIED  <結構化欄位>
```
實例：
```
07-28 21:27 | b12_cap2m_reg000_exact   | START  max_steps=60,000 cap=2.00M opacity_reg=0.0 out=outputs/...
07-28 21:27 | b12_cap2m_reg000_exact   | DONE   step=60,000/60,000 N=1.93M 4.12it/s VRAM=4.83/6.1G PSNR=23.457@60,000
07-28 21:27 | b12_cap2m_reg000_exact   | DIED   OutOfMemoryError: CUDA out of memory... | step=12,345/60,000 N=1.93M ...
```

**由誰寫**：`internal/callbacks.py` 的 `TrainConsole._progress()`，掛在 `setup`(START) /
`on_train_end`(DONE) / `on_exception`(DIED)。數值直接取自 live footer 與 `state.vals`。

**為何改**：舊做法是**每個腳本各自 grep 訓練 log 再拼字串**，結果
(1) 把 tqdm 進度條與 ANSI 逃脫碼一起撈進台帳（`DONE rc=0 Epoch 5: 29%|██▊ |...[A[A`），
(2) 各腳本欄寬漂移（`%-22s` vs `%-24s`），
(3) 跑掛的時候常常什麼都沒寫（grep 不到 results.txt 就靜默）。

**規則**：
- **腳本不得再寫 START/DONE/DIED**——那三個由程序負責。
- 腳本的 `log()` 只寫**程序不可能知道的佇列層事件**（等 GPU、批次邊界），一律加 `QUEUE ` 前綴。
- 台帳寫入失敗**絕不影響訓練**（`_progress` 整段包在 try/except）。

## S-1. SB color 是什麼、相關檔案、訓練指令

### S-1-1. SB color 是什麼

從 Deformable Beta Splatting 移植的色彩表示（**只移植 SB color，不移植 beta falloff kernel**——
後者我方實測淨負且需重寫 CUDA）。公式（ASCII）：

```
C(d) = clamp(SH_eval(shs, d) + 0.5, 0) + sum_i c_i * max(0, <mu_i, d>)^(4*exp(b_i))
```

- 每 lobe 6 參數 `[r,g,b,theta,phi,beta]`，rgb 過 softplus；預設 `sb_number=2`
- 搭配 `sh_degree=0`：色彩參數 48 floats(SH3) → 15 floats(DC 3 + SB 12)
- **每點總 floats：59 → 25**（模型狀態 944B/pt → 400B/pt，公式 F 槓桿，同 VRAM 塞 ~2.4x 點）
- 顏色在 Python 算好走 `colors_precomp` 進 trim rasterizer，**不碰 CUDA**

### S-1-2. 相關檔案

| 檔案 | 內容 |
|------|------|
| `internal/utils/sb_utils.py` | SB 數學（activation + eval，autograd backward） |
| `internal/models/gaussian_2d_sb.py` | `Gaussian2DSB`（config: `sb_number`, `sb_params_lr`） |
| `internal/renderers/sep_depth_trim_2dgs_sb_renderer.py` | `SepDepthTrim2DGSSBRenderer` |
| `configs/mcmc_2dgs_sb_60k_aggr17_aerial.yaml` | aggr17 的 SB 版 config |

kernel 切換 = config 換 `gaussian.class_path` + `renderer.class_path`（jsonargparse 原生機制）。
訓練開始時 stdout 印 `[kernel] renderer=... model=... color=... floats/point=...` 橫幅。
