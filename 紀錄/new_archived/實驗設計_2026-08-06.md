### P1 ★★★ 起始 trim 一次砍掉 73% 的初始化

**現象**：任何 init 進入訓練，step 1 就被砍掉 ~73%，且是**確定性**的（每個跑次在 step 499 都恰好
338,033 顆）。

```
graded init 1,316,223 → 360,817 (27.4%)
depth-init  1,211,537 → 338,033 (27.9%)
到 step 24,000 只剩 78,899（98% 消失）
```

**機制**：`internal/renderers/sep_depth_trim_2dgs_renderer.py:185-218`

```python
def before_training_step(self, step, module):
    if step != 1 or self.diable_trimming or self.diable_start_trimming:
        return
    cameras = ...train_set.cameras            # 全部 284 台
    ...
    contribution = torch.stack(top_list, -1).mean(-1)
    tile = torch.quantile(contribution, self.start_prune_ratio)   # = 0.0
    prune_mask = contribution <= tile          # 剪掉「對所有視角零貢獻」的點
```

**為什麼是問題**：
- 任何 init 實驗的處理組都在被測量之前被刪掉 ⇒ **Stage 0 空結果的直接成因**
- 錨點（被 4~338 個視角三角化的真實表面點）也被砍掉 74%——它們**不該**零貢獻
- 對成本感知論述是重要材料：**73% 的初始化預算是可證明的浪費**，在 step 0 就付了 VRAM

**參考檔案／數據**：
- `outputs/graded_k4_24k_b12/blocks/block_12/checkpoints/*.ckpt`（六個 step 的 N）
- `tools/measure_anchor_drift.py` 的輸出（本檔 §附錄 A）
- 可設參數：`diable_start_trimming`（現為 `false`）、`start_prune_ratio`（現為 `0.0`）

**★2026-08-06 已解（`tools/audit_start_trim.py`）**：

```
被砍點在存活點『後方』的比例 = 69.1%   （隨機應為 50%）
徑向距離差中位 = 0.0600                ← 對應深度誤差 0.0795，不是體素 0.03
[離表面] 存活 p50 = 21.4x   被砍 p50 = 18.3x   ← 被砍的比留下的更接近真表面
```

**結論一：厚殼假說成立。** depth-init 不是一層表面，是 284 張影像各自的表面估計互相錯開堆成的殼。
根因在我方檔頭 `utils/depth_init_blocks.py:10`：*"Point 6 — Voxel deduplication replaces online
fusion for offline case"*——RTG-SLAM 用線上 TSDF 融合合成單一表面，我方用體素去重取代，
**體素 0.03 合併不了相距 0.0795 的層**。

**結論二（更嚴重）：trim 留下的是錯的那一層。** 它只看「誰在最前面」，而 depth-init 的前層系統性
偏向相機 ⇒ **自我強化的選擇**：錯的在前 → 對的在後被刪 → 錯的鎖死。
**這也解釋了為什麼「保護錨點免於被剪」無效**——錨點留著也仍被前層遮住，收不到梯度。
**問題不是「後面的對點被刪」，是「前面的錯點還在」。**

**結論三：存活數與投入顆數無關。** 餵 1,316,223 → 存活 360,817；餵 991,841 → 存活 363,190。
⇒ 存活數由**場景可見表面容量**決定，約 36.2 萬。

### ⛔ 已證偽的三個修法（別再試）

| 修法 | 結果 |
|---|---|
| 加大體素 0.03→0.08 | 離表面 20.2× → **23.0×（更差）**。open3d 體素去重取每格第一個點，不是平均 |
| 取質心融合 @0.08 | 去重 23.0× vs 融合 **23.0×（完全相同）** |
| 球狀清除 `--fill_radius 0.08` | 錨點留存 10.7%→13.1%，但填充也同步 7.8%→9.6% ⇒ 增益來自「雲變小、分母變小」，遮擋沒解決。球只清錨點旁一圈，視線上 0.1~1.0 處照樣擋 |

⇒ **殼解釋 73% 被砍，但不解釋 20.2×。** 融合掉層間散佈，共模偏移還在。**兩個獨立問題，先前混為一談。**

### P2 ★★★ 剪枝完全盲於「是否被多視角驗證」

**現象**：
```
step  5,999   錨點留存 5.6%   填充留存 6.0%
step 24,000   錨點留存 2.1%   填充留存 2.4%
```

錨點 = SfM `track >= 4`（中位 11、p90 42 個視角交叉驗證），**留存率反而略低於單目猜測**。

**為什麼是問題**：這是第六個獨立證據。前五個（貢獻度 / opacity_reg / 塵埃收割 / 多視角集中度 /
深度一致度）都是「判準分不出 floater」，這一個是「**ground-truth 級的標籤擺在面前，剪枝照砍**」。

⇒ **不是判準選錯，是剪枝機制根本不接受幾何資訊當輸入。**

**參考檔案**：`tools/measure_anchor_drift.py`、`data/.../graded_k4_block_12.ply.w.npy`

### P3 ★★ 我方 graded init 的清除半徑用錯尺度（自己的 bug）

**現象**：錨點放在真表面上，卻對所有視角零貢獻 ⇒ 被擋住了。擋住它的是我自己放的填充點。

```
depth-init 離表面 p50 = 21.9× unit = 0.0795     ← 真正的誤差尺度
make_graded_init.py 的 fill_radius = 0.02456    ← 我用的（depth-init 的「間距」）
                                                   只有誤差的 31%
```

填充點 opacity = logit(0.99)，散佈在真表面前後 0.0795 處，**約一半在錨點前面**，把它擋死。

**解法**：`fill_radius` 改用誤差尺度（0.08），`anchor_voxel` 解耦保持 0.02456。
⚠ 預設 `anchor_voxel = fill_radius`，直接調 `fill_radius` 會連錨點一起稀釋
（實測 `fill_radius 0.05` → 錨點掉到 72,019）。

**狀態**：`graded_k4r08_block_12.ply` **已產出**（`--anchor_voxel 0.02456 --fill_radius 0.08`）：

```
                       原版(r=0.02456)      修正版(r=0.08)
錨點                    203,916              203,840      （幾乎不變 ✓ 解耦成功）
填充                  1,112,307              788,001      （−29%，清掉了遮擋者）
總數                  1,316,223              991,841
對 depth-init 的比值      1.09x                0.82x       ⚠ 顆數不再對齊
```

⚠ **新的 confound**：修正版比 depth-init 少 18% 的顆數，所以對照 v1 時「位置」與「顆數」同時變。
若 E5 拿到正向結果，要用 `--anchor_voxel` 微調把總數推回 1.2M 再確認一次。

**參考檔案**：`tools/make_graded_init.py`

### P5 ★★ 論文主張撞到 prior art

**現象**：RAIN-GS §5.2 的 `s = HW/(9πN)` 就是「每顆的螢幕預算」。

| `c_i` 角色 | 由粗到細的**優化排程下界** | 逐顆**實際成本** |

## 第二部分：實驗排程

### 排序原則

1. **CPU 能驗的先驗**（成本 0，不佔 GPU）
2. **<1h GPU 探針**次之
3. 4~11h 訓練最後，且**一次只動一個變數**
4. 6GB 單卡序列 ⇒ 同時只能有一個訓練

---

### E1【CPU，~10 分鐘】被 trim 砍掉的 73% 到底是什麼？ ← **最高優先**

**解決 P1 的未解問題**，而且**決定 E4/E5 要不要做**。

**做法**：載入 graded init PLY 與 step-499 的 ckpt，用位置比對出「被砍的集合」，然後量：

| 量測 | 若如此 ⇒ 結論 |
|---|---|
| 被砍點的離表面距離分佈 | 若遠 ⇒ 是真垃圾，trim 正確，**P1 不是問題** |
| 被砍點中錨點的比例與其 track 長度 | 若高 track 也被砍 ⇒ **被擋住**，trim 在殺真幾何 |
| 被砍錨點「前方是否有存活的填充點」（沿最近相機方向） | 直接證實/證偽遮擋假說 |

**預期**：依 P3 的推理，錨點被砍是遮擋造成的 ⇒ 會看到「被砍錨點的前方 0.02–0.15 處有填充點」。
**若證偽**（被砍錨點前方沒東西），則 P3 的診斷錯，要重想。

**工具**：新寫 `tools/audit_start_trim.py`（~80 行，沿用 `floater_label.surface_distance` 與
`eval_official_test.load_test_cameras`）。

### E2【CPU，~5 分鐘】把漂移從剪枝裡拆出來 ← 解決 P6

**做法**：不用「種子→最近存活粒子」，改用**匈牙利式的單向最近鄰＋存活遮罩**不可行（無 ID），
所以改成**分佈層級的比較**：

1. 取 step 499 的點雲 `A`（trim 後、幾乎未訓練）與 step 24,000 的 `B`
2. 量 `A → B` 的 Chamfer 單向距離，**再與「把 A 隨機稀疏化到 |B| 顆」的對照組比較**
3. 差值 ＝ 扣掉稀疏化後的**真實移動量**

**預期產出**：一個能跟 RAIN-GS Table 2（0.349 / 12.100，需換算成場景尺度比例）對照的數字。
**若我方移動量接近 3DGS 的 0.349** ⇒ 我們也在「搬不動」regime ⇒ ABE-Split 值得借。
**若接近 12.100** ⇒ `noise_lr` 已經在做傳輸 ⇒ 不用借。

### E3【CPU，~15 分鐘】v1 的 77,616 顆為什麼只低 1.3 dB？ ← 解決 P4 的未解部分

**做法**：對 `aggr24k_b12`（77.6k / 22.070）與 `b12_cap2m_reg000_exact`（1.8M / 23.39）：
- 逐顆螢幕足跡分佈（沿用 `tools/calibrate_block_caps.py` 的 τ 量測）
- 紋理比（`feedback_metric_resolution` 認證過唯一有鑑別力的尺）
- 兩者的離表面距離

**為什麼重要**：如果 77.6k 的**紋理比**也接近，那「極稀疏高效率前緣」是一條真實且**極便宜**的路線
（24k 步、3.8 it/s、VRAM 1.5G），而且正好落在 RAIN-GS 漸進低通會**開始有意義**的 N 區間
（77.6k → 半徑下界 2.4 px，而 1.3M 是 0.59 px）。

## 附錄 B：2026-08-06 晚間的三個自我修正

### B1 ⛔ `cap_max` 設在低於當前顆數 ＝ 把 densify 永久關閉（設計缺陷，與 P7 無關）

`add_new_gs`：`num_gs = max(0, min(cap, 1.05N) - N)`。N 一碰到 cap，`min(80000, 84000)=80000`
⇒ **`num_gs = 0`，densify 永久關閉**；但 relocation 與 trim 照跑 ⇒ **只剩破壞沒有建設**。

⇒ `cap80k_60k_b12` **就算沒有 P7 也測不出「少而準」**。使用者指出「反而會影響增生剪枝（效率差）」，
正確。**重跑 cap80k 的建議撤回。**

**取代方案（免訓練）**：把已經健康的模型**事後剪枝**到各種顆數，量建築紋理比。
工具 `tools/prune_curve.py`。它同時分離兩件先前被 cap 混在一起的事：
「小模型能不能**表現**這個場景」 vs 「我方密度控制能不能**走到**小模型」。

### B2 ⚠ `compare_init_geometry.py` 的覆蓋倍數/overdraw **不可跨類比較**

```
                        覆蓋倍數   overdraw    結果
coarse_mc_aerial_1.2x     8.60      565.7     幾何 67.1×（我曾判「異常」）
oreg 60k                  8.79      629.8     23.848 ← 我方最佳
official_ft_blk5         17.76     1775.1     23.342
```
**我方最好的模型比我判定為「異常」的那個更極端。** 根本缺陷：**指標完全不看 opacity**
（init 一律 0.99，訓練後中位 0.03~0.11）。一顆又大又透明的高斯在 binning 成本上很貴、
在成像上幾乎不存在，兩者被混為一談。

⇒ **8~18 才是訓練後模型的常態**；拿 init 的 3.67 去判訓練後的 8.60 為異常是**比錯對象**。
`coarse_mc_aerial_1.2x` 真正的問題是**離表面 67.1×**（獨立量測），不是覆蓋倍數。

### B3 ⚠ 「可見表面容量 ≈ 36.2 萬」目前**不可證**，只有兩個點

```
餵 1,316,223 → 存活 360,817
餵   991,841 → 存活 363,190
```
兩點一致但**不構成證明**。要證需要：①**掃投入量**（30萬/60萬/120萬/240萬，看存活是否持平）
②**掃解析度**（改 `down_sample_factor`，看存活是否隨像素數等比例）。兩者皆便宜（起始 trim 在
step 1 就跑完）。**在證明之前這只是假說，不可寫進論文。**

（`prune_curve.py` 順帶測它：若品質撐到 ~36 萬才崩 ⇒ 支持；一路平滑下滑 ⇒ 不支持。）

### B4 C 案（SfM 密度加權深度損失）**擱置，可能淨負**

SfM 稀疏處正是水面與無紋理牆，**那裡光度梯度也接近零，深度是唯一約束**。
按 SfM 密度降權 ＝ 在唯一有訊號的地方把訊號關掉。
（時間衰減與空間權重是正交的兩件事，相乘即可，不需另設衰減——但這不是它的問題所在。）

### B5 B 案（SfM-guided relocation）槓桿已確認

`oreg_0p002_b12`（乾淨 60k）relocation 死亡率**平均 9.8%、最大 23.9%、27 次事件**
⇒ 60k 內累計換血約 2.6 次。**「新點該去哪」確實有份量**，而且 relocation 的目的地
**不受遮擋影響**——那正是 init 端錨點失敗的原因。⇒ track 長度這個標籤唯一還活著的用法。
