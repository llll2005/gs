  Ran 1 shell command

forward 在做什麼

五個階段,前四個 O(N) 或 O(Load),第五個才是大宗:

1. preprocess(每顆平行):投影、算 2DGS 的三個齊次平面 Tu/Tv/Tw、算半徑、算覆蓋幾個 tile、SH→RGB。O(N)
2. 複製鍵值:每個 (tile, 高斯) 配對寫一筆 (tile id, 深度)。這就是 Load
3. 排序:按 (tile, 深度) 基數排序 Load 筆
4. 切出每個 tile 的範圍
5. renderCUDA:每個 tile 一個 block、256 條執行緒 = 256 個像素,各自遍歷該 tile 的所有高斯

為什麼第五階段這麼貴

每個 (tile, 高斯) 配對要付 256 次像素計算,而每一次都不便宜(forward.cu:404-450):

兩個齊次平面 k, l  →  叉積得交點 p  →  除以 p.z 投到 splat 平面
→ 3D 馬氏距離 rho3d  →  2D 螢幕距離 rho2d  →  取 min
→ 深度、near plane 檢查  →  exp(power)  →  alpha 混色

一次叉積、兩次除法、一次 exp。這是 2DGS 特有的 ray-splat 求交,比 3DGS 直接算 2D 高斯貴。

成本 ≈ 256 × Load × (每次約 20 個浮點運算),而不是 O(N)。所以 Load 才是對的成本單位。

三個浪費來源:
1. 外接盒是正方形(用較長軸撐出來的)⇒ 長寬比 k 有 1−1/k 的 tile 完全空白。b12 實測浪費 76.5%
2. 一個 tile 裡的高斯,256 個像素每個都要算一遍,不管它實際蓋到哪幾個像素
3. 提前結束(T < 1e-4)只救得了被前景擋住的,救不了「在 tile 裡但不在這個像素上」的

但有個重要的落差要先講

如果 forward 純粹是 O(Load),Load 砍 77% 時 forward 應該也砍 77%。實測只砍 17 到 21%。

差距的原因:
- 階段 1 是 O(N),完全沒變
- 被 v/c 剪掉的那些本來就是便宜的、或已經被提前結束跳過的 —— 它們在 Load 的帳面上很大,但在實際的像素迴圈裡沒真的花那麼多
- 排序、kernel 啟動、影像緩衝區的記憶體流量是固定開銷

⇒ Load 會高估可省的時間。 要輕量化 forward,不能只看 Load 的下降幅度。

對你的目標(顆數輕量化)的意涵

既然 forward ≈ 256 × Load,而 Load = Σ(2r/16)²,那降低 forward 有兩條路:

┌──────────────────┬───────────────────────────────┬─────────────────────────────┐
│       路徑       │             作用              │            現況             │
├──────────────────┼───────────────────────────────┼─────────────────────────────┤
│ 減少顆數 N       │ 階段 1 線性降,階段 2-5 跟著降 │ 你要走的方向                │
├──────────────────┼───────────────────────────────┼─────────────────────────────┤
│ 減少每顆的足跡 r │ 只動階段 2-5,但那是大宗       │ trimvpc 走這條,實測 −17~21% │
└──────────────────┴───────────────────────────────┴─────────────────────────────┘

兩條是乘法關係,可以疊。而且第二條有一個還沒碰的結構性浪費:那個 76.5% 的正方形外接盒。Elongation filter 想解它但失敗了(剪掉長條,模型又長回更肥的)—— 問題可能不在「有長條」,而在「外接盒的形狀」。改外接盒要動光柵器,但那是把浪費直接消掉,不是靠剪枝繞過。
