# 指標時間線與姿態稽核（2026-08-01）

起點是一個很簡單的問題：把 PSNR/SSIM/LPIPS 依時間畫成折線，看哪一次加/刪機制讓指標動了。
圖在 `紀錄/metric_timeline.png`，產生器 `tools/plot_metric_timeline.py`（只畫「當前資料」）。
結果比預期的多，也包含三個我自己的錯誤與撤回。

---

## 1. b12 的機制拆解（可信，config 逐項驗證過）

比對 resolved config 確認 `mcmc_sb_ns_b12_cap1m_K1`（07-21）與 `oreg_0p007_b12`（08-01）
**逐項完全相同**：b12 / cap 1M / down_sample 1.2 / opacity_reg 0.007 / scale_reg 0.007 /
sh_degree 0 / max_steps 60000 / train_strips 1。唯一差異是 rasterizer 二進位。
於是整條線可以乾淨拆開：

| 步驟 | PSNR | SSIM | LPIPS | ΔLPIPS |
|---|---|---|---|---|
| A' 07-21（舊 kernel） | 22.12 | 0.592 | 0.742 | — |
| **+ EXACT_SUPPORT**（同 config） | 23.31 | 0.640 | 0.624 | **−0.118** |
| + opacity_reg 0.007 → 0 | 23.11 | 0.652 | 0.525 | **−0.099** |
| + cap 1M → 2M（實得 1.80M） | 23.39 | 0.667 | 0.491 | −0.034 |

兩個要改的既有認知：

**(a) EXACT_SUPPORT 要重新歸類。** 它一直被記成「省 20.3% 渲染 VRAM 的無損優化」。
在固定模型上它確實是位元級無損（maxdiff 0 驗過），但訓練時被 binning 剔除的 primitive
**拿不到梯度**——那是一個隱式稀疏化機制。它是我們量到過最大的單一品質槓桿。

**(b) reg→0 讓 PSNR 掉 0.20 卻讓 LPIPS 進步 0.099。** 只看 PSNR 會做出相反的決定，
把一半的收益丟掉。b12 大約一半畫面是平坦水面，PSNR 被稀釋，LPIPS 才看得到建築。

## 2. 「平原期」不是機制無效，是尺失去鑑別力

當前資料的 b12，07-19～07-28 的 MCMC/SB 系列全部擠在 LPIPS **0.720–0.742，全距 0.022**。
第一直覺是「這些機制都沒用」。**那個結論不成立。** 把同期跑次依存活狀態拆開：

| | n | 平均 PSNR | 平均 LPIPS |
|---|---|---|---|
| 30~34k 就 OOM 死掉 | 4 | 19.39 | **0.729** |
| 完整跑完 60k | 9 | 21.97 | **0.737** |

（排除崩到 10.4 dB 的 `dar_arm_b12`）

**半途死掉的殘廢模型 LPIPS 反而比健康跑完的「好」**（差 4.4 dB PSNR，LPIPS 差 −0.008）。
一個指標若無法把「OOM 死在半路」和「健康跑完」分開，它在該區間就沒有解析度，
**那段時間任何 <0.02 的 LPIPS 差異都不能下結論，正反方向都不行**。

⇒ 那些實驗的狀態是「**沒測過**」，不是「測過沒用」。負結果有資訊（此路不通），無結果沒有。
凝結退火、harvest 三臂、色彩手術等，現在都應視為未決。

⇒ 另外，同期有一半的機制（K-strip、塵埃收割、v/c 剪枝、SB color）本來就是**成本側**槓桿：
目標是同品質下省 VRAM／省顆數，**品質持平即設計成功**。用 LPIPS 評它們是量錯軸；
它們的 VRAM 與顆數數字仍然有效。

⇒ EXACT_SUPPORT 之後四臂散成 0.491/0.525/0.536/0.624（跨度 0.13），尺才恢復鑑別力。
所以 §1 那張三段拆解表可信（落在有鑑別力的區間），但它上面那段平原不可信。

**方法論教訓**：我們有大量 OOM 死掉的跑次，本來就該拿它們當「已知的壞模型」去校驗指標
有沒有解析度。這個檢查免費、隨時可做，而它在 CSV 裡躺了兩週沒被做。

**⇒ §7 已補測完畢，結論比預期強**：那段「平原」底下，建築區的紋理比差了 **4 倍**
（舊 kernel 0.069~0.099 vs 新 kernel 0.315~0.393），而且 **LPIPS 連死掉的模型都分不出來**。
替代尺**紋理比 = 渲染梯度 / GT 梯度**已驗證有 7× 分離且完全不重疊。詳見 §7。

## 3. 姿態稽核 — 三次撤回，以及一個關掉的分支

驅動問題：使用者回報 test 畫面「結構大致對、細節全糊、滿天 floater」，而自跑 CityGSV2
在當前資料上 LPIPS 0.659、舊資料上 0.169。想找出 0.169 → 0.659 的成因。

**撤回 ①「CityGSV2 擬合不了自己的訓練集」。** 依據是 `train/ssim` 0.494 vs 0.869。
錯的：`train/ssim` 是訓練途中單一 batch 的快照，不是擬合度。我方最佳 b7 的 train/ssim
只有 0.370，val/ssim 卻是 0.770。此欄位跨 run 不可比。

**撤回 ②「`images_1.2 -> input` 符號連結造成影像與內參錯位」。**
`internal/dataset.py:59` 會把讀進來的影像 resize 成相機的 `(cam_w, cam_h)`，符號連結無害。

**撤回 ③（最嚴重）「COLMAP 姿態有 47 px 全域 drift、18% 相機局部矛盾、逐塊壞相機比例
b17 42% ～ b11 0%」。** 全部是我自己的 off-by-one 造成的虛構發現：COLMAP 影像 `N` 對應
GT 幀 `N+1`。修正配對後殘差是 **0.0 px**。

⚠ 這個假發現當時長得非常像真的：數字有結構（b12 35.9% 高、b11 0% 低）、和「b12 一半是水
所以 COLMAP 在那裡失敗」的物理故事完全吻合、還解釋了 b12 vs b7 的品質差。**唯一救回來的線索
是 p90 出現重複的離散值（242.9 px 出現在 5 個區塊）——殘差取離散值代表索引錯位而非量測誤差。**

### 修正後的事實

`data/matrix_city/aerial/train/block_all/sparse/0` 存的**不是 COLMAP 估計的姿態，
而是 MatrixCity GT 姿態 × 1/100**：

- Umeyama Sim3 對齊 5621 張後殘差 **0.0 px**（全域 / 局部 / p99 全為 0）
- 尺度因子 **s = 0.010000，恰好 1/100**（乾淨的單位換算）
- COLMAP 只做了三角化：3.83M 點，重投影誤差中位 0.367 px

工具：`tools/audit_pose_consistency.py`（純 CPU 數分鐘）。已改成**搜尋索引偏移**而非信任檔名，
偏移表會印出來，同樣的錯不可能再靜默發生。資料集若重生，第一件事就是重跑它確認殘差仍為 0。

**結論：「霧」不是姿態造成的。這條病因分支永久關閉。**

## 5. 逐塊評測官方 test 是無效的（2026-08-01 實測，主線因此重排）

接上官方測試集後第一批數字看起來很嚇人（b12 held-out PSNR 15.0 vs val 23.4），但逐項查下去
發現那不是泛化落差，而是**協定本身無效**。過程中我又撤回了兩件事，記在這裡以免重犯。

**撤回 ④「我方訓練集與官方不同」** — 見上一節，3932 是本機產物。

**撤回 ⑤「b12 壞掉、b7 正常」** — 我用「相機中心落在該塊 AABB 內」挑訓練視角，但分區是用
**可見度**指派的，AABB 只是它的超集。拿分區外的相機去渲染單塊模型，本來就沒有有效幾何，
自然是碎裂的。改用分區清單本身重驗後：

| | 建築視角 PSNR | 渲染紋理／GT 紋理 |
|---|---|---|
| block 7（分區清單 192 張） | 19.9 / 21.0 / 21.5 | 0.63 ~ 0.72 |
| block 12（分區清單 284 張） | 16.6 / 17.0 / 20.9 | 0.23 ~ 0.64 |

範圍重疊，**兩塊都能重建自己分區的訓練視角**（b12 的白色高樓、藍色屋頂、街廓都認得出來），
只是都比 GT 少了三到四成紋理。b12 略差但不是壞掉。

### 為什麼逐塊評測無效

b7 模型渲染一個官方測試視角：**畫面左半重建正常（建築、屋頂、窗格都在），右半與上方是
空白與拉絲**——那是塊的內容邊界之外。單塊只擁有 1/9（3×3）或 1/25（5×5）的城市，而航拍
視錐涵蓋範圍遠大於此，畫面大半渲染成空，PSNR 就卡在 ~15 dB，**與該塊好壞無關**。
偏移校準也因此分不出候選（三個偏移都 ~15 dB），這正是校準守門機制該擋下的情況。

同理，`web_demo` 讓使用者從任意角度看，單塊或少數幾塊的模型一離開覆蓋範圍就是碎裂加霧——
先前「整個空間覆蓋滿 floater」的觀察有一部分是這個成因，不全是模型病態。

**⇒ 只有合併模型的官方 test 數字能對外比較。** 主線因此重排為 3×3 全場景。

## 7. 兩個診斷的結果（2026-08-02 01:07~01:12，純推論）

工具：`tools/rescore_by_content.py`、`tools/measure_signal_ceiling.py`
原始輸出：`紀錄/rescore_plateau.txt`、`紀錄/rescore_by_content.csv`、`紀錄/signal_ceiling.txt`
取樣一律來自**分區清單**（非 AABB），並按 GT 梯度分成水面組／建築組各 8 張。

### 7.1 「平原」底下藏著 4 倍差距

只看建築視角：

| 群組 | 建築 PSNR | 建築 LPIPS | **紋理比** |
|---|---|---|---|
| 舊 kernel（7 個跑次） | 17.7 ~ 18.3 | 0.879 ~ 0.929 | **0.069 ~ 0.099** |
| 新 kernel（4 個跑次） | 19.4 ~ 20.0 | 0.566 ~ 0.648 | **0.315 ~ 0.393** |
| 已知壞（30k OOM 死掉） | 16.5 ~ 16.6 | 0.920 ~ 0.927 | **0.011 ~ 0.012** |

**舊 kernel 的模型在建築區只重建出 GT 紋理的 7~10%**——不是「有點糊」，是幾乎沒有細節。
val 的 LPIPS 平線（0.72~0.74）把這件事完全蓋住，因為 b12 一半是水，
而水面只要塗成均勻色塊就有 32~40 dB。

### 7.2 尺的校驗（同 kernel regime 內比較才公平）

| 指標 | 健康跑次 | 已知壞 | 判定 |
|---|---|---|---|
| **紋理比** | 0.069 ~ 0.099 | 0.011 ~ 0.012 | ✅ **7× 分離，完全不重疊** |
| 建築 PSNR | 17.74 ~ 18.33 | 16.53 ~ 16.62 | ✅ 不重疊 |
| 建築 LPIPS | 0.879 ~ 0.929 | 0.920 ~ 0.927 | ❌ **完全重疊** |

⇒ **紋理比 = 渲染梯度／GT 梯度，是目前唯一驗證過有鑑別力的品質尺。**
LPIPS 連「30k 就死」和「跑完 60k」都分不出來。
（工具印的組內標準差把新舊 kernel 混在一起而偏大，但分 regime 檢查結論相同。）

### 7.3 副產物：清塵剪掉 92% 顆粒，建築紋理零損失

`mcmc_sb_b12_cap1m_harvestdust`：**N = 73,637**（比基線少 12.2 倍），建築紋理比 **0.094**；
同期 900k 基線 `mcmc_sb_ns_b12_cap1m_K1` 是 0.090。
**成本側工作最強的一個佐證**，而它一直躺在那個被誤判為「無效」的平原裡沒被看見。

### 7.4 ⚠ opacity_reg 的排序在建築區反轉

新 kernel、同 cap（0.9M），只看建築視角：

| | 建築 PSNR | 建築 LPIPS | 紋理比 |
|---|---|---|---|
| reg=0 | 19.43 | 0.604 | 0.338 |
| **reg=0.002** | **20.04** | **0.580** | **0.372** |

## 8. 合併路徑的 bug 與修復（2026-08-03）

第一次中途合併（五塊）在 11 秒內失敗：

    utils/merge_citygs_ckpts.py:111  state = optimizer["state"][param_group_idx]
    KeyError: 1

**成因是我方模型自身。** 檢查 ckpt：optimizer 1 有 6 個 param group
（`shs_dc`0 / **`shs_rest`1** / `opacities`2 / `scales`3 / `rotations`4 / `sb_params`5），
但 `optimizer["state"]` 的鍵只有 **[0, 2, 3, 4, 5]**。
`Gaussian2DSB` 的顏色來自 `shs_dc` + `sb_params`，**`shs_rest` 配置了卻從未使用**
→ 永遠收不到梯度 → Adam 不會替它建立 state。合併程式用 group 索引盲取 state 就撞洞。

**修復**（已套用）：`optimizer["state"].get(param_group_idx)`，取不到就跳過並記錄。
沒有動量要合併的參數，其**值**由依名稱處理的 `state_dict` 迴圈負責，跳過是安全的。

**驗證**（2026-08-03，`CUDA_VISIBLE_DEVICES=""` 純 CPU，不干擾訓練中的 blk2）：

## 9. 第一次合併評測的兩個 bug（2026-08-03 18:31，7 塊）

合併本身成功（5,050,606 顆），**且 5M 模型在 GPU 上載入與渲染探針視角都正常**
——大型合併模型沒有 VRAM 問題。但評測掛掉，而且是**靜默**掛掉。

**Bug A（`tools/eval_official_test.py`）**：省略 `--block` 時 `sel` ＝全部 741 幀，
探針取樣包含**頭尾兩端**：相機 `0000.png` 在 offset −1 映射到索引 −1、`0740.png` 在 +1
映射到 741，兩者越界。原程式一碰越界就 `break` 丟掉**整個 offset**，只剩 offset 0 一個候選，
`max(... if k != best)` 對空序列丟 `ValueError`。
**修**：探針改取 `sel[1:-1]`；越界時只跳過**該探針**而非整個 offset；
需 ≥2 個有效探針才給分；`scores` 全空時若已指定 `--offset` 就直接採用。
純 Python 驗證（不需 GPU）：全 741 幀時探針＝`[1, 247, 493, 739]`，三個 offset 皆可比 ✓

**Bug B（`scripts/merge_3x3_and_eval.sh`）— 更危險**：兩次評測都經 `| grep | tee`，
而 pipeline 的退出碼取自**最後一個**指令，所以 runner 收到 rc=0、台帳記 DONE，
**兩次 traceback 全被當成成功**，佇列直接往下走、下一個區塊佔卡八小時後才被發現。
**修**：`set -o pipefail` ＋ 每次評測後 `|| rc_any=1` ＋ 結尾非零則 `exit 1`。

**副產物**：`cull_dust` 在合併模型上只剪掉 **1.1%**（5,050,606 → 4,994,449），
而單塊時是 7.4×。因為合併依格子歸屬已丟掉每塊 68~75% 的顆粒，塵埃在那一步就清掉了。
⇒ **清塵是單塊階段的工具，對合併後的模型幾乎沒有作用**。

### 11.2 自我強化機制

    不透明毯子 → MCMC 以 opacity 取樣 → 更多粒子放進毯子 → 毯子更不透明
        ↑                                                      ↓
        └────────── 毯子下方被遮擋，拿不到梯度 ←────────────────┘

模型 63.3% 的高斯 o>0.9、中位不透明度 0.996。毯子獲得最多 relocation 配額，
而它遮住的真實幾何拿不到任何梯度。**這是「內參代理」失效的教科書案例。**

⚠ **但重新加權取樣器解不了這個問題**：MCMC 的 `relocate_gs` 是把死掉的高斯搬到
**既有高斯的位置**再加擾動。改機率只會換「複製到哪顆既有粒子旁邊」，
**永遠不會在「目前什麼都沒有的地方」放粒子**。毯子問題是結構性的，不是機率性的。

### 13.1 ⛔ 我的設計錯誤：量 coarse 自己的深度回答不了問題

我原本說「只要量 coarse 模型自己的深度偏差就能回答毯子的成因」。**那是錯的。**

- **coarse 本來就不該有準確幾何**：它是分區用的粗略代理，50 萬顆蓋整座城市。
  這個剔除量是**演算法決定的**（同一個 controller 在 8×A100 上也會這樣），不是預算造成的。
- **讀數在視角間變異極大**：8 視角得 slope 0.356 / corr **+0.585**，6 視角得 0.240 / corr **−0.193**。
  負相關代表那組數字是噪音。
- 拿 50 萬顆的粗略代理去跟我方 7.18M 顆的合併模型比 slope，是比兩種不同性質的東西。

⇒ **真正該量的是「從 coarse 微調出來的區塊模型」**，那才和我方逐塊模型同性質可比。
而那正是我當初為了避開 OOM 而砍掉的階段。

### 13.2 量測工具的修正與一個被推翻的假設

加了 `--min_alpha`（只採納累積 alpha 達門檻的像素），理由是「稀疏模型多數像素沒有表面」。
**實測推翻**：官方 coarse 與我方合併模型的覆蓋率**都是 100%**——50 萬顆大高斯確實把畫面蓋滿了。
過濾保留（正確的防禦性寫法、無副作用），但視角間變異才是真正該回報的量，尚未補上。

### 13.3 實質收穫（與毯子無關但重要）

**官方全域 coarse 在 6GB 上可行**：1.8 h、峰值 1.72 GB。四次失敗全是可修的工程問題，
