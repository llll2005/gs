## 2. 新物理圖像（v3）：殭屍經濟 (Zombie Economy)

- **工作集** ~1 萬顆（o 高、尺寸真實）扛整張 22dB 的圖。
- **殭屍庫存** ~88 萬顆：opacity L1 + scale L1 聯手把點碾到
  o~0.01-0.05、scale~0——**但停在 min_opacity=0.005 死亡線之上**
  → 不死（不觸發 MCMC relocation 回收）、不渲染（次像素×近透明）、
  不省（照付 F floats 模型記憶體 + cap 額度 + O(N) projection 算力）。
- **機制根因 = 兩條線錯位**：L1 均衡停車位（光度梯度 ~= lambda_o 處，
  實測 o~0.02）在死亡線（0.005）**之上** → MCMC 的回收引擎接不到屍體。
  躺平不如死透——死了還能被 relocation 送回工作集當探針。
- 回合 3 的「外觀容量/微視差」假說：**陣亡**（塵埃無渲染貢獻，談不上容量）。
  法向一致性 0.971 降格為副現象（被碾碎前對齊過，或塵埃繼承出生時的法向）。

**旁證回收**：我方舊實驗「importance-prune 砍 50% 零 PSNR 損失」——當年當
黑箱結論收檔，現在有了機制解釋：砍掉的全是殭屍。

## 3. 對我方 cost-aware 論文主線的意義（請你 stress-test）

1. **cap_max 的顆數會計=殭屍會計**：count-based 預算（MCMC cap）不僅盲於
   渲染成本（我方原命題），還把 97% 的預算花在殭屍庫存上。
2. **計價框架需補「存放成本」項**：殭屍的 render cost ~0 但 model-state cost
   = F*4*M bytes 實打實 → 正確計價 `c_i = render_cost + storage_cost`。
   （我方 gsplat 探針的 CostAware 本就有 storage_cost_tiles 項，當時拍腦袋，
   現在有了實證錨。）
3. **count ablation 重讀風險**：Arm B（cap 2.0M）若增益小，可能不是「內容
   天花板」而是「**cap 加的全是殭屍、工作集沒長**」——等 B 出爐必須先量
   它的工作集大小再下結論。（B 的 ckpt 一到手就跑同款審計。）
