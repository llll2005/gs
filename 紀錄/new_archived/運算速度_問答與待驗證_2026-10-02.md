# 運算速度：問答紀錄與待驗證清單（2026-10-02）

背景：使用者決定「先處理運算速度」，4x4 我方最佳解暫停（lab 佇列已移除，prep 從未開跑）。
本檔記錄這輪問答的結論，並把每一句標成 **已量**／**推論**／**估計**，讓之後能逐條驗證。

## 一、問答

### Q1 白算的那些計算，是 CityGS 原程式碼要用、我們廢棄的嗎？
是。2DGS 的光柵器每像素累積深度、法線、中位深度、distortion，是為了 2DGS 的法線一致性 loss、
深度 distortion loss，以及 CityGSV2 的偽深度監督。我方配方 `lambda_normal=0`、`depth_loss_weight.init=0`、
`lambda_dist=0`（預設）=> 這些圖在我們這裡**算完即丟**。
trim pass（record 模式）照算顏色則是**上游本身**的浪費，官方配方也一樣。
⚠ `depth05`（深度 loss 重測，已在佇列）若贏，深度通道又會被用到 => lean 要加「只保留深度」模式。

### Q2 逐個查找修改，還是開新專案重寫成乾淨 pipeline（順便升級 Python/套件）？
建議**逐個改，但由量測驅動**（先 kernel 拆解，再按時間大小排序打）。理由：
- 時間幾乎全在 GPU kernel；Lightning／dataloader／Python 的迴圈外開銷實測只佔每步約 2%（**已量**，§資源彙整 1.2）
  => 重寫換掉框架能得到的很少；真正有用的是換 kernel 的做法，原專案裡就能做。
- Python 版本不改變 kernel 速度；**PyTorch** 版本才可能（`expandable_segments` 取代 max_split 的固定 6.4%、
  fused optimizer、`torch.compile`）。可以「程式碼不動、只換環境」當**單變數**測 => 解決「分不清是版本還是重構變快」。
- 重寫要重新移植並重驗幾十項（EXACT_SUPPORT、conic、absgrad、v/c trim、zfill 修正、uint8 快取…），
  所有基準要重跑；本專案已抓到 7 個「看起來正常但沒作用」的 bug，移植風險高。
- 逐個改且每次證明逐位元等價（如 lean）=> 既有結果全部仍可比。
- 若要換光柵器（例：gsplat 的 2DGS，已有 warp 內加總、packed 模式），那是換渲染器**一個模組**做 A/B，不是重寫整個專案。

### Q3 梯度計算是不是運算大宗？
約一半。本機 b6、N=1.54M、增生期每步 492 ms（**已量**，`紀錄/資源與效能量測彙整.md` §1.2）：

| 段落 | 增生期 | 收割期（無 trim，**推論**：去掉 trim 後重新歸一） |
|---|---|---|
| backward（梯度） | 35% | ~50% |
| 週期 trim（只有 forward） | 31% | 0 |
| forward | 19% | ~28% |
| optimizer（套用梯度） | 9% | ~13% |
| loss | 3% | ~5% |

整趟 60k 平均（**估計**）：梯度相關（backward + optimizer）約 50%，渲染類（forward + trim）約 40%。

梯度內部分兩種：
- **逐 (像素, 顆粒) 配對**：光柵 backward kernel 每個配對做 atomicAdd，對象是 13 個渲染空間量
  （顏色 3、opacity 1、transMat 9）＋ absgrad 1 ＋ 加 0 的法線 3（lean 去掉的就是這 3 個）=> 每配對 17 個。
- **逐顆／逐像素**：前處理 backward（SH、投影）、N 大小的 PyTorch 小運算、SSIM、Adam。
- 兩者比例（**推論**，假設時間與配對數成正比）：v/c trim 同 N 下 Load −63%、fwd+bwd −27%（**已量**）
  => 逐配對約佔 fwd+bwd 的 0.27/0.63 ≈ **43%**，其餘約 57% 不隨配對數變。⏳ 由 kernel 拆解驗證。

### Q4 對參數做特徵壓縮，讓梯度只算一種數而非五種？encode/decode 划得來嗎？
- **打不到逐配對那一塊**：SH 的 48 個係數在光柵化前就逐顆解碼成 3 個顏色，配對層級只碰 13 個渲染量
  —— 這一層本身就是「已壓縮」的表示。參數怎麼壓，配對層級都要算顏色／opacity／幾何。
  減少它只能靠「配對更少」（trim、v/c、conic、EXACT_SUPPORT）或「每配對更便宜」（lean、warp 內加總）。
- **打得到逐顆那一塊**：每顆 58 個 float，SH 高階佔 78%（**已量**，記憶 storage_structure）。
  壓縮省 Adam、逐顆前處理、N 大小運算的時間，以及 **VRAM**（VRAM 主要由 N 決定 => 6GB 內能放更多顆，
  對命題可能比速度更有價值）。
- encode/decode 成本看解碼器：codebook 查表便宜，但 backward 要把梯度 scatter 回共享碼本（atomic 搶位址）；
  MLP 解碼（Scaffold-GS 類）貴，且本專案已退役；SB 顏色（25 float/顆）也退役（+35% 顆數、六項全輸）。
- **最便宜的單變數版本＝降 SH 階數**：官方 CityGSV2 空拍就是 sh2，我們是 sh3。sh3→sh2 每顆 58→37 float（−36%），
  沒有額外編解碼（SH 求值本來就有，係數少更省）。品質要實測 => 已排 `csh2`。

### Q5 逐 (像素, 顆粒) 配對主要用於什麼？訓練一定需要嗎？
**一定需要 —— 它就是可微光柵化本身，也是訓練訊號的唯一來源。**
- forward：每個像素的顏色 = Σ_i c_i·α_i·T_i（沿深度序把覆蓋它的顆粒逐一混合）。
- backward：把每個像素的 loss 梯度分回給每個覆蓋它的顆粒 => 每顆的顏色、opacity、形狀／位置梯度
  都是「它覆蓋的所有像素」的總和。沒有這一步就沒有梯度。
- 我方配方在配對層級上搭載的東西：
  ```
  渲染與光度 loss 的梯度（L1+SSIM）      必要
  absgrad（|dL/ds| 逐配對取絕對值再加總） 增生取樣用（現行配方開 2.0）
  trim 的貢獻 v（record：T·α 逐配對累積）  週期 trim 判準
  覆蓋數 c（逐配對計數）                  v/c trim、成本 c_i
  tiles（binning 的 (tile,顆) 對數）       Load／成本預算
  深度／法線／distortion                  ⛔ 現行配方沒有消費者（lean 去掉）
  ```
- 能動的只有「做多少配對」與「每個配對多貴」：
  ```
  配對更少   trim／v/c trim（Load −63%）、conic 精確外接盒（−40%）、EXACT_SUPPORT（o<=1/255 不進 binning）、
             T<1e-4 提早結束（已有）、alpha<1/255 跳過（已有）
  每配對更便宜 lean（去掉 3 個加 0 的 atomicAdd＋幾何算術）、warp 內先加總再 atomic（同 warp 32 條執行緒打同一顆）
  像素更少   低解析度起步（coarse-to-fine）／像素抽樣 —— 會改變訓練，要訓練驗
  ```

### Q6 把整個計算搬到 latent space 會如何？還是現在就是？
**現在不是。** 現在是：逐顆參數（log 尺度、logit opacity、四元數、SH 係數）-> **固定的逐顆解碼**
（SH 基底把 48 個係數解成 3 個顏色；位置／尺度／旋轉解成 9 個 transMat）-> 在**全解析度 RGB 像素**上逐配對混合。
SH 可以看成「固定基底的逐顆 latent」，但混合本身在像素空間。「latent」有三種搬法，代價落在不同層：

| 作法 | 逐配對 | 逐顆 | 逐像素 | 記憶體 | 風險 |
|---|---|---|---|---|---|
| 現在 | 3 色＋opacity＋幾何 | SH 48->3 | L1+SSIM | 58 float/顆 | — |
| A 逐顆 latent＋共享解碼器（Scaffold-GS 類） | 不變 | ↑ 解碼器 fwd/bwd | 不變 | ↓↓ | 本專案 Scaffold/latent-MLP、SB 顏色都輸過 |
| B 渲染 K 維特徵圖，逐像素小 MLP 解成 RGB（延遲著色） | K 個通道（K>3 反而變貴） | ↓（SH 48->K） | ↑ 小 MLP | ↓ | 視角相依改靠 MLP，未測 |
| C 低解析度 latent 影像＋學習式解碼／上採樣 | ↓ s² 倍 | 不變 | ↑ 解碼網路 | 不變 | 細節由解碼器生成 => 虛假細節（本專案已見四次）、PSNR 有上限 |
| C' 解析度排程（前期低解析、後期全解析，無解碼器） | 前期 ↓ s² 倍 | 不變 | 前期 ↓ | 不變 | 最後全解析度，無上限；增生訊號在低解析度下會變，要訓練驗 |

結論（**推論**）：只有「像素變少」那一類（C、C'）打得到最大的逐配對成本；A、B 主要省記憶體、速度持平或變慢。
C 的學習式解碼器對「與 GT 逐像素比」的重建指標風險大；C' 是同一個想法去掉解碼器的版本，可直接測。
💤 提案（未排）：C' 前 50% 步數用 1/2 解析度（相機內參與 GT 同比例縮）。預期增生期每步 −40~50%、整趟 −15~30%（**估計**，
取決於 kernel 拆解的逐配對佔比）；品質要 60k b6/b13 對 cs60_conic。

### Q7 Gemini 的三類解法；誤差引導「完美 tile 不再算」的想法（使用者提，討論中）
**本機論文核對（已讀原文，`參考論文/`）**：
- `taming_3dgs.pdf` §4（Fig. 3a）：3DGS 訓練「backward 是主要瓶頸，其次是 Adam（隨顆數增加）」—— 與我方實測一致。
  §4.1 **per-splat 平行化 backward**：每條執行緒負責一顆、在 warp 內交換「像素狀態（T 與累積顏色）」，取代逐像素 atomicAdd；
  **數值等價**；另外用 tile 的 last contributor 跳過整段被遮住的尾巴；並採用 StopThePop 的更緊剔除。
  引用 DISTWAR [36]＝warp 層級先加總（Gemini 第 1 點說的就是這類）。
  §4.2：SH 高階係數（59 個屬性中的 48 個）改成每 16 步才做一次 Adam（**不等價**）；
  SH dc 與高階不再先 torch.cat 成一個張量（「佔 forward 驚人的比例」，**等價**）；SSIM 改成可分離 1D 卷積＋融合 kernel（等價）。
- `StopThePop.pdf`「Tile-based culling」：用 3DGS 本來就有的 1/255 貢獻條件，把每顆限制在**真正有貢獻的 tile** ——
  逐像素已經會跳過這些配對 => **渲染逐位元相同**，但 binning、排序、forward、backward 的配對都變少。比我方 conic 外接盒更緊。
- Gemini 列的 2025/2026 論文（硬體光柵化、Mono3DGS-SLAM、Splatonic、TurboGS）**未核實**；本專案有 Gemini 幻覺文獻前例 => 下載到原文前不引用。
**之前做過的「降採樣」不是同一件事**：09-12 否決的是 `TRIM_SUBSAMPLE`（trim pass 只看部分**相機**；因為判準是跨視角取 max，
少看相機會讓值變小 => 誤剪，遮罩重疊只剩 81~86%）。**訓練 loss 的像素抽樣從沒測過。**
⚠ tile 式光柵器的抽樣要 tile／warp 對齊：零散抽像素時，同一個 warp 只要有一條執行緒在算，整個 warp 就得跑，省不到。

**使用者的想法**：每隔一段步數比較 render 與 GT，「完美」的 tile 取消標記；每顆記錄涉及的 tile 數，歸 0 後不再處理 => 越後期負載越小。
問題（**推論**，未量）：
1. 訊號其實免費：每個訓練步本來就渲染一個視角並和 GT 算 loss => 每個 (視角, tile) 的誤差可以從訓練步累積，不用另外 render。
2. **最大的瑕疵**：完美像素的梯度正是讓它保持完美的力量。顆粒跨好幾個 tile、好幾個視角共用；
   不算完美 tile 之後，橫跨完美／不完美區域的顆粒只被不完美那邊拉動，可能把完美區弄壞，而且沒有力量拉回來 =>
   「驗過不用再驗」是不可逆的，必須定期重驗。
3. 凍結的顆粒仍要參與渲染（它們會遮擋、也貢獻其他像素的顏色）；真正能省的是「(視角, tile) 層級跳過 forward＋backward」。
   而 Adam 對零梯度的參數仍會照動量繼續更新；MCMC 的位置噪音與 opacity/scale 正則也照常作用 => 要配 selective Adam 等。
4. 能省多少＝完美 tile 裡的**配對數**佔比，不是 tile 數佔比。完美 tile 很可能是平坦地面、水面這些本來就便宜的地方，
   貴的（建築、多層殼）正是不完美的 => 實際省下的工作可能遠小於 tile 比例。
5. 「完美」的判準：相對門檻在空拍圖上會被平坦區汙染（記憶 blur_metric_contaminated）=> 要絕對門檻、要按 Load 加權；
   而且只在訓練視角上完美（val⊂train），凍結可能把「訓練視角好看、別處是 floater」鎖死。
6. MCMC 會搬移顆粒（索引與位置都變），逐顆計數要在搬移時重設。
**改良版**（誤差引導的 tile 重要性抽樣）：誤差高的 tile 每步都算；「好」的 tile 每步只隨機算一部分 p，loss 乘 1/p 補回
=> 梯度期望值不變（Adam 容許這種噪音）、好 tile 仍持續受約束並被隨機重驗。kernel 端是 tile 遮罩（整個 block 提早結束）。
**先量再做**（✅ 10-02 使用者同意，已排 `scripts/lab/task_tile_audit.sh` b6/b13，光柵器加純量測的 `auditCUDA`，訓練 kernel 不動）：在 cs60_conic b6 @14,999／29,999／60,000 上渲染訓練視角，算每個 tile 的絕對誤差與配對數 =>
各門檻下「tile 比例」vs「配對（工作量）比例」＝可省上限；以及 15k 判為完美的 tile 到 30k/60k 還完美的比例。

### Q8 先只訓練灰階，最後再上色（densify → 精修 → 上色）會不會更快？（使用者提）
**前提修正**：trim pass 裡的顏色計算本來就是純浪費，lean 的 MODE 2 已經整段拿掉 => 這部分灰階不會再多省。
**顏色真正的成本**（**推論**，待 kernel 拆解）：
  逐配對  forward 每配對 3 次非合併的顏色讀取＋3 個 FMA；backward 每配對 3 個顏色 atomicAdd（lean 後共 14 個裡的 3 個）
  逐顆    SH 佔每顆 58 個 float 裡的 48 個 => SH 求值、Adam、VRAM（參數＋梯度＋2 動量 = 16 B/float）
灰階（亮度 SH3 = 16 個係數）在前兩階段：逐配對顏色讀取 3 -> 1、atomic 14 -> 12（−14%）；每顆 58 -> 26 個 float（−55%）
  => Adam −55%、VRAM 每顆 −512 B（2.34M 顆約 **−1.2 GB**）。**最大的收益其實是 VRAM 與 Adam，不是逐配對。**
**上色階段很便宜（推論）**：幾何與 opacity 凍結後，像素顏色 = Σ_i w_i·c_i(視角)，權重 w_i = α_i·T_i 固定
  => 對顏色參數是**線性**問題（L2 下是凸的最小平方），收斂快；backward 也只需顏色那 3 個 atomic。
**關鍵前提已量（✅ 已量，CPU，b6 60 張 GT，1600x900）**：
  梯度能量 亮度 Y **85.6%** ／ 色度 Cb+Cr 14.4%
  明顯色度邊（|∇C|>0.05）佔像素 4.59%，其中亮度幾乎不變的「等亮度邊」只有 **5.2%**（中位 5.1%、最大 6.9%）
    => 只看亮度會漏掉的邊約佔全部像素的 0.24% —— 幾何從亮度學幾乎不會缺邊
  色度變異中 <4px 細節佔 26.6% => 色度不是全低頻，上色階段仍要有足夠的空間解析度（由幾何決定，已凍結）
**風險**：①等亮度邊的幾何不會長出來，凍結後上色修不了（已量：約 0.24% 像素）②三階段多了上色的步數，淨收益看前兩階段省多少
  ③光柵器顏色通道數是編譯期常數 3 => 真正省到逐配對要另生 1 通道的 kernel ④最後可能需要短暫解凍聯合微調。
**同族的單階段替代**：YCbCr，亮度用 SH3（16）、色度只用 SH0（2）=> 每顆顏色 48 -> 18 個 float，逐配對不變（仍 3 通道），
  沒有上色階段也沒有等亮度邊問題；可走現有 `colors_precomp` 路徑（SB 顏色用過的基建）。代價：色度不再視角相依（空拍多為漫反射）。
**測試順序（提案未排）**：①品質原型（不改 kernel）：前段 loss 只算亮度、後段凍結幾何只用 RGB loss 上色，60k b6/b13 對 cs60_conic
  ②品質過了才做 1 通道 kernel 量速度；或改測單階段 YCbCr。sh2（csh2）已排，可先看「顏色參數變少」的品質代價。

### Q9 Gemini 對 Q8 的建議（使用者轉貼）—— 採納與修正
**採納**：先不寫灰階原型；先等 SH 降階的品質數字。另加 **sh0 當底線**（`csh0`，60k b6/b13，⏳ 已排在 csh2 後面）。
**修正**：
1. 「原版 3DGS 的漸進式 SH 就是先建幾何」——我方 config 本來就有（`sh_degree_up_interval: 1000`），**第 3,000 步就到 SH3**，
   而且高階係數從第 0 步就配置好、Adam 也照跑 => 對一個 60k 的訓練既不省記憶體也不省時間，不是「先幾何後外觀」。
2. 「SH0 比灰階好，避開等亮度邊」——等亮度邊已量到只約 0.24% 像素；SH0（3 個）與灰階（1 個）只差每顆 2 個 float。
   真正的槓桿是丟掉 45 個高階係數。使用者的想法若改成「大半訓練只用 SH0、最後才解鎖高階」就不需要 1 通道 kernel，
   但**峰值 VRAM 出現在最後**（那時高階已配置）=> 省時間（Adam）不省峰值，對 6GB 命題幫助有限；YCbCr 才是永久省峰值。
3. 「YCbCr 省超過 60%」——那是**顏色參數**（48 -> 18，−62.5%）；每顆總參數是 58 -> 28（−52%）。

## 二之一、10-02 lab 結果摘要（細節見 研究總覽_v2 §0「2026-10-02 lab 結果」）
- lean：真實迴圈每步 152.3 -> 120.5 ms（-20.9%），渲染逐位元相同，梯度差在 atomic 順序級（rotations 最大約噪音底 5 倍）。
- fused Adam：torch 2.0.1 下慢 2.3~3.2 倍 => 不採用。
- kernel 拆解：逐配對（光柵 fwd/bwd/record）約佔 kernel 時間 63%；Adam 6%、SSIM 4%。
- lean 後增生期的最大頭是 trim 的 record pass（約 37%）；它每個被評估配對做 2 個 atomicAdd（在 alpha 判斷前）。
- tile 精確剔除上限 30~42% 配對；遮擋尾巴 20~40%；誤差引導的低誤差 tile 不比較便宜。

## 三、判定規則（寫在結果出來之前）

- **lean**：B（新 .so 舊路徑 vs 舊 .so）渲染／radii／覆蓋數逐位元相同，梯度差在 A（舊 .so 兩次）的噪音底內；
  C（lean 關 vs 開）同樣成立 => `task_lean_check.sh install` 裝進 gspl，新跑次加 `--model.renderer.init_args.lean_train true`。
  B 若不逐位元相同 => 新 .so 改到了舊路徑的 codegen，**不可**在比較家族進行中安裝。
- **fused Adam**：50 步後最大差 ≤ 更新量的 1e-5、且 optimizer.step 確實變快 => 新家族用
  `--model.gaussian.init_args.optimization.optimizer.init_args.fused true`。
- **sh2**：與 cs60_conic 比四項指標（PSNR/SSIM/LPIPS/紋理比）；60k 噪音底未量，22k 的 3sd = 0.24 dB 當參考；
  品質持平且成本（profile_runs、VRAM）下降 => 採用；品質掉則記下「每 dB 換多少 VRAM」供 6GB 取捨。
- **warp 加總**：只有在 kernel 拆解顯示「光柵 backward（逐配對）」≥ 每步約 20% 才動手。
