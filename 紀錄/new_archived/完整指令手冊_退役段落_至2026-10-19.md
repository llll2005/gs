## 6. 逐塊 cap 校準（封閉預算公式）

```
N_max = (V_target * 0.9 - V_os) / (4*F*4 + gamma * tau_max * tau_growth / K)
```

```bash
python tools/calibrate_block_caps.py taus --blocks 0-24        # 1) 逐塊量 tau（免訓練）
```
```bash
python tools/calibrate_block_caps.py probe-trim --block 12     # 2) 校準 gamma/V_os
```
```bash
python tools/calibrate_block_caps.py caps --gamma_trim <G> --vos_trim <V>   # 3) 產 cap 表
```
```bash
python tools/measure_tau.py --run <run> --block-list data/matrix_city/aerial/train/block_all/partition/partitions-dim_5_5_visibility_0.08/002_002.txt
```

- `tau_growth` 預設 1.65：init-tau → trained-tau 的漂移修正（b12 實測 73 → ~120）。
- gamma/V_os 是 **kernel-specific**（gsplat 量的 23 B/isect 不能套到 trim）；tau 是幾何屬性，可跨 kernel。
- ⚠ **cap 只交付 90%**：四個跑次全停在 cap 的 90.00%，10% 全掉在收割期
  ⇒ 峰值按 cap 付、交付只有 0.9·cap。
- ⚠ 位元組模型**低估 8~37.5%** 且隨 lobe 數放大（Python 端 autograd 的 N×L 沒計入）。
- ⚠ `紀錄/block_taus.csv` / `block_caps.csv` 舊版已移入 `archive/`（用初始化期的 tau 算的）⇒ 要用請重跑。

## 7. 動態 K-strip ⚠ **會改變 loss，預設不要開**

```bash
--model.dynamic_strips true --model.strip_max 8 --model.strip_vram_target_gb 5.4 --model.strip_v_os_gb 0.8 --model.strip_safety 0.6
```
固定 K 用 `--model.train_strips N`（`dynamic_strips` 關閉時才生效）。

機制：`internal/utils/strip_cameras.py:estimate_render_load`（只投影不渲染）+ `predict_num_strips`
⇒ 把畫面切成 K 條橫帶，**逐帶前向 + 反向**，峰值 VRAM 按帶算。

### ⛔⛔ 2026-09-11 更正（舊版手冊這段是錯的）

舊版寫「K 是 loss 不變量，故可動態調而不影響品質」。**不成立**：
`internal/gaussian_splatting.py:_strip_forward_backward` 的 docstring 自承
*"Image-space SSIM is computed per strip (**boundary-window approximation**)"*。
逐點正則項確實是精確的（帶權重 h/H 且權重和為 1），但**影像空間的 SSIM 不是**。

實際代價（`speed3_sfminit_b12`，N=2.34M）：
```
VRAM 峰值實佔  4.87 -> 4.08 GB（-0.79）
速度           2.44 -> 1.85 it/s（**慢 24%**）
dynk_K.log     K>1 佔 **77.7%**、K>=6 佔 69.3%（K=1 只到 step ~12,900）
=> 77.7% 的訓練步跑在被改過的 loss 上 ⇒ 該次 60k 分數作廢
```

### 而且預測器太保守（`tools/strip_k_audit.py`，純 CPU）

```
兩個 60k 模型（load 中位 5.4M vs 6.9M）在**同一組參數**下都被判 K=6
predict budget = 0.85*(5.2-0.8) = 3.740 GiB
而 depth-init 同 N=2.34M 用 K=1 **實測**峰值 4.87 GB，沒 OOM（卡 6.1 GB）
=> budget 訂低約 1.1 GB，那 24% 的時間是白付的
```
⚠ 舊版手冊寫的公式 `K = ceil(load_bytes / (render_budget × safety))` **是過時版本**，
現行 `predict_num_strips` 還含一個不可切分的 `model_state + A_RENDER*N` 項
（程式碼註解自承舊公式「undercounted the N-scaling term and picked K=1 into an OOM at N=1.45M」）。
⚠ `strip_safety` 是**預算乘數**（`budget = safety*(target - v_os)`，越大越寬鬆），不是折減係數。

**結論**：要省 VRAM 優先用 `cap_max`；`dynamic_strips` 只在確定會 OOM 時開，
而且開了之後**不可與沒開的跑次直接比分數**。

## S-1. SB color 是什麼、相關檔案、訓練指令

### S-1-1. SB color 是什麼

從 Deformable Beta Splatting 移植的色彩表示（**只移植 SB color，不移植 beta falloff kernel**——
後者我方實測淨負且需重寫 CUDA）。公式（ASCII）：

```
C(d) = clamp(SH_eval(shs, d) + 0.5, 0) + sum_i c_i * max(0, <mu_i, d>)^(4*exp(b_i))
```

- 每 lobe 6 參數 `[r,g,b,theta,phi,beta]`，rgb 過 softplus；預設 `sb_number=2`
- 搭配 `sh_degree=0`：色彩參數 48 floats(SH3) → 15 floats(DC 3 + SB 12)
- **每點總 floats：59 → 25**（模型狀態 944B/pt → 400B/pt，公式 F 槓桿，同 VRAM 塞 ~2.4x 點）
- 顏色在 Python 算好走 `colors_precomp` 進 trim rasterizer，**不碰 CUDA**

### S-1-2. 相關檔案

| 檔案 | 內容 |
|------|------|
| `internal/utils/sb_utils.py` | SB 數學（activation + eval，autograd backward） |
| `internal/models/gaussian_2d_sb.py` | `Gaussian2DSB`（config: `sb_number`, `sb_params_lr`） |
| `internal/renderers/sep_depth_trim_2dgs_sb_renderer.py` | `SepDepthTrim2DGSSBRenderer` |
| `configs/mcmc_2dgs_sb_60k_aggr17_aerial.yaml` | aggr17 的 SB 版 config |

kernel 切換 = config 換 `gaussian.class_path` + `renderer.class_path`（jsonargparse 原生機制）。
訓練開始時 stdout 印 `[kernel] renderer=... model=... color=... floats/point=...` 橫幅。
