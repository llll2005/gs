# 初始化溯源：depth-init 的來歷、精度上限，與 SfM-init 這條路

2026-08-05。起因是一個提問：「如果深度圖給的資訊是完全正確的，為什麼我們沒辦法讓點只出現在深度
圖限定的位置範圍中？」追下去之後，結論從「深度損失管不住位置」變成「**病灶在初始化，不在訓練，
也不在剪枝**」。

本檔取代先前把 floater 歸因於剪枝判準不足的一系列推論。

---

## 1. 深度圖對位置到底有沒有約束力：兩層量測

### 1.1 射線層級：已經滿足了

`tools/measure_depth_bias.py`，參照模型 `b12_cap2m_reg000_exact`：

```
渲染深度 slope 1.082   corr 0.903
```

深度損失管的是 `surf_depth`，也就是「沿著射線累積 alpha 的中位深度」——**一個射線的統計量**。這個量
已經對了。

### 1.2 粒子層級：也已經滿足了

`tools/measure_depth_agreement.py`（本次新建）把每顆粒子投影進每個視角，讀該像素的偽深度，跟粒子
自己的相機空間 z 比。跨視角取**最小值**（深度圖只記錄第一個可見表面，被遮擋的粒子在多數視角必然
不一致，取最佳視角才是問「有沒有任何一個視角看得到它貼在表面上」）。

```
覆蓋（至少投影進一個視角）  79.5%
跨視角最佳不一致度 p10/p50/p90 = 0.006 / 0.068 / 0.241
  <10% 佔 62.8%    <25% 佔 90.7%    >50% 佔 0.2%
```

**62.8% 的粒子跟深度圖的一致度在 10% 以內**，而深度圖自身的誤差中位就是 8.6%。也就是說粒子已經貼
到深度圖的解析極限了。

### 1.3 但離表面還是 29×

同一個模型，`tools/floater_label.py:surface_distance`（到最近 SfM 點的距離，單位 = SfM 點彼此的中位
NN 距離 0.00363）：

```
離表面中位 29.2×
```

### 1.4 深度不一致度不能當剪枝判準

```
深度不一致度 vs 離表面距離：r = +0.253
  最一致 20%   286,069 顆   26.9×
  最不一致 20% 286,069 顆   34.4×
  ⇒ 只差 1.3×
```

**判定：❌ 不成立。** 這是繼「多視角集中度」之後**第二個**沒能把 floater 分離出來的判準。

### 1.5 為什麼——精度的量級對不上

| | 場景單位 | 相對於表面解析度 |
|---|---|---|
| SfM 點彼此的距離（表面解析度） | 0.00363 | 1× |
| 我方粒子離表面 | 0.106 | 29× |
| **偽深度圖自身的誤差** | **0.633**（8.57% × 典型深度 7.39） | **174×** |

深度圖的噪音比我們現在的位置誤差**還大 6 倍**。深度損失根本看不到 29× 這個量級的偏差——它在噪音底
之下。

> **⇒ 深度監督這條線已經榨乾了。它不可能再讓位置更準，因為它自己就沒那個精度。**

## 2. 更正：問題在起點，不是訓練

先前一度寫成「depth-init 把粒子放對，訓練把它們推壞」。**這是錯的**，已量測推翻：

```
SfM 點自己彼此              1.0×      （定義上的基準）
depth_init/block_12.ply    20.2×     ← 初始化就偏了（p10 5.7× / p90 45.3×）
訓練 60k 之後               29.2×
28.9 分那次（SfM 世系 init）  6×
官方 b7 重跑                528×
```

訓練只從 20.2 推到 29.2（1.45 倍）。**約 80% 的偏差在第一步就存在。**

---

## 3. 兩個必須先擋掉的混淆

### 3.1 循環論證

`surface_distance` 的定義就是「到最近 SfM 點的距離」，所以 SfM-init 在這個指標上起點必然是 0×。
**這個指標不能用來論證 SfM-init 比較好。** 勝負只能看 PSNR / SSIM / LPIPS / 紋理比。

### 3.2 離表面距離有一部分只是「SfM 比較稀」

參照模型，用 64×64 的 xy 網格統計每格 SfM 點數 vs 該格粒子的離表面中位：

```
該格 SfM 點數      粒子數      離表面中位
      1-200      885,464      34.5×
   200-1000      859,411      24.1×
  1000-5000       55,124       9.8×
```

（b12 範圍內 2,688 個有模型內容的格子中，**沒有一格是 0 個 SfM 點**，所以不是「水面完全沒點」那種
洞；是密度梯度。）

3.5× 的分離度表示**這個指標同時在量「SfM 密度」**。`floater_label.py` 的 docstring 早就警告過這點，
現在有了量化。用它比較模型時必須同塊、同參照點雲。

## 4. 溯源：depth-init 從哪來

`utils/depth_init_blocks.py` 檔頭第 2 行：

```
Depth-Prior Per-Block Initialization (RTG-SLAM style, adapted for offline batch use)
```

**它不是任何一篇 GS 初始化論文的方法**，是我們把 RTG-SLAM 的深度先驗播種搬過來的自製流程。

關鍵落差（**待 Gemini 聯網查證 RTG-SLAM 的輸入型態**）：

| | RTG-SLAM | 我方 depth-init |
|---|---|---|
| 深度來源 | RGB-D 感測器 | Depth Anything V2 單目估計 |
| 性質 | 公制實測 | 相對深度，需 scale/offset 校準 |
| 精度 | 感測器級 | 中位相對誤差 **8.6%** = 0.633 場景單位 = **174×** 表面解析度 |

**機制照搬了，撐住那個機制的精度沒搬過來。**

## 5. 論文怎麼說：SfM-init 是預設，我們才是例外

`參考論文/3dgs.pdf`（Kerbl et al. 2023）原文：

- 行 108-110：*"cameras calibrated with Structure-from-Motion (SfM) ... and **initialize the set of
  3D Gaussians with the sparse point cloud produced for free as part of the SfM process**"*
- 行 113：*"achieve high-quality results with **only SfM points as input**"*
- Fig. 2 的流程圖，起點方塊就是 **"SfM Points"**

CityGaussian V1/V2 的 coarse 模型也是 SfM-init（見記憶 `citygs_official_configs`）。

### 5.1 3DGS 自己的 init 消融，正好對上我們的症狀

行 1175-1184，把 SfM-init 換成隨機初始化之後：

> *"in areas not well covered from training views, the random initialization method appears to have
> **more floaters that cannot be removed by optimization**"*

**初始化不良造成的 floater，優化過程移除不掉。**

這解釋了為什麼我們試過的下游手段全部失敗——貢獻度剪枝、opacity_reg、塵埃收割、多視角集中度
（§1.4 之前那個）、深度一致度（§1.4）——**它們都在下游，病灶在上游。**

## 6. 深度相關的東西要拆成三件，不能一起砍

| | 是什麼 | 判斷 |
|---|---|---|
| **A. depth-init** | 初始點雲（`--model.initialize_from .../depth_init/block_N.ply`） | **最該換**，且零成本 |
| **B. depth loss** | 訓練中逐像素稠密監督（`depth_loss_weight`） | **獨立一臂**，別跟 A 綁 |
| **C. lambda_normal** | 2DGS 自身法向一致性，來自 render 不是偽深度 | **別動**，跟這題無關 |

B 不能跟著砍：SfM 是**點雲**不是**損失**。它只能說「靠近某個點」，沒辦法逐像素監督每個視角。深度圖
在 SfM 稀疏處（§3.2 的 1-200 點/格那 88 萬顆所在區域）仍然提供訊號。砍掉 B 就沒有任何稠密幾何監督。

## 7. SfM-init 不需要寫任何程式

`internal/dataparsers/colmap_block_dataparser.py:148-153`：

```python
if self.params.points_from == "sfm":          # "sfm" 是預設值
    xyz, rgb, _ = ColmapDataParser.read_points3D_binary(
        os.path.join(sparse_model_dir, "points3D.bin"),
        selected_image_ids=selected_image_ids,   # ← 已經逐塊過濾
    )
```

`internal/gaussian_splatting.py:227-229`：

```python
elif self.hparams["initialize_from"] is None:
    # legacy path: SfM point-cloud cold start
    self.gaussian_model.setup_from_pcd(xyz=self.trainer.datamodule.point_cloud.xyz, ...)
```

**⇒ `--model.initialize_from null` 就是逐塊 SfM-init。**

### 7.1 實測 b12 拿得到多少

```
[block_12] 影像 284 / 全場景 5621
[SfM-init] 該塊可見的 3D 點 = 320,513
[對照]     depth_init/block_12.ply = 1,211,537
[範圍]     [-143, -152, -202] .. [202, 112, 4.4]
```

三個推論：

1. **cap_max 不用改。** MCMC 每次 densify ×1.05，320k → 2M 需 `ln(2M/320k)/ln(1.05) ≈ 38` 次事件；
   interval 150 → 約 5,700 步。depth-init 從 1.21M 起只要約 1,550 步。SfM-init 晚約 4,100 步達 cap，
   在 60k 排程內不成問題。
2. **這不是純單變數。** 起始位置變了，**起始顆數也 1.21M → 320k（3.8× 少）**。兩者是 init 方法本身
   的差異，拆不開——報告時必須照實寫，不能說成「只改了位置」。
3. **z 有離群點。** 地面中位 z≈0.20、屋頂 p99≈2.14，但 SfM 點雲 z 最低到 **-202**（比場景高度低 100
   倍）。3DGS 原版不濾這些（靠後續剪枝）。裁掉會多一個變數，傾向第一臂不裁。
